# 실험용 Qdrant 관리

저장소 루트를 기준으로 작업한다. 실행 전 `evaluation/legal-retrieval/README.md`와 `evaluation/legal-retrieval/scripts/lib/QdrantLab.ps1`을 확인한다. 파일 경로는 `scripts/lib/Paths.ps1`을 기준으로 해석하고 문서에 적힌 예전 경로를 그대로 가정하지 않는다.

기존 진입점은 `evaluation/legal-retrieval/scripts/manage-qdrant-lab.ps1`이다. `-Action List`로 목적별 조회, `-Action Verify`로 관리 목록과 실측 결과 검증, `-Action ApplyAliases`로 충돌을 검사한 별칭 적용을 수행한다. 관리 목록은 `experiments/infrastructure/qdrant/collections.json`이며 상세 사용법은 같은 폴더의 `README.md`를 따른다. 새 실험은 실측 메타데이터를 확인한 후 분류 규칙에 추가한다.

## 조사와 분류

- 기존 `Initialize-QdrantLab`과 `Invoke-QdrantLab`을 재사용한다. 이 헬퍼는 로컬 주소와 인증 정보를 설정한다. 키나 헤더, `.env` 내용은 출력하거나 관리 목록에 저장하지 않는다.
- 연결할 주소와 포트를 확인하고 컬렉션 목록, 별칭, 벡터 스키마, 정확한 포인트 수, 소유권 메타데이터를 조사한다. 컬렉션 이름만으로 실험 소유권을 판단하지 않는다. 생산 서비스 컬렉션과 소유권이 불분명한 데이터는 정리 대상에서 제외한다.
- 모델 비교, 검색 검증, 질의 전략, 하이브리드, 인프라처럼 실험 목적별로 묶는다. 모델·리비전·차원·청크 정책·코퍼스 해시·질의 버전과 문서/질의/목록 역할을 함께 기록한다. 공유 코퍼스는 여러 실험에서 참조할 수 있다.
- 관리 목록에는 물리 이름, 의미를 드러내는 별칭, 실험 그룹, 역할, 관련 결과 경로를 남긴다. 조회하지 못한 값은 추측하지 않는다.

## 정리와 재사용

- 현재 사용자 방침은 용량이 괜찮은 실험 DB와 벡터를 보존하는 것이다. 일반적인 정리 요청을 컬렉션 삭제나 재임베딩 요청으로 해석하지 않는다.
- 분류만 필요하면 별칭과 관리 목록을 우선 사용한다. 별칭은 물리 컬렉션을 숨기거나 이름을 바꾸지 않으며 저장 데이터를 복제하지 않는다. Qdrant UI에 물리 이름이 남는다는 사실도 설명한다.
- 별칭 생성 전 기존 대상을 비교한다. 같은 매핑은 건너뛰고, 다른 대상으로 연결된 별칭이 있으면 충돌을 보고한다. 정리 과정에서 기존 별칭을 임의로 재지정하지 않는다.
- 고정된 결과의 물리 컬렉션 참조와 해시를 보존한다. 새 별칭 도입 때문에 기존 평가를 다시 실행하지 않는다.
- 벡터 재사용은 차원뿐 아니라 모델 리비전, 입력 형식, 정규화, 런타임 등 기존 캐시 검증 계약이 일치할 때만 한다. 같은 기반 모델의 파인튜닝이라는 이유로 벡터를 섞지 않는다.
- 삭제나 재색인은 해당 작업이 사용자 범위에 포함될 때만 수행한다. 실행 전 대상과 영향, 복구 자료를 확인하고 성공을 검증하지 못하면 후속 파괴 작업을 중단한다.

## 검증과 보고

별칭 작업에는 Qdrant의 `GET /collections`, `GET /aliases`, `POST /collections/aliases`, `POST /collections/{name}/points/count` 계약을 확인한다. 실제 요청 형식은 사용 중인 서버 버전의 공식 문서를 따른다.

정리 전후 물리 컬렉션 집합, 정확한 포인트 수, 벡터 스키마가 같은지 비교한다. 생성한 별칭의 대상과 별칭을 통한 조회도 확인한다. 관리되지 않는 컬렉션은 목록에 표시하되 수정하지 않는다. API 실패나 충돌이 있으면 성공으로 보고하지 않는다.

새 관리 명령은 가능하면 기본 조회와 명시적인 변경 모드를 나눈다. 실측 결과와 실행하지 않은 검증을 구분하고, 남은 용량 및 보존·삭제·생성한 대상을 간결하게 보고한다. 실험 결과 비교 기준을 관리 작업 때문에 바꾸지 않는다.
