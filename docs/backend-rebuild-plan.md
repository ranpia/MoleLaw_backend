# 백엔드 재구성 계획

## 1. 목표와 범위
- 작업 브랜치: `refactor/backend-rebuild`.
- 국가법령정보센터 API의 법령 검색·상세 조회 방식과 수집 동작은 유지한다.
- RAG는 데이터 준비부터 검색, 근거 구성, 답변 생성까지 재설계한다.
- Spring AI `ChatClient`로 모델 호출을 통합하고 예시 한 개를 넣는 one-shot prompting과 step-back 검색을 검증한다.
- 첫 답변 이후 세션별 메시지 리스트를 저장하고 대화 맥락을 유지하며 후속 상담을 제공한다.
- 법령·판례 조회는 상담방의 최초 질문 처리에서만 수행한다. 후속 질문은 최초에 저장한 근거와 대화 내역으로 답변한다.
- 중복 호출 코드, 과도한 서비스 책임, 불필요한 DTO·메서드와 로그를 정리한다.
- 서버와 DB는 로컬에서 실행한다. 법령 API와 모델 API는 우선 외부 서비스를 사용한다. 로컬 LLM 도입은 별도 범위다.
- 기존 사용자·채팅 기능과 API 계약은 우선 유지한다. 변경이 필요하면 차이를 문서화한다.

## 2. 현재 구조에서 확인한 문제
| 영역 | 현재 상태 | 개선 방향 |
| --- | --- | --- |
| 모델 호출 | `FinalAnswer`, `GptService`, `EmbeddingService` 등에 HTTP 요청·파싱 코드 분산 | `ChatClient`와 `EmbeddingModel` 기반 호출 통합 |
| 후속 상담 | 최초 BOT 답변과 최신 질문만 전달 | 세션별 사용자·답변 메시지 리스트로 대화 맥락 전달 |
| 검색 | `LawSimilarityService`가 전체 임베딩을 읽어 직접 코사인 유사도 계산 | 벡터 저장소에서 검색하고 점수·메타데이터 반환 |
| 검색 실패 | 요청 중 수집·임베딩 수행, 빈 결과 처리 후 `chunks.get(0)` 접근 가능 | 수집과 검색 분리, 빈 결과를 명시적인 상태로 처리 |
| 검색 재시도 | 낮은 점수에서 수집·임베딩·재검색을 수행하고 질문 임베딩을 중복 생성 | 동일 질의 임베딩 재사용, 제한된 질의 변환·후보 확장 후 종료 |
| 판례 | 조문별 법령명을 `JO`로 조회하고 목록 정보만 전달, 관련성 검증·중복 제거 없음 | 쟁점 기반 검색, 상세 내용 확보, 관련성 검증 후 근거로 채택 |
| 임베딩 | 모델명과 존재 여부 중심으로 중복 판단 | 본문 해시·모델·차원·색인 버전 기준으로 갱신 |
| 실행 환경 | 기본 설정이 원격 MySQL을 가리킴 | 명시적인 local/test 프로필과 환경변수 구성 |
| 검증 | 컨텍스트 로딩 테스트 중심 | 검색 품질 평가와 핵심 동작 회귀 테스트 추가 |

## 3. 목표 구조
### 법령 수집과 색인
`기존 법령 API 연동 → 원문/수집 결과 → 정규화 → 청킹 → 임베딩 → 벡터 색인`

API 요청 파라미터, 검색 순서, 응답 해석은 먼저 회귀 테스트로 고정한다. 기존 수집 결과를 받는 어댑터를 두고 RAG용 청킹을 별도 단계로 구성한다. 기존 파서가 항·호·목이나 개정 정보를 누락하는지는 점검하되, 수정은 별도 항목으로 다룬다. 기존 수집 로직 보존과 검색 문서 구성 변경을 구분한다.

### 질문 처리
최초 질문: `소유권·조회 상태 확인 → 법령 검색 → 부족하면 제한된 대체 검색 → 판례 검색·검증 → 근거 저장 → 답변 1회 생성 → 출처 검증 → 대화 저장/응답`

후속 질문: `소유권 확인 → 저장된 근거·대화 조회 → 답변 1회 생성 → 출처 검증 → 대화 저장/응답`

질문 처리 중 법령 수집이나 문서 재임베딩·재색인을 수행하지 않는다. 자료가 부족하면 근거 부족을 응답하고, 필요한 수집은 별도 작업 대상으로 기록한다. 후속 질문에서는 법령·판례 추가 조회와 검색용 질의 변환을 수행하지 않는다. 새로운 쟁점이나 기존 근거의 범위를 벗어난 질문에는 한계를 설명하고 새 상담방에서 질문하도록 안내한다.

## 4. 로컬 환경 구성
- 애플리케이션은 IDE 또는 Gradle `bootRun`으로 실행하고 DB는 Docker Compose로 관리한다.
- 업무 데이터는 기존 MySQL을 유지하고 벡터 전용 DB를 분리한다. 로컬 구성안은 MySQL + Qdrant이며, Qdrant는 우선 도입 후보로 소규모 색인·검색을 검증한다.
- MySQL은 사용자·상담방·채팅 기록, 법령 원문·수집 상태, 상담방별 최초 조회 상태와 근거 스냅샷을 관리한다. Qdrant는 검색용 청크·임베딩·메타데이터를 관리한다.
- MySQL 원문을 기준 데이터로 삼고 Qdrant 색인은 재생성 가능하게 구성한다. 안정적인 청크 ID로 갱신·삭제하며, 두 DB 간 단일 트랜잭션 대신 색인 상태·실패 기록·재시도로 일관성을 관리한다.
- 두 DB는 Docker Compose로 실행하고 데이터를 볼륨에 보존한다. 이미지 버전은 고정하고 로컬 접근 주소·포트를 실행 문서에 명시한다.
- `application-local.yml`, `application-test.yml`, `.env.example`, `compose.yml`과 실행 문서를 준비한다. 예제에는 비밀값을 넣지 않는다.
- DB 계정, JWT 비밀값, 모델명, 임베딩 모델·차원, 검색 옵션을 설정으로 분리한다. 로컬 CORS와 쿠키 설정을 맞춘다.
- 스키마 변경은 Flyway 등 명시적인 마이그레이션으로 관리한다. 기존 데이터 초기화는 별도 작업으로 분리한다.
- 기존 컨텍스트 테스트가 원격 DB에 연결되지 않도록 테스트 설정과 외부 호출을 격리한다.
- 예상 실행 흐름: `docker compose up -d` → 로컬 프로필로 서버 실행 → 수집/색인 작업 → API 확인. 실제 명령은 구성 완료 후 확정한다.
- DB 인프라 초안은 `docker/compose.yml`과 `docker/.env.compose.example`로 구성한다. `docker` 폴더에서 실제 DB 실행 명령은 `docker compose --env-file .env.compose up -d`이며 자원 예산·LAN 연결·검증 범위는 [로컬 인프라 가이드](../docker/README.md)를 따른다. `mysql`·`qdrant`·`local`·`test` 프로필과 저장소 빈 구성은 추가했으며, 마이그레이션과 실제 Qdrant 색인·검색 경로 전환은 남은 작업이다.

## 5. RAG 재설계
### 문서와 청크
- 법령명, 법령ID/MST, 조·항·호·목 경로, 원문 링크, 수집 시각을 보존한다. 시행일·개정 정보는 수집 가능 여부부터 확인한다.
- 조문을 기본 단위로 삼고 긴 조문만 항·호 단위로 분할한다. 작은 하위 청크에는 상위 조문 제목과 필요한 맥락을 포함한다.
- 검색용 본문과 표시용 원문을 구분한다. 안정적인 문서 ID와 내용 해시로 중복 저장을 방지한다.
- 본문 변경·삭제 및 모델 변경 시 재색인 정책을 정의한다. 실패 작업은 기록하고 재실행 가능하게 만든다.
- 초기 색인은 선정한 소규모 법령 묶음으로 검증한 뒤 확대한다.

### 검색과 근거 구성
- 첫 버전은 벡터 검색, 메타데이터 필터, 중복 제거, 조문 맥락 확장으로 구성한다.
- 법령명·조문번호의 정확한 질의가 약하면 키워드 검색을 추가해 하이브리드 검색을 비교한다. 한국어 검색 지원과 별도 인프라 필요성도 평가한다.
- `topK`, 점수 기준, 컨텍스트 토큰 상한은 평가 결과로 조정한다. 기존 `0.5` 기준을 그대로 복사하지 않는다.
- 빈 색인, 관련 없는 질문, 오래된 문서, 임베딩 차원 불일치를 명시적으로 처리한다.

### 낮은 유사도에서의 대체 검색
- 최초 질문 처리 안에서 법령 검색은 최대 2라운드로 제한한다. 처음에는 전체 색인을 검색하고, 근거가 부족하면 법률 쟁점으로 질의를 변환해 다른 법령 후보까지 탐색한다.
- 질의 변환은 최대 1회이며 step-back은 이 단계의 비교 전략으로 검증한다. 동일 질의의 임베딩은 요청 내에서 재사용하고 동일 질의·필터 조합은 반복하지 않는다.
- 다른 법령 후보를 확장하되 기존 법령을 무조건 제외하지 않는다. 같은 법령의 다른 조문이나 복수 법령이 필요할 수 있으므로 두 라운드 결과를 병합·중복 제거한다.
- 유사도는 답변 정확도나 근거 충분성과 동일하지 않다. 최고 점수뿐 아니라 질문의 주요 쟁점을 뒷받침하는 조문이 있는지 평가하고, 구체적인 판정 기준은 평가셋으로 검증한다.
- 근거 확보, 새로운 질의·후보 없음, 검색 횟수 또는 전체 시간 예산 소진 시 종료한다. 임계값을 계속 낮추거나 문서를 반복 임베딩하며 조건 충족을 기다리지 않는다.
- 빈 색인·미수집 자료와 낮은 관련성을 구분한다. 재검색 후에도 부족하면 추가 사실관계를 묻거나 답변 범위를 제한한다. 후속 답변에도 최초 근거만 사용한다.

### 판례 검색과 근거 검증
- 판례는 법령과 출처 유형을 분리하며 상담방 최초 질문에서만 조회한다. 판례를 찾지 못해도 확보한 법령 근거로 답변할 수 있다.
- 질문의 쟁점으로 `query`를 구성하고 `search=2`로 본문을 검색한다. `JO`는 참조법령명 필터로 사용하며 법령명만으로 관련 판례라고 판단하지 않는다.
- 검색 결과가 없으면 법령 필터를 완화하거나 대체 검색어를 사용하고, 무관한 후보만 있으면 쟁점을 구체화한다. 목록 검색은 최초 요청 포함 최대 2회로 제한한다.
- 조문별 동일 법령 요청을 제거하고 판례 ID로 후보를 중복 제거한다. 초기 상세 조회 상한은 3건, 최종 채택은 0~2건으로 제안하며 평가 후 조정한다.
- 상세 API에서 판시사항·판결요지·참조조문·판례내용을 확보하고 질문의 쟁점 및 사실관계와의 관련성을 검증한다. 구체적인 검증 방식과 합격 기준은 평가셋으로 정한다.
- 제목·사건번호만 확보하거나 상세 내용을 확보하지 못한 판례는 판결 내용의 근거로 사용하지 않는다. 관련성 검증을 통과한 내용과 출처만 답변 모델에 전달한다.
- 결과 없음, 관련성 검증 탈락, 상세 조회 실패, API 오류·시간 초과를 구분한다. 검색 실패가 법령 답변을 막지 않도록 하고, 결과가 없을 때는 '관련 판례를 찾지 못했다'고 표현하며 존재하지 않는다고 단정하지 않는다.
- 목록·상세 조회에 시간 예산과 호출 상한을 적용한다. 판례 본문을 Qdrant에 사전 색인하는 작업은 후속 범위로 검토한다.

### 상담방별 최초 조회 상태와 근거 보존
- 조회 상태는 상담방 ID 기준으로 `미시작 → 진행 중 → 완료 / 실패`를 관리한다. HTTP 세션이 바뀌거나 서버가 재시작되어도 완료된 상담방을 다시 조회하지 않도록 DB에 보존한다.
- 동시 최초 요청 중 하나만 조회를 시작하도록 상태 전이를 원자적으로 처리한다. 네트워크 호출 동안 DB 트랜잭션을 유지하지 않으며, 중단된 진행 상태의 복구 정책을 정의한다.
- 정상 검색의 빈 결과·관련성 탈락도 완료 상태로 기록한다. 판례만 실패하고 법령 근거를 확보한 경우 판례 실패 상태를 별도 기록하고 최초 조회는 완료한다.
- 최초 검색 자체를 수행하지 못한 실패만 제한적으로 재시도하는 안을 검토한다. 재시도 가능 오류·상한은 구현 전에 확정하며, 답변 생성 실패는 저장된 근거로 재시도해 검색을 반복하지 않는다.
- 최초 사용한 조문 원문, 검증된 판례 내용, 근거 ID, 출처 링크, 조회 시점을 상담방별 스냅샷으로 저장한다. 색인 변경과 별개로 후속 답변의 근거를 보존한다.

## 6. ChatClient와 답변 전략
**one-shot은 프롬프트에 질문·근거·모범 답변 예시를 한 개 넣는 기법**이다. 각 사용자 질문의 최종 답변은 한 번 생성하고 이후 세션의 대화 내역을 사용해 상담을 이어간다. 임베딩·질의 변환·step-back을 위한 호출은 최종 답변 생성과 별도로 집계한다.

one-shot은 답변 프롬프트 구성이고 step-back은 검색 질의 구성 기법이므로 함께 사용할 수 있다. 예시는 답변 형식, 제공된 근거의 인용, 근거 부족 처리 방식을 보여주되 현재 질문의 사실관계나 실제 검색 근거로 취급하지 않는다.

| 전략 | 처리 흐름 | 검증할 항목 |
| --- | --- | --- |
| zero-shot RAG 기준선 | 최초 질문 검색 → 근거 + 질문 → 예시 없이 답변 | 비교 기준, 응답시간, 비용 |
| one-shot RAG | 동일한 검색 → 예시 1개 + 근거 + 대화 + 질문 → 답변 | 형식 일관성, 근거 인용, 예시로 인한 사실 혼입 |
| one-shot + step-back RAG | 최초 검색의 근거 부족 시 쟁점으로 추상화 → 2차 검색 → 근거 병합 → 예시 1개와 질문을 반영한 답변 | 검색 누락 감소, 무관한 근거 증가, 추가 비용 |

- 예시 사용 여부와 검색 질의 전략을 독립적인 옵션으로 둔다. step-back은 기존 사실관계와 질문을 대체하지 않는다.
- 검색 전략 비교는 상담방 최초 질문에 적용한다. 모든 전략의 후속 답변은 저장된 최초 근거·대화·현재 질문을 사용하며 추가 검색하지 않는다.
- 프롬프트는 리소스 파일로 분리하고 공통 지시, 질문, 검색 문서를 구분한다.
- 답변은 본문, 근거 ID, 근거 부족 여부를 구조화된 결과로 받는다. 출처 링크와 조문 표시는 서버가 검증한 메타데이터로 구성한다.
- 모델이 반환한 근거 ID가 상담방에 저장한 검증된 근거에 속하는지 확인한다. 근거 부족 시 추가 질문 또는 답변 범위 제한을 허용한다.
- 모델 호출의 타임아웃, 제한적인 재시도, 사용량과 지연시간 기록을 공통화한다.
- Java 17 / Boot 3.5와 호환되는 Spring AI 버전 및 BOM을 확인하고 고정한다. 최신 버전 도입을 위해 프레임워크 전체를 먼저 업그레이드하지 않는다.

### 세션별 대화 내역과 후속 상담
- 첫 버전은 서버 메모리에 세션별 `List<Message>`를 저장한다. 브라우저 세션 안에서 상담방 ID별 리스트를 분리해 서로 다른 상담의 맥락이 섞이지 않게 한다. 여기서 `Message`는 Spring AI 메시지 타입이며 기존 JPA `Message` 엔티티와 구분한다.
- 리스트에는 역할을 구분한 사용자 질문과 최종 assistant 답변을 순서대로 저장한다. one-shot 예시, 검색 원문, step-back 중간 결과는 실제 대화 내역에 추가하지 않는다. 출처는 답변의 별도 메타데이터로 관리한다.
- 첫 질문은 빈 리스트로 시작하고, 후속 질문은 저장된 최초 근거·대화와 현재 질문을 전달한다. 이전 assistant 답변을 법령·판례 원문 근거로 취급하지 않는다.
- 전체 대화 저장 리스트와 모델에 보낼 메시지 범위를 구분한다. 최근 완결된 턴과 최초 상담의 주요 사실을 토큰 예산 안에서 전달하고, 길어진 대화의 요약은 후속 개선으로 둔다. 세션 저장량도 상한을 둔다.
- 성공한 질문·답변 쌍은 함께 추가한다. 실패 시 정상 답변을 저장하지 않고 재시도 중복과 동일 상담의 동시 요청 순서가 꼬이지 않도록 처리한다.
- 세션 만료·로그아웃·상담방 삭제 시 메모리를 정리한다. 첫 버전의 세션 리스트는 서버 재시작 시 소실되지만 DB 채팅 기록과 최초 조회 상태·근거는 보존한다. 상담방 삭제 시 해당 근거도 정리한다. 세션 만료 후 대화 복원은 후속 범위로 두며, 기존 상담방의 근거는 DB에서 불러오고 추가 검색하지 않는다.
- 현재 인증은 JWT 기반이므로 대화 저장용 HTTP 세션과 로그인 인증을 구분한다. 기존 `STATELESS` 설정과 `HttpSession` 사용의 호환성, 세션 쿠키 전달, 로컬 CORS를 검증한다. 상담방 소유권은 매 요청 확인한다.
- 최초 구현은 리스트를 직접 조회해 `ChatClient`에 전달하는 방식으로 단순하게 시작한다. `ChatMemory`/Advisor를 도입할 경우 같은 메시지가 이중 저장·전달되지 않도록 메모리 관리 주체를 하나로 정한다.

## 7. 코드 정리 원칙
- `FinalAnswer`의 검색·프롬프트·호출·마크다운 책임을 분리하고 `GptService`와 겹치는 답변 호출을 합친다.
- 외부 API 클라이언트, 수집 작업, 색인 작업, 검색, 답변 생성, 채팅 저장의 경계를 명확히 한다.
- `ObjectMapper`·HTTP 클라이언트의 직접 생성, 중복 예외 처리, 미사용 import·메서드·DTO를 정리한다.
- `System.out`, `printStackTrace`, 외부 응답 원문 로그를 구조화된 로그로 교체한다. 키·토큰·민감한 질문 본문을 남기지 않는다.
- 외부 API 응답의 세부 오류를 사용자에게 그대로 노출하지 않는다.
- DB 트랜잭션 안에서 장시간 외부 호출하지 않도록 하고 임베딩 작업의 동시성·재시도·진행 상태를 관리한다.
- 패키지명 변경과 전면 DTO 재작성은 동작 개선과 분리한다. 실제 책임이 없는 인터페이스나 계층은 추가하지 않는다.

## 8. 실행 순서와 완료 조건
| 단계 | 작업 | 완료 조건 |
| --- | --- | --- |
| 1. 기준선 확보 | API 계약, 수집 응답 샘플, 평가 질문 정리 | 기존 수집 동작과 주요 응답 형식을 검증 가능 |
| 2. 로컬 실행 | DB/벡터 저장소, 프로필, 환경변수, 마이그레이션 | 원격 DB 없이 서버와 테스트 실행 가능 |
| 3. 호출·세션 통합 | Spring AI 연결, 예시 프롬프트, 세션별 메시지 리스트, 공통 오류 처리 | 첫 질문과 후속 상담의 맥락 유지·세션 분리 확인 |
| 4. 색인 재구축 | 문서 모델, 청킹, 임베딩 갱신과 재실행 | 동일 자료 재실행 시 중복 없음, 변경 자료만 갱신 |
| 5. 기본 RAG | 최초 검색·대체 검색, 판례 검증, 근거 저장, one-shot 답변, 후속 질문 처리 | 검색 상한 준수, 유효한 출처, 빈 결과 정상 처리, 후속 조회 없음 |
| 6. 전략 비교 | zero-shot/one-shot 비교 후 step-back과 필요 시 하이브리드 검색 실험 | 같은 평가 질문으로 품질·시간·비용 비교표 작성 |
| 7. 정리와 문서화 | 구 코드 제거, 실행 가이드·AGENTS 갱신 | 로컬 수집 → 색인 → 질문 → 출처 확인 흐름 재현 |

## 9. 검증 기준
- 평가 질문 30~50개를 준비한다: 법령명/조문 지정, 일상 표현, 복합 쟁점, 후속 질문, 자료 부족 사례를 포함한다.
- 각 질문에 기대 법령·조문과 판단 기준을 기록한다. 학습용 예시와 평가 질문을 구분한다.
- 검색은 Recall@K와 무관한 문서 비율, 답변은 인용 정확도·근거 일치·근거 부족 처리, 운영은 지연시간·호출 수·토큰 사용량으로 비교한다.
- 기존 방식, 새 zero-shot, one-shot, one-shot + step-back을 같은 문서 집합과 모델 설정에서 비교한다. 예시 효과와 검색 질의 변환 효과를 구분한다.
- 다중 턴 상담에서 사실관계 추가·정정, 지시어 해석, 주제 변경을 검증한다. 사용자/상담방 간 분리, 세션 만료, 저장량 상한, 동시 요청, 실패 후 재시도를 테스트한다.
- 후속 질문·세션 변경·서버 재시작 후에도 완료된 상담방의 법령·판례 조회가 재실행되지 않는지 검증한다. 새 쟁점은 기존 근거의 한계를 안내하는지 확인한다.
- 낮은 유사도에서 검색 라운드·질의 변환·시간 상한, 반복 후보 차단, 동일 질의 임베딩 재사용, 문서 수집·재임베딩 호출 없음, 근거 부족 종료를 검증한다.
- 판례의 무관한 결과·빈 결과·본문 미확보·API 실패·중복 후보를 검증한다. 최초 동시 요청의 단일 조회, 중단 상태 복구, 답변 실패 후 저장된 근거 재사용도 확인한다.
- 청킹·중복 방지·갱신·빈 검색·타임아웃·출처 검증은 자동 테스트로 확인한다. DB/벡터 통합 테스트와 실제 모델 평가를 분리한다.
- 품질 합격 기준은 평가셋과 기준선을 확보한 뒤 수치로 정한다. step-back은 개선 효과가 확인된 경우 기본 또는 선택 전략으로 채택한다.

## 10. 구현 전에 확정할 선택
1. MySQL + 벡터 전용 DB 분리 방향에서 Qdrant 도입 검증 및 이미지·클라이언트 버전, 임베딩 모델·차원 확정.
2. 초기 수집할 법령 분야와 데이터 범위.
3. 사용할 답변 모델과 실험 호출 예산.
4. 세션 만료 시간, 저장량·모델 입력 상한, 만료 후 DB 기록 복원 필요 여부. 첫 버전은 메모리 리스트로 시작한다.
5. 법령 검색 최대 2라운드·질의 변환 최대 1회 정책의 평가 기준과 전체 시간 예산, 근거 충분성 판정 방식.
6. 판례 목록 검색 최대 2회 정책의 시간 예산, 상세 조회·채택 건수 제안의 확정, 관련성 검증 방식.
7. 최초 조회 실패의 재시도 가능 오류·상한, 진행 상태 복구, 근거 스냅샷 저장량·모델 입력 범위.

- [ ] 세션 만료·로그아웃·상담방 삭제 시 대화 메모리와 근거 정리, 메시지 정렬의 안정성, 목록 조회의 N+1, 지연 로딩과 트랜잭션 경계를 점검한다. 외부 API 호출 동안 DB 트랜잭션을 유지하지 않는 방향으로 책임을 분리한다.
- [ ] 채팅 본문과 토큰·개인정보의 로그 노출 및 현재 메시지 암호화 키 관리도 점검한다.

### 다음 작업 2: JWT에 채팅방 리스트 객체를 담는 방안 검토
- [ ] 현재 JWT subject·claim, Access/Refresh 구분, 인증 필터, 발급·재발급·로그아웃 경로를 먼저 확인한다. Access 만료식은 현재 `1000 * 60 * 15 * 60`으로 15시간이므로 의도한 정책과 일치하는지 점검한다.
- [ ] 리스트를 담으려는 목적이 초기 목록 표시, DB 조회 감소, 상담 상태 전달, 접근 권한 확인 중 무엇인지 구분하고 필요한 필드를 정의한다. 전체 `ChatRoom` JPA 객체를 직접 직렬화하는 대신 전용 DTO나 ID 목록으로 최소화하는 안도 비교한다.
- [ ] 채팅방 목록 객체 포함, 최소 ID·목록 버전 claim 포함, 기존 `GET /api/chat-rooms` 조회 유지 방안을 비교한다. 검토 결과가 나오기 전에는 토큰 claim에 목록을 추가하지 않는다.
- [ ] 상담방 수별 토큰 크기를 측정하고 쿠키·HTTP 헤더 전달 한계와 요청마다 반복 전송되는 비용을 확인한다. 메시지·법령/판례 원문·대화 메모리를 담을 필요가 있는지와 정보 노출 범위를 검토한다.
- [ ] 현재 서명 JWT의 payload 열람 가능성을 고려해 제목·상담 내용 등 민감한 필드 포함 여부를 점검한다. JPA 연관 객체 직렬화·순환 참조·불필요한 사용자 정보 포함 문제도 확인한다.
- [ ] 상담방 생성·삭제·제목 변경 이후 claim 목록의 최신성, Access/Refresh 재발급 시 갱신 비용, 오래된 토큰·삭제된 상담방의 처리 정책을 정의한다. claim에 담긴 목록만으로 현재 상담방 소유권을 판단하지 않고 서버 권한 검사와의 관계를 검증한다.
- [ ] 비교 결과와 선택 이유, 필요한 API·프론트 변경, 인증 회귀 테스트를 문서화한 뒤 채택 여부를 결정한다.

### 현재 검증 상태
- Docker를 중지한 상태에서 `gradlew.bat test`로 전체 테스트 20개 통과. 프로필 구성·H2 컨텍스트·ChatClient 메시지 역할과 오류·구조화 응답·임베딩 차원 및 기존 법령 수집 기준선을 검증했다.
- `gradlew.bat build`로 실행 가능한 JAR 패키징까지 통과했다. 실제 MySQL·Qdrant·모델 API 연결과 위 채팅방·JWT 검토 항목은 아직 완료하지 않았다.
