# 백엔드 재구성 계획

최신화: 2026-10-07. 계획과 구현 상태를 구분하며 아래 결정 사항을 기준으로 후속 작업을 진행한다.

## 1. 목표와 범위
- 작업 브랜치: `refactor/backend-rebuild`.
- 국가법령정보센터 API의 기존 검색 순서·MST 상세 조회·응답 해석을 기준선으로 보존하고 페이지 탐색·수집 범위를 확장한다.
- RAG는 데이터 준비부터 검색, 근거 구성, 답변 생성까지 재설계한다.
- 저장소는 MySQL + Qdrant로 확정한다. Spring AI ETL 구성부터 시작해 Qdrant 색인·검색을 검증한 뒤 상담 RAG에 연결한다. PostgreSQL/pgvector 도입은 이번 범위에 포함하지 않는다.
- 인증 저장소는 Access 활성·폐기 상태용 Redis와 Refresh 관리용 MySQL 별도 테이블로 구성한다. 토큰 원문 대신 Access 식별자와 Refresh 해시를 관리한다.
- Spring AI `ChatClient`로 모델 호출을 통합하고 예시 한 개를 넣는 one-shot prompting과 step-back 검색을 검증한다.
- MessageChatMemoryAdvisor와 ChatMemory로 MySQL 채팅방 기록을 전달하고 대화 맥락을 유지하며 후속 상담을 제공한다.
- 법령·판례 조회는 상담방의 최초 질문 처리에서만 수행한다. 후속 질문은 최초에 저장한 근거와 대화 내역으로 답변한다.
- 중복 호출 코드, 과도한 서비스 책임, 불필요한 DTO·메서드와 로그를 정리한다.
- 서버와 DB는 로컬에서 실행한다. 법령 API와 모델 API는 우선 외부 서비스를 사용한다. 로컬 LLM 도입은 별도 범위다.
- 기존 사용자·채팅 기능과 API 계약은 우선 유지한다. 변경이 필요하면 차이를 문서화한다.

### 최신 결정과 변경 요약
이 문서는 목표 설계다. 아래 변경 사항은 코드에 적용된 것으로 간주하지 않으며, 구현 상태는 11절에서 별도로 관리한다.

| 영역 | 현재 구현 | 재구축 후 동작 |
| --- | --- | --- |
| 저장소 | MySQL + Qdrant 빈·Compose 구성 | MySQL(업무·원문·Refresh) + Qdrant(벡터 검색) + Redis(Access 인증 상태) |
| 법령 수집 | 첫 페이지 중심, 부족할 때 기존 fallback 실행 | 최초 질문에서 다음 페이지·다른 후보를 수집하고 ETL·색인·재검색 결과를 같은 답변에 반영 |
| 검색 | MySQL 임베딩 전체 조회·코사인 직접 계산 | Qdrant 검색으로 점수·메타데이터 반환, 중복 제거·조문 맥락 확장 |
| ETL | 기존 수집·청크 저장·임베딩 서비스 결합 | Spring AI Reader → Transformer → Qdrant writer, 변경 감지·배치·실패 복구 |
| 최초 질문 | 검색·답변과 부분 저장이 섞임 | 상담방 처리 상태·중복 요청 제어 → 근거 스냅샷 확정 → 답변 검증 → 성공 턴 저장 |
| 후속 질문 | 최초 BOT 답변 + 현재 질문 | MessageChatMemoryAdvisor의 채팅방 기록 + 최초 원문 근거 + 현재 질문, 추가 수집·검색 없음 |
| 대화 복원 | 전체 DB 기록을 모델에 전달하지 않음 | MySQL 기록 기반 Advisor 메모리, 재로그인·재시작 후 복원 |
| Access | 15시간 JWT, 서버 등록·폐기 확인 없음 | 짧은 수명 JWT + Redis jti·세션 활성 상태 확인, 로그아웃·침해 시 차단 |
| Refresh | 서버 저장·회전 없음, JSON과 쿠키에 전달 | MySQL 별도 테이블에 해시·회전·폐기 이력, 브라우저는 HttpOnly 쿠키 |
| 인증 요청 보호 | 토큰 원문 로그, 용도 혼용, 광범위 CORS·CSRF 비활성화 | 로그 제거·용도 분리·Origin 허용 목록·쿠키 요청 CSRF 보호 |

- 확정: MySQL + Qdrant + 인증용 Redis, 최초 질문의 수집 허용, Advisor 기반 기록 전달, Refresh 별도 테이블 관리.
- 최초 질문의 법령 수집·재검색에는 고정 2라운드·질의 변환 1회 제한을 적용하지 않는다. 근거 확보·탐색 소진·설정한 실행 예산으로 종료한다.
- 수동 HTTP 세션 메시지 리스트와 질문 중 수집 금지 방식은 채택하지 않는다. Advisor 메모리와 로그인 세션 상태는 서로 다른 책임이다.
- 초기 제안: Access 15분, Refresh 7일·회전, 판례 상세 조회 3건·최종 채택 0~2건. 수치와 Refresh 표현 형식은 구현 전 확정한다.
- 후속 검토: JWT에 채팅방 목록을 넣는 방안. 결정 전에는 기존 GET /api/chat-rooms를 유지하고 claim을 추가하지 않는다.

### API와 프론트엔드에 영향을 주는 변경
- 채팅방·메시지 API 경로와 USER/BOT/INFO 응답 형태는 우선 유지한다. 최초 수집이 오래 걸릴 때의 동기 응답 예산·비동기 상태 조회 필요 여부는 구현 전에 정하고 변경 시 계약을 문서화한다.
- 로그인·재발급 응답에서 Refresh 원문을 제거한다. /api/auth/reissue는 만료된 Access 없이 정상 Refresh로 처리하며 회전된 Refresh는 쿠키로 갱신한다.
- JWT subject·claim과 Access 만료가 바뀌므로 사용자 조회·OAuth·프론트 재발급 처리와 관련 테스트를 함께 수정한다. Redis 사용으로 인증은 서버 상태 확인을 포함하지만 Spring Security HTTP 세션 정책은 STATELESS를 유지할 수 있다.
- 쿠키 Secure·SameSite·Path·수명을 공통화하고 CSRF 토큰 전달·허용 Origin을 프론트와 맞춘다. Access의 쿠키 또는 메모리+Authorization 전달 방식은 아직 확정하지 않았다.
- 로그아웃은 쿠키 삭제와 서버 토큰 폐기를 수행하되 상담 기록·근거를 삭제하지 않는다. 상담방 삭제는 해당 기록·메모리·근거를 정리한다.

## 3. 목표 구조
### 법령 수집과 색인
`기존 법령 API 연동 → MySQL 원문/수집 결과 → DocumentReader → DocumentTransformer → QdrantVectorStore(임베딩·색인)`

API 요청 파라미터, 검색 순서, 응답 해석은 먼저 회귀 테스트로 고정한다. 기존 수집 결과를 받는 어댑터를 두고 RAG용 청킹을 별도 단계로 구성한다. 기존 파서가 항·호·목이나 개정 정보를 누락하는지는 점검하되, 수정은 별도 항목으로 다룬다. 기존 수집 로직 보존과 검색 문서 구성 변경을 구분한다.

### 질문 처리
최초 질문: `소유권·조회 상태 확인 → 기존 색인 검색 → 필요하면 법령 수집(다음 페이지·다른 후보) → ETL·색인 → 재검색 → 판례 검색·검증 → 근거 저장 → 답변 1회 생성 → 출처 검증 → 대화 저장/응답`

후속 질문: `소유권 확인 → 저장된 근거·대화 조회 → 답변 1회 생성 → 출처 검증 → 대화 저장/응답`

| 쿠키·인증 계약 | 공통 설정, 브라우저 쿠키와 API 응답 | CookieUtil·UserController·AuthResponse·SecurityConfig |

이 표의 새로운 서비스·테이블 이름은 역할 정의이며 최종 클래스명은 구현 시 정한다. 기존 JPA Message와 Spring AI Message를 구분하고, 로그인 sessionId와 상담방 conversationId를 혼용하지 않는다.

최초 질문에서는 필요한 법령 수집·청킹·임베딩·색인·재검색을 허용한다. 빈 색인이나 부족한 근거를 확인하면 같은 검색 조건의 다음 페이지와 다른 법령 후보를 탐색하고, 확보한 자료를 같은 질문의 답변 근거에 반영한다. 수집량과 검색 횟수를 고정된 2라운드로 제한하지 않으며, 종료 조건과 실행 예산은 설정으로 관리한다. 후속 질문에서는 추가 수집·색인, 법령·판례 조회와 검색용 질의 변환을 수행하지 않는다. 새로운 쟁점이나 기존 근거의 범위를 벗어난 질문에는 한계를 설명하고 새 상담방에서 질문하도록 안내한다.

## 4. 로컬 환경 구성
- 애플리케이션은 IDE 또는 Gradle `bootRun`으로 실행하고 DB는 Docker Compose로 관리한다.
- 업무 데이터는 기존 MySQL을 유지하고 벡터 전용 DB는 Qdrant로 확정한다. 소규모 법령 묶음으로 실제 색인·검색을 검증한 뒤 범위를 확대한다.
- MySQL은 사용자·상담방·채팅 기록, 법령 원문·수집 상태, 상담방별 최초 조회 상태와 근거 스냅샷을 관리한다. Qdrant는 검색용 청크·임베딩·메타데이터를 관리한다.
- 인증용 Redis를 로컬 Compose와 프로필 설정에 추가한다. Access의 jti·로그인 세션 활성 상태와 TTL을 관리하고 Refresh 해시·회전·폐기 이력은 MySQL 별도 테이블에 보존한다. Redis 장애·키 유실 시 인증을 우회하지 않으며 정상 Refresh로만 복구한다. 실제 Redis 없이 실행되는 test 프로필과 별도 Redis 통합 검증을 준비한다.
- MySQL 원문을 기준 데이터로 삼고 Qdrant 색인은 재생성 가능하게 구성한다. 안정적인 청크 ID로 갱신·삭제하며, 두 DB 간 단일 트랜잭션 대신 색인 상태·실패 기록·재시도로 일관성을 관리한다.
- MySQL·Qdrant·Redis는 Docker Compose로 실행한다. MySQL·Qdrant 데이터를 볼륨에 보존하고 Redis 영속화·복구 시 인증 상태 정책은 별도로 검증한다. 이미지 버전은 고정하고 로컬 접근 주소·포트를 실행 문서에 명시한다.
- `application-local.yml`, `application-test.yml`, `.env.example`, `compose.yml`과 실행 문서를 준비한다. 예제에는 비밀값을 넣지 않는다.
- DB 계정, JWT 비밀값, 모델명, 임베딩 모델·차원, 검색 옵션을 설정으로 분리한다. 로컬 CORS와 쿠키 설정을 맞춘다.
- 스키마 변경은 Flyway 등 명시적인 마이그레이션으로 관리한다. 기존 데이터 초기화는 별도 작업으로 분리한다.
- 기존 컨텍스트 테스트가 원격 DB에 연결되지 않도록 테스트 설정과 외부 호출을 격리한다.
- 예상 실행 흐름: `docker compose up -d` → 로컬 프로필로 서버 실행 → 수집/색인 작업 → API 확인. 실제 명령은 구성 완료 후 확정한다.
- DB 인프라 초안은 `docker/compose.yml`과 `docker/.env.compose.example`로 구성한다. `docker` 폴더에서 실제 DB 실행 명령은 `docker compose --env-file .env.compose up -d`이며 자원 예산·LAN 연결·검증 범위는 [로컬 인프라 가이드](../docker/README.md)를 따른다. `mysql`·`qdrant`·`local`·`test` 프로필과 저장소 빈 구성은 추가했으며, 마이그레이션과 실제 Qdrant 색인·검색 경로 전환은 남은 작업이다.

## 5. RAG 재설계
### Spring AI ETL 구성
ETL은 독립된 책임으로 구현하고, 사전 수집 작업과 최초 질문 처리에서 같은 파이프라인을 호출한다. 최초 질문은 필요한 수집·색인이 완료된 자료를 재검색해 답변에 반영한다. Spring AI의 `DocumentReader → DocumentTransformer → DocumentWriter` 구조를 사용하며, 최종 writer는 `QdrantVectorStore`로 구성한다. API 사용은 저장소에 고정한 Spring AI 1.0.9에서 확인하고, 최신 문서의 기능을 그대로 전제하지 않는다.

| 단계 | 구성과 책임 | 완료 조건 |
| --- | --- | --- |
| Extract | 기존 `LawSearchService`의 검색 순서·MST 상세 조회를 유지한다. 원문과 수집 결과를 MySQL에 보존하고, 저장된 법령을 읽는 전용 `DocumentReader` 어댑터로 변환한다. | 합성 fixture로 기존 수집 동작과 Document 본문·메타데이터 매핑을 검증하고, 저장된 자료는 외부 API 없이 다시 읽을 수 있음 |
| Transform | 조문 경계를 우선 보존하는 `DocumentTransformer`로 정규화·청킹한다. 긴 조문에만 항·호 분할과 필요 시 `TokenTextSplitter`를 적용한다. | 조·항·호·목과 상위 조문 맥락 유지, 빈 본문 처리, 토큰 상한 및 결정적인 청크 ID 검증 |
| Load | `QdrantVectorStore.add`를 통해 설정한 `EmbeddingModel`로 임베딩하고 Qdrant에 저장한다. 입력을 배치로 제한하고 작업 상태·실패를 MySQL에 기록한다. | 실제 Qdrant 저장·검색 성공, 재실행 중복 없음, 변경·삭제 반영 및 부분 실패 재시도 검증 |

- Document 메타데이터 계약은 `sourceType`, `lawId`, `mst`, `lawName`, `articleNumber`, `clauseNumber`, `itemPath`, `sourceUrl`, `collectedAt`, `contentHash`, `indexVersion`으로 정의한다. 시행일·개정 정보는 확보 가능한 경우 추가하며 누락 정책을 명시한다.
- 청크 ID는 법령 식별자·조문 경로·분할 순번·색인 버전으로 만든 결정적 UUID를 사용한다. 본문 해시는 변경 감지에 사용하고, 모델·차원·청킹 정책 변경은 색인 버전으로 구분한다.
- MySQL에 청크 ID 목록과 본문 해시·모델·차원·색인 버전·작업 상태를 보존한다. 변경 없는 자료는 임베딩을 건너뛰고, 변경 자료는 갱신하며 더 이상 존재하지 않는 청크는 제거한다.
- 임베딩 생성 주체는 writer로 통일한다. 기존 `LawEmbeddingService`에서 임베딩한 뒤 `VectorStore.add`로 다시 임베딩하는 이중 호출을 피하고, 기존 임베딩 테이블의 제거는 검색 전환 검증 후 별도 마이그레이션으로 진행한다.
- Qdrant 컬렉션의 이름·차원·거리 함수·메타데이터 인덱스를 명시적으로 준비한다. 현재 `initializeSchema(false)` 설정을 고려해 생성 절차와 차원 불일치 검사부터 마련한다.
- 두 DB의 분산 트랜잭션을 전제하지 않는다. 작업별 재시도와 청크 ID 기반 재실행으로 복구하며, 부분 반영된 새 색인 버전을 검색에 노출하지 않도록 활성 버전 전환 절차를 정의한다.
- 첫 실행은 법령 ID/MST 또는 선정한 법령 목록을 받는 로컬 작업으로 검증한 뒤 최초 질문의 수집 흐름에 연결한다. 서버 시작 시 자동 전체 수집·색인은 하지 않고, 외부 공개 관리 API와 스케줄링은 후속 범위로 둔다.
- 초기 ETL에는 LLM 기반 요약·키워드 보강을 넣지 않는다. 원문 보존과 기본 검색 품질을 먼저 검증한 뒤 비용과 효과를 비교한다.

### 법령 목록 페이지 탐색과 수집 범위 확장
- 현재 `LawSearchService`는 `display=20`, `sort=lasc`를 사용하고 `page`를 전달하지 않아 첫 페이지에 한정된다. 첫 페이지의 결과만으로 관련 법령 전체를 수집했다고 판단하지 않는다.
- 목록 조회의 `page`, `display`, 응답의 `totalCnt`·페이지 번호를 수집 어댑터에서 관리한다. `target=eflaw` 공식 가이드상 `page` 기본값은 1, `display` 기본값은 20·최대값은 100이다. 실제 응답을 확인해 페이지 종료 조건을 고정한다. 페이지 확장은 기존 검색 범위·부처 fallback 순서와 MST 상세 조회를 유지하면서 별도 회귀 테스트로 추가한다.
- 검색어·검색범위·부처·정렬·페이지 크기를 하나의 탐색 조건으로 기록하고, 같은 조건의 다음 페이지를 이어서 수집한다. 페이지 번호는 동일 탐색 조건 안에서만 재사용한다. 페이지 순서는 관련성 순위로 간주하지 않는다.
- 응답 총건수와 실제 처리 건수를 확인하고 마지막 페이지·빈 결과·반복 페이지·새 MST 없음에서 종료한다. 최대 페이지 수·상세 조회 건수·외부 호출 수·시간 예산을 설정해 무제한 수집을 막는다. 상한 도달은 수집 완료와 구분한다.
- 페이지 간 후보는 법령ID와 MST로 중복 제거한다. 같은 법령의 개정 버전을 무조건 합치지 않고 현행·시행일 정책을 적용한다. 이미 처리한 MST·페이지와 마지막 성공 위치를 MySQL에 보존해 실패 후 이어서 실행한다. 재개 시 목록 변경으로 인한 누락을 확인하기 위해 앞 페이지를 재확인하고 중복은 제거한다.
- 유사도가 낮거나 근거가 부족한 경우, 다른 검색어·다른 법령 후보 확장과 함께 기존 검색 조건의 미수집 다음 페이지 여부를 확인한다. 낮은 유사도만으로 미수집이라고 단정하지 않고, 수집 이력과 함께 판단한다.
- 최초 질문에서는 미수집 다음 페이지와 다른 법령 후보를 필요한 만큼 수집하고, 원문 저장 → 청킹 → 색인 → 재검색 결과를 같은 질문의 근거에 반영한다. 마지막 페이지나 새 후보 없음은 해당 탐색 조건의 종료로 처리하고 다른 조건을 검토한다. 전체 실행 예산이 소진되면 확보한 근거와 부족 상태를 저장한다. 완료된 상담방의 근거 스냅샷은 이후 추가 색인으로 교체하지 않는다.
- 다중 페이지, 마지막 페이지, 빈 페이지, 중복 MST, 반복 응답, 총건수 변경, 중간 실패·재개, 호출 상한을 fixture 기반으로 검증한다. 고정 검색 라운드 제한은 두지 않고 ETL 페이지·API 호출·시간 예산과 탐색 진행을 함께 관리한다.

### 문서와 청크
- 법령명, 법령ID/MST, 조·항·호·목 경로, 원문 링크, 수집 시각을 보존한다. 시행일·개정 정보는 수집 가능 여부부터 확인한다.
- 조문을 기본 단위로 삼고 긴 조문만 항·호 단위로 분할한다. 작은 하위 청크에는 상위 조문 제목과 필요한 맥락을 포함한다.
- 검색용 본문과 표시용 원문을 구분한다. 안정적인 문서 ID와 내용 해시로 중복 저장을 방지한다.
- 본문 변경·삭제 및 모델 변경 시 재색인 정책을 정의한다. 실패 작업은 기록하고 재실행 가능하게 만든다.
- 초기 색인은 선정한 소규모 법령 묶음으로 검증한 뒤 확대한다.

### 검색과 근거 구성
- 첫 버전은 벡터 검색, 메타데이터 필터, 중복 제거, 조문 맥락 확장으로 구성한다.
- 법령명·조문번호의 정확한 질의가 약하면 키워드 검색을 추가해 하이브리드 검색을 비교한다. 한국어 검색 지원과 별도 인프라 필요성도 평가한다.
- `topK`, 점수 기준, 컨텍스트 토큰 상한은 평가 결과로 조정한다. 기존 `0.5` 기준을 그대로 복사하지 않는다.
- 빈 색인, 관련 없는 질문, 오래된 문서, 임베딩 차원 불일치를 명시적으로 처리한다.

### 낮은 유사도에서의 대체 검색
- 최초 질문에서는 기존 색인을 먼저 검색하고, 근거가 부족하면 미수집 페이지·다른 검색어·다른 법령 후보의 수집과 ETL을 거쳐 재검색한다. 검색 라운드는 고정 2회로 제한하지 않고 근거 확보·탐색 소진·실행 예산으로 종료한다.
- 질의 변환과 step-back은 최초 질문의 후보 확장 전략으로 검증한다. 동일 질의의 임베딩은 요청 내에서 재사용하고, 같은 질의·필터·색인 상태에서 반복 검색하지 않는다. 새 자료가 색인되면 같은 질의로 재검색할 수 있다. 변환된 질의와 이미 탐색한 조건을 기록해 순환을 막는다.
- 다른 법령 후보를 확장하되 기존 법령을 무조건 제외하지 않는다. 같은 법령의 다른 조문이나 복수 법령이 필요할 수 있으므로 각 라운드 결과를 병합·중복 제거한다.
- 유사도는 답변 정확도나 근거 충분성과 동일하지 않다. 최고 점수뿐 아니라 질문의 주요 쟁점을 뒷받침하는 조문이 있는지 평가하고, 구체적인 판정 기준은 평가셋으로 검증한다.
- 근거 확보, 새로운 질의·페이지·후보 없음, 설정한 전체 시간·외부 호출·임베딩 예산 소진 시 종료한다. 변경 없는 문서는 반복 임베딩하지 않고 임계값을 계속 낮추며 조건 충족을 기다리지 않는다. 고정 횟수보다 실제 탐색 진행과 근거 충분성을 기준으로 판단한다.
- 빈 색인·미수집 자료와 낮은 관련성을 구분한다. 재검색 후에도 부족하면 추가 사실관계를 묻거나 답변 범위를 제한한다. 후속 답변에도 최초 근거만 사용한다.

### 판례 검색과 근거 검증
- 판례는 법령과 출처 유형을 분리하며 상담방 최초 질문에서만 조회한다. 판례를 찾지 못해도 확보한 법령 근거로 답변할 수 있다.
- 질문의 쟁점으로 `query`를 구성하고 `search=2`로 본문을 검색한다. `JO`는 참조법령명 필터로 사용하며 법령명만으로 관련 판례라고 판단하지 않는다.
- 검색 결과가 없으면 법령 필터를 완화하거나 대체 검색어를 사용하고, 무관한 후보만 있으면 쟁점을 구체화한다. 목록 검색은 최초 질문 안에서 필요한 페이지·검색어를 확장하고 호출·시간 예산과 후보 소진 조건으로 종료한다.
- 조문별 동일 법령 요청을 제거하고 판례 ID로 후보를 중복 제거한다. 초기 상세 조회 상한은 3건, 최종 채택은 0~2건으로 제안하며 평가 후 조정한다.
- 상세 API에서 판시사항·판결요지·참조조문·판례내용을 확보하고 질문의 쟁점 및 사실관계와의 관련성을 검증한다. 구체적인 검증 방식과 합격 기준은 평가셋으로 정한다.
- 제목·사건번호만 확보하거나 상세 내용을 확보하지 못한 판례는 판결 내용의 근거로 사용하지 않는다. 관련성 검증을 통과한 내용과 출처만 답변 모델에 전달한다.
- 결과 없음, 관련성 검증 탈락, 상세 조회 실패, API 오류·시간 초과를 구분한다. 검색 실패가 법령 답변을 막지 않도록 하고, 결과가 없을 때는 '관련 판례를 찾지 못했다'고 표현하며 존재하지 않는다고 단정하지 않는다.
- 목록·상세 조회에 시간 예산과 호출 상한을 적용한다. 판례 본문을 Qdrant에 사전 색인하는 작업은 후속 범위로 검토한다.

### 상담방별 최초 조회 상태와 근거 보존
- 조회 상태는 상담방 ID 기준으로 `미시작 → 진행 중 → 완료 / 실패`를 관리한다. HTTP 세션이 바뀌거나 서버가 재시작되어도 완료된 상담방을 다시 조회하지 않도록 DB에 보존한다.
- 동시 최초 요청 중 하나만 조회를 시작하도록 상태 전이를 원자적으로 처리한다. 네트워크 호출 동안 DB 트랜잭션을 유지하지 않으며, 중단된 진행 상태의 복구 정책을 정의한다.
- 정상 검색의 빈 결과·관련성 탈락도 완료 상태로 기록한다. 판례만 실패하고 법령 근거를 확보한 경우 판례 실패 상태를 별도 기록하고 최초 조회는 완료한다.
- 최초 검색 자체를 수행하지 못한 실패만 제한적으로 재시도하는 안을 검토한다. 재시도 가능 오류·상한은 구현 전에 확정하며, 답변 생성 실패는 저장된 근거로 재시도해 검색을 반복하지 않는다.
- 최초 사용한 조문 원문, 검증된 판례 내용, 근거 ID, 출처 링크, 조회 시점을 상담방별 스냅샷으로 저장한다. 색인 변경과 별개로 후속 답변의 근거를 보존한다.

## 6. ChatClient와 답변 전략
**one-shot은 프롬프트에 질문·근거·모범 답변 예시를 한 개 넣는 기법**이다. 각 사용자 질문의 최종 답변은 정상 흐름에서 한 번 생성하고 이후 Advisor가 전달하는 채팅방 기록으로 상담을 이어간다. 임베딩·질의 변환·step-back을 위한 호출은 최종 답변 생성과 별도로 집계한다.

one-shot은 답변 프롬프트 구성이고 step-back은 검색 질의 구성 기법이므로 함께 사용할 수 있다. 예시는 답변 형식, 제공된 근거의 인용, 근거 부족 처리 방식을 보여주되 현재 질문의 사실관계나 실제 검색 근거로 취급하지 않는다.

| 전략 | 처리 흐름 | 검증할 항목 |
| --- | --- | --- |
| zero-shot RAG 기준선 | 최초 질문 검색 → 근거 + 질문 → 예시 없이 답변 | 비교 기준, 응답시간, 비용 |
| one-shot RAG | 동일한 검색 → 예시 1개 + 근거 + 대화 + 질문 → 답변 | 형식 일관성, 근거 인용, 예시로 인한 사실 혼입 |
| one-shot + step-back RAG | 최초 검색의 근거 부족 시 쟁점으로 추상화 → 후보 수집·색인 또는 대체 검색 → 근거 병합 → 예시 1개와 질문을 반영한 답변 | 검색 누락 감소, 무관한 근거 증가, 추가 비용 |

- 예시 사용 여부와 검색 질의 전략을 독립적인 옵션으로 둔다. step-back은 기존 사실관계와 질문을 대체하지 않는다.
- 검색 전략 비교는 상담방 최초 질문에 적용한다. 모든 전략의 후속 답변은 저장된 최초 근거·대화·현재 질문을 사용하며 추가 검색하지 않는다.
- 프롬프트는 리소스 파일로 분리하고 공통 지시, 질문, 검색 문서를 구분한다.
- 답변은 본문, 근거 ID, 근거 부족 여부를 구조화된 결과로 받는다. 출처 링크와 조문 표시는 서버가 검증한 메타데이터로 구성한다.
- 모델이 반환한 근거 ID가 상담방에 저장한 검증된 근거에 속하는지 확인한다. 근거 부족 시 추가 질문 또는 답변 범위 제한을 허용한다.
- 모델 호출의 타임아웃, 제한적인 실패 재시도, 사용량과 지연시간 기록을 공통화한다. 정상 답변 생성 1회 원칙과 실패 재시도를 구분하고 모든 시도를 계측한다.
- Java 17 / Boot 3.5와 호환되는 Spring AI 버전 및 BOM을 확인하고 고정한다. 최신 버전 도입을 위해 프레임워크 전체를 먼저 업그레이드하지 않는다.

### Advisor 기반 채팅방 기록과 후속 상담
- `MessageChatMemoryAdvisor`와 `ChatMemory`로 역할별 대화 기록을 전달한다. 수동 메시지 리스트와 HTTP 세션 메모리 방식은 대체하며 실제 API와 저장 시점은 고정한 Spring AI 1.0.9에서 확인한다.
- 인증 사용자와 상담방 소유권 확인 후 서버가 상담방 ID로 `ChatMemory.CONVERSATION_ID`를 설정한다. 임의 입력 ID나 기본 공용 ID를 사용하지 않는다. JWT 인증과 대화 메모리를 분리하고 STATELESS 인증을 유지한다.
- 기존 MySQL JPA Message 기록을 대화 원본으로 유지한다. 이를 읽는 `ChatMemoryRepository` 어댑터와 `MessageWindowChatMemory` 구성을 우선 검토한다. USER는 user, BOT는 assistant로 매핑하고 암호화 본문을 복호화한다. timestamp와 ID로 순서를 고정하며 INFO·검색 원문·one-shot 예시·step-back 결과는 대화 메모리에서 제외한다.
- 전체 기록과 모델 입력 윈도우를 구분한다. 최근 완결된 턴과 필요한 최초 사실관계를 메시지 수·토큰 예산 안에서 전달한다. 윈도우 축소와 메모리 clear가 원본 기록을 지우지 않도록 저장소의 쓰기·삭제 계약을 분리한다.
- Advisor를 대화 전달·갱신 주체로 두고 ChatService의 수동 메시지 재주입을 제거한다. 기존 DB 저장과 Advisor의 add/save가 같은 질문·답변을 중복 저장하지 않도록 관리 주체를 정한다. 현재 질문을 미리 저장한 뒤 Advisor가 다시 추가하는 경로도 차단한다.
- 기본 Advisor의 모델 호출 전후 메모리 저장 시점을 검증한다. 요청 단위 임시 메모리 또는 저장 조정 계층을 통해 출처 검증·DB 저장까지 성공한 질문·답변 쌍만 확정한다. 모델 실패·검증 실패·재시도·동시 요청의 불완전 턴과 중복을 방지하며, 외부 호출 동안 DB 트랜잭션을 유지하지 않는다.
- 후속 질문은 Advisor의 대화와 별도로 최초 근거 스냅샷을 전달한다. assistant 답변을 원문 근거로 취급하지 않고 후속 호출에 자동 검색 Advisor를 붙여 추가 검색하지 않는다.
- 메모리 Advisor는 상담용 ChatClient에만 적용한다. 키워드 추출·step-back·ETL 보강 호출은 상담 기록을 읽거나 쓰지 않도록 분리한다.
- 서버 재시작·재로그인 후에도 소유권 확인을 거쳐 MySQL 기록으로 대화를 이어간다. 대화 측면에서는 로그아웃 시 임시 캐시만 정리하고 원본 기록·근거는 유지한다. 인증 측면에서는 Redis Access 세션과 MySQL Refresh를 폐기한다. 상담방 삭제 시 기록·메모리·근거를 함께 정리한다.
- 역할·순서·윈도우·방별 격리·권한·기록 복원·동시 요청·실패 재시도·현재 질문 중복 방지·보조 호출의 메모리 미사용·후속 추가 검색 없음을 테스트한다.

## 7. 코드 정리 원칙
- 인증 세부 구현·폐기·장애 처리·회전 정책은 [JWT 인증 보안 검토](jwt-security-review.md)를 따른다. Redis에는 Access 원문을 저장하지 않고 활성 식별자를 등록하며 MySQL에는 Refresh 원문 대신 해시를 저장한다. Redis 등록 실패·키 유실을 JWT 단독 인증으로 우회하지 않는다.
- `FinalAnswer`의 검색·프롬프트·호출·마크다운 책임을 분리하고 `GptService`와 겹치는 답변 호출을 합친다.
- 외부 API 클라이언트, 수집 작업, 색인 작업, 검색, 답변 생성, 채팅 저장의 경계를 명확히 한다.
- `ObjectMapper`·HTTP 클라이언트의 직접 생성, 중복 예외 처리, 미사용 import·메서드·DTO를 정리한다.
- `System.out`, `printStackTrace`, 외부 응답 원문 로그를 구조화된 로그로 교체한다. 키·토큰·민감한 질문 본문을 남기지 않는다.
- 외부 API 응답의 세부 오류를 사용자에게 그대로 노출하지 않는다.
- DB 트랜잭션 안에서 장시간 외부 호출하지 않도록 하고 임베딩 작업의 동시성·재시도·진행 상태를 관리한다.
- 패키지명 변경과 전면 DTO 재작성은 동작 개선과 분리한다. 실제 책임이 없는 인터페이스나 계층은 추가하지 않는다.

## 8. 실행 순서와 완료 조건
RAG 기능 개발은 ETL부터 진행한다. 토큰 로그·용도 혼용·CORS/CSRF 개선은 초기 점검에서 우선 처리하고, 상담 API 통합 전 인증 저장소 전환과 권한 검증을 완료한다.

| 단계 | 작업 | 완료 조건 |
| --- | --- | --- |
| 1. 기준선·보안 점검 | API 계약·채팅 권한/실패 테스트, 토큰 로그 제거·용도 분리·요청 보호 | 기존 동작 고정, 토큰 교차 사용 거부·비허용 요청 차단 검증 |
| 2. 실행 환경·스키마 | MySQL/Qdrant/Redis 설정, Flyway, 원문·색인·근거·Refresh 데이터 모델 | 로컬 저장소 실행, 외부 저장소 없이 단위·컨텍스트 테스트 가능 |
| 3. Spring AI ETL | 다중 페이지 수집, Reader·Transformer·Qdrant writer | 소규모 자료 색인·재실행·변경·삭제·실패 재개 검증 |
| 4. 인증 저장소 전환 | Redis Access·세션, MySQL Refresh 회전·폐기, 쿠키·재발급 계약 | 만료 Access 없이 재발급, 로그아웃·재사용 차단, 부분 실패·장애 검증 |
| 5. 검색·최초 질문 | Qdrant 검색, 근거 부족 시 수집·ETL·재검색, 판례 상세 검증, 최초 상태·스냅샷 | 새 페이지 자료가 최초 근거에 반영됨, 빈 결과·예산 종료·동시 요청 검증 |
| 6. 기본 RAG·Advisor | zero-shot 답변·출처 검증, 기록 어댑터·메모리 윈도우·성공 턴 저장 | 방별 맥락 유지·재시작 복원, 후속 추가 검색 없음, 검증 전 답변 미확정 |
| 7. 품질 비교 | one-shot·step-back·필요 시 하이브리드 검색 | 같은 평가셋의 검색·인용·시간·호출량·비용 비교 및 채택 근거 |
| 8. 정리·실행 문서 | 기존 검색·임베딩 경로 제거, API 변경·운영·복구 문서 | 로그인 → 최초 수집/RAG → 후속 상담 → 재발급/로그아웃 흐름 재현 |

기존 LawEmbedding 테이블과 검색 경로는 전환 검증 후 별도 마이그레이션으로 제거한다. 초기화·대량 삭제는 일반 개발 작업과 분리하며 AGENTS.md는 수정하지 않는다.

## 9. 검증 기준
- 평가 질문 30~50개를 준비한다: 법령명/조문 지정, 일상 표현, 복합 쟁점, 후속 질문, 자료 부족 사례를 포함한다.
- 각 질문에 기대 법령·조문과 판단 기준을 기록한다. 학습용 예시와 평가 질문을 구분한다.
- 검색은 Recall@K와 무관한 문서 비율, 답변은 인용 정확도·근거 일치·근거 부족 처리, 운영은 지연시간·호출 수·토큰 사용량으로 비교한다.
- 기존 방식, 새 zero-shot, one-shot, one-shot + step-back을 같은 문서 집합과 모델 설정에서 비교한다. 예시 효과와 검색 질의 변환 효과를 구분한다.
- 다중 턴 상담에서 사실관계 추가·정정, 지시어 해석, 주제 변경을 검증한다. 사용자/상담방 간 분리, 재로그인 후 복원, 윈도우·토큰 상한, 동시 요청, 실패 후 재시도를 테스트한다.
- 후속 질문·세션 변경·서버 재시작 후에도 완료된 상담방의 법령·판례 조회가 재실행되지 않는지 검증한다. 새 쟁점은 기존 근거의 한계를 안내하는지 확인한다.
- 최초 질문의 빈 색인·낮은 관련성에서 다중 페이지·다른 후보 수집 → ETL → 재검색 → 근거 반영을 검증한다. 반복 후보 차단, 동일 질의 임베딩 재사용, 변경 없는 문서 재임베딩 방지, 실행 예산·근거 부족 종료와 후속 질문의 수집·색인 호출 없음을 확인한다.
- 판례의 무관한 결과·빈 결과·본문 미확보·API 실패·중복 후보를 검증한다. 최초 동시 요청의 단일 조회, 중단 상태 복구, 답변 실패 후 저장된 근거 재사용도 확인한다.
- 청킹·중복 방지·갱신·빈 검색·타임아웃·출처 검증은 자동 테스트로 확인한다. MySQL/Qdrant/Redis 통합 테스트와 실제 모델 평가를 분리한다. JWT 검증은 Redis TTL·폐기·장애, Refresh 회전·재사용·동시 요청, 쿠키·CSRF·CORS와 두 저장소 부분 실패를 포함한다.
- 품질 합격 기준은 평가셋과 기준선을 확보한 뒤 수치로 정한다. step-back은 개선 효과가 확인된 경우 기본 또는 선택 전략으로 채택한다.

## 10. 구현 전에 정할 세부 정책
저장소 선택·최초 수집 허용·Advisor 도입은 확정 사항이며 다시 선택할 항목이 아니다.

1. 초기 법령 분야·현행/연혁/시행예정 범위와 파서 보완 범위, 수집 완료 판정.
2. 임베딩 모델·차원·거리 함수·청킹 토큰 수, 컬렉션·Payload 인덱스·활성 색인 전환 정책.
3. 답변 모델, 최초 질문의 시간·외부 호출·임베딩 예산, 근거 충분성 판정과 장시간 요청 응답 방식.
4. 판례 목록 검색은 기존 최대 2회 제안을 확정 정책으로 보지 않는다. 필요 시 페이지·검색어를 확장하되 상세 조회·채택 건수와 실행 예산은 평가로 정한다.
5. Advisor 저장소 어댑터의 읽기·쓰기·삭제 계약, 윈도우·토큰 상한, 성공 턴 확정·동시 요청·기존 기록 복원 방식.
6. 최초 질문 재시도·중복 제출 식별, 중단된 진행 상태 복구와 근거 스냅샷 용량. 답변 실패 시 이미 확정한 근거를 재사용한다.
7. Access 수명(15분 제안), Refresh 수명(7일 제안)·난수/JWT 형식·절대/연장 만료, 다중 기기 세션 정책.
8. Redis 키·TTL·복구 정책, MySQL/Redis 부분 실패 보상·폐기 완료 조건, Refresh 동시 회전·응답 유실 재시도 정책.
9. Access 클라이언트 전달 방식, 운영 사이트 관계에 맞춘 SameSite·CSRF, 민감 작업 재인증·인증 호출 제한.
10. JWT 채팅방 목록 claim은 별도 비교 검토만 수행한다. 목록 최신성·크기·민감정보·권한 위험을 확인하기 전 추가하지 않는다.

### 검증 이력과 현재 한계
이전 문서에는 Docker 중지 상태에서 전체 테스트 20개와 build/JAR 패키징 통과가 기록되어 있다. 이는 당시 구현의 검증 이력이며 새 계획의 구현 완료나 이번 작업의 재실행 결과가 아니다.

이번 최신화는 문서 변경만 포함한다. Redis·Refresh 테이블·ETL·Qdrant 실제 검색·Advisor·최초 근거 저장과 실제 외부 연결은 아직 구현·검증 완료로 표시하지 않는다. 기존 동작 기준은 [backend-baseline.md](backend-baseline.md), 인증 상세는 [jwt-security-review.md](jwt-security-review.md)를 참고한다.
