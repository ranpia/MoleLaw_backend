# 임베딩·리랭커 혼합 부하

2026-10-29. 같은 KURE 서버에 두 연산을 동시에 보내 공유 추론 잠금·대기열의 간섭을 측정한다. [임베딩 단독](embedding-capacity.md), [리랭커 단독](reranker-capacity.md) 이후 단계다.

## 입력과 조건

- 임베딩: 고정 법률 질문 30개, 요청당 텍스트 1개. 512토큰 문서 색인 부하는 포함하지 않는다.
- 리랭킹: 고정 질문 8개와 실제 Qdrant 검색 후보 5/20개. 기존 후보 파일·해시를 검증해 재사용하며 측정 중에는 Qdrant 조회나 새 자료 적재를 실행하지 않는다.
- CPU 4개·메모리 6GiB·float32·추론 스레드 4개, 리랭커 내부 배치 2개, 고정 모델 revision은 단독 시험과 같다. 실행 1개·대기 슬롯 4개·대기 한도 5초를 바꾸지 않는다.
- 임베딩 E개·리랭킹 R개의 전용 HTTP worker를 만든다. 각 worker는 자신의 연산만 순환하며 성공 후 즉시 다음 요청을 보낸다. 거절 후에는 0.25초 쉬고 다음 입력으로 진행한다. 같은 실패 요청을 자동 재시도하지 않는다.
- `(E,R)=(1,1)`은 120초, `(4,1)`과 `(4,4)`는 각각 60초 측정한다. 후보 5개와 20개를 분리해 총 6조건이다. 각 조건 앞에 같은 worker 구성으로 10초 예열하고 모든 요청을 완료한 뒤 별도로 측정한다.
- worker마다 입력 시작 위치가 다르고 각 단계에서 순환을 다시 시작한다. 입력별 성공 횟수와 표본 수가 달라질 수 있으므로 단계 간 처리량 차이를 동일 입력의 인과 효과로 단정하지 않는다.
- 성공 응답의 임베딩 1,024차원·unit norm·유한 값과 리랭커 모델/revision·후보 ID/개수/순서·유한 점수를 검사한다. 예상한 503(full/timeout)은 용량 보호 결과로 집계하고 다른 오류는 중단한다.

E/R worker 비율은 고정 **동시 요청 배분**이다. 각 연산의 속도가 달라 실제 요청 수의 비율이나 사용자 비율과 같지 않다. 한 사용자 요청에서 임베딩→검색→리랭킹을 순서대로 수행하는 전체 RAG 시험과도 구분한다. 이번에는 LLM 호출이나 AI 답변 생성이 없다.

1+1 조건에서도 임베딩 거절 비율은 후보 5개에서 42.4%, 20개에서 66.7%였다. 두 조건의 임베딩 503은 모두 대기 만료다. R worker가 1개인 네 조건에서 리랭킹 거절은 없었으나 임베딩은 모두 대기 만료를 겪었다. 슬롯을 늘리거나 총 요청 수만 조절하는 것으로 긴 리랭킹 뒤의 짧은 임베딩 대기를 해결할 수 있다고 보기 어렵다.

4+4에서 후보 5개의 503은 임베딩 full 336·timeout 22, 리랭킹 full 346·timeout 13이었다. 후보 20개는 임베딩 full 391·timeout 27, 리랭킹 full 286·timeout 19였다. 후보 20개 과부하에서 임베딩 p95가 0.711초로 낮아 보여도 성공은 4건뿐이고 99.1%가 거절됐다. 지연 수치만 보면 과부하를 정상으로 잘못 판단할 수 있다. 예상 밖 HTTP·전송·벡터/점수 검증 오류는 없었다.

12개 예열·측정 단계의 worker 연산 고정·두 연산 HTTP 시간 중첩·집계·창·해시 검증을 통과했다. 서버 카운터에서도 두 연산의 성공 증가를 확인했다. scrape 관측 최대 active 합은 1, waiting 합은 4였다. 발생기 최고 CPU 약 0.050코어·메모리 약 18.7MiB, 대상 working-set/한도 최고 약 49.02%로 관측됐다. 발생기 자원 포화는 보이지 않았다.

부하 해제 후 단독 회복 요청은 임베딩 0.160초·리랭킹 2.667초에 각각 200이었다. 회복 리랭킹은 후보 5개 입력 한 건으로, 후보 20개의 회복 지연을 재측정한 것은 아니다. 최종 두 모델 준비/UP은 1, 두 연산 active/waiting은 모두 0, 전체 Prometheus 9개 job은 UP이었다. 도구는 종료했고 모델·관측 환경은 유지했다.

과거 임베딩 단독 동시 1개는 5.650성공/초·성공 p95 0.246초였다. 이번 1+1의 임베딩은 처리량 감소와 초 단위 성공 지연·503을 보였다. 리랭커 단독 동시 1개·120초는 후보 5개 0.192성공/초·p95 10.394초, 20개 0.092성공/초·p95 14.535초였다. 측정 시점·표본·성공한 입력 분포가 달라 이 비교는 경향 확인용이며 동일 입력 전체의 정확한 성능 감소율로 쓰지 않는다.

현재 구성은 공유 잠금으로 한 번에 추론 1개를 수행한다. 다음 개선 실험은 후보 수/길이 축소와 연산별 추론 자원 분리를 우선 비교한다. 프로세스나 서버를 나누더라도 물리 CPU/GPU를 같이 쓰면 자원 경쟁이 남으므로 각 모델의 자원 예산을 명시해야 한다. 대기 한도만 늘리면 거절 대신 긴 지연으로 바뀔 수 있다. 이번 측정에서는 모델·서버·타임아웃 설정을 변경하지 않았다.

## 지표 해석

처리량·성공 p95/p99·성공/503 수를 연산별로 분리한다. 성공 RPS는 측정 창 안에서 완료한 성공 수/측정 시간이며, 지연은 창 안에서 시작한 성공 요청을 drain까지 포함한다. 503을 섞은 전체 평균 지연으로 성능을 평가하지 않는다. 표본이 적은 p95/p99는 관측 최댓값에 가까울 수 있다.

짧은 임베딩도 긴 리랭킹 뒤에서 대기할 수 있다. 대기 5초 만료가 늘면 계산 자체의 실패와 구별한다. 공유 잠금에는 FIFO·연산별 공정성이 보장되지 않으므로 두 작업 중 하나가 자원을 더 오래 차지하는지 함께 본다. 단독 시험과 측정 시점·성공 입력 구성·표본 수가 다르며, 지연 SLO를 정하지 않았으므로 이 결과로 운영 사용자 수를 보장하지 않는다.

## 실행과 보존

```powershell
.\scripts\load-testing\run-mixed-rag-capacity.ps1
```

모델·Prometheus·Qdrant 환경과 기존 데이터가 준비돼 있어야 한다. 부하 도구는 CPU 1개·메모리 512MiB다. 입력 준비 도구는 오프라인 토크나이저용 1GiB를 사용한다. 기존 개발 환경이나 앱 DB·컬렉션에 데이터를 쓰지 않는다.

Git 제외 경로 `build/rag-dataset/legal-perf-v1/mixed-runs/<실행 ID>/`에 환경/입력 해시, 12개 예열·측정 단계 요약과 요청 JSONL, 최종 결과, 검증 보고서, Prometheus 원시 자료를 남긴다. 원시 기록에는 연산·worker·입력 ID·상태·시각·지연을 기록하며 본문·벡터·비밀값은 넣지 않는다.

검증 도구는 worker별 연산 고정, 두 연산의 실제 HTTP 요청 시간 중첩, 시작/완료 창·상태 집계·파일 해시와 서버의 두 연산 성공 카운터 증가를 확인한다. 부하 해제 뒤 각 연산을 단독 호출해 회복을 확인하고 마지막 scrape의 active/waiting이 모두 0인지 확인한다. 전체 RAG·AI 답변·기본 후보 50개·문서 색인 혼합은 후속이다.
