# AI 답변 생성 부하 테스트 계획

2026-10-29 최초 계획. [실행 결과](answer-generation-results.md)에서 A 대역 14건과 B 재실행의 진단 1건+smoke/단독/동시 2개 15건을 완료했다. 최초 6호출의 인용 실패는 별도 보존하며 해결됐다고 단정하지 않는다. C/D는 미실행이다. 아래는 최초 기준이며 현재 구현/측정 범위는 결과 문서를 따른다. [임베딩·리랭커 혼합 결과](mixed-rag-capacity.md)를 출발점으로 사용한다.

## 먼저 분리할 범위

| 단계 | 무엇을 확인하는가 | 검색/임베딩/리랭킹 | 실제 답변 모델 |
| --- | --- | --- | --- |
| A. 스트림 기능·장애 | 이벤트 파싱·실패 판정·슬롯 반환·저장 경계 | 고정 대역 | 대역 |
| B. 최종 답변 생성 단독 | 고정 근거에서 첫 글자·완료·토큰·인용 검증 | 미실행, 준비한 근거 사용 | 실제 모델 |
| C. 고정 색인 전체 RAG | 질문 처리→검색→근거 판단→답변→검증 | 실제 KURE/Qdrant | 실제 모델, 보조 AI 호출도 포함 |
| D. 저장형 상담 | 완료 전후 방/메시지/근거의 원자적 저장 | C와 동일 | 소수 실제 호출, 장애는 대역 중심 |

현재 혼합 시험은 임베딩 1+리랭킹 1에서도 임베딩 대기 만료가 발생했다. C의 지연과 실패를 곧바로 답변 모델 문제로 해석하지 않는다. 후보 5개와 20개를 별도 실행하고, 후보 50개·새 법령 수집/색인·판례 검색·장문 후속 대화는 첫 범위에서 제외한다.

## 현재 코드와 준비할 부분

- [스트림 계약](../chat/initial-answer-stream.md): 무저장 `POST /api/legal-answers/ndjson`, 저장형 `POST /api/chat-rooms/ndjson`, SSE 대응 경로가 있다. Access 쿠키와 `/api/auth/csrf`에서 받은 토큰 헤더가 필요하다. 무저장은 답변 저장을 하지 않는 경로이며 검색 자체가 전부 읽기 전용이라는 보장은 별도로 확인한다.
- `LegalAnswerService`는 근거 수집 후 실제 모델의 `stream().content()`를 소비하고 인용·길이 검증을 거쳐 완료한다. **고정 근거를 외부에서 주입하는 기존 공개 API는 없다.** B용 도구는 별도 구현이 필요하다. 동일 prompt builder·답변 ChatClient·검증기를 재사용하는 테스트 실행 도구로 준비하며 성능 시험용 공개 엔드포인트를 추가하지 않는다.
- `InitialAnswerStreamService`의 기본 동시 슬롯은 4개다. 5번째 요청의 `RETRIEVAL_BUSY` 공개 오류 이벤트를 A에서 검증한다. 실제 실행에서는 환경변수 덮어쓰기 값을 기록한다.
- 서비스의 `.timeout(timeout)` 기본 20분은 작업 이벤트 사이 무응답 시간에 적용된다. MVC는 설정값+30초를 사용한다. 이를 전체 상담 deadline으로 간주하지 않고, 발생기에서 전체 경과 시간 상한을 별도로 둔다. heartbeat 수신으로 그 상한을 연장하지 않는다.
- 소스 기본 최종 답변 설정은 `APP_AI_ANSWER_MODEL=gpt-5.4-mini`, effort `medium`, max-completion-tokens `16384`다. 실제 실행 설정·공급자 지원 여부는 실행 직전에 확인하고 기록한다. 질문 분석·근거 판단 등의 역할별 모델은 다를 수 있다.
- 현재 부하 Compose는 `OPENAI_API_KEY=loadtest-dummy-key`, 내부 네트워크, `LT_RAG_ENABLED=false`다. 그대로는 실제 생성 시험이 불가능하다. 별도 override에서 테스트 키와 제한된 외부 통신을 구성해야 하며 기존 관측/DB 격리는 유지한다. 실제 키는 Git 제외 환경변수로만 전달한다.
- 기존 1,000개 성능 컬렉션을 앱에 바로 연결할 수 있다고 가정하지 않는다. 앱 VectorStore의 payload·ID·컬렉션 계약과 모델 설정을 먼저 확인하고, 필요하면 별도 앱 호환 시험 색인을 만든다. 동적 수집을 끄는 설정/대역도 준비해야 한다. 단순히 RAG 플래그만 켜서 C를 시작하지 않는다.
- 현재 공통 HTTP/JVM 지표만으로 답변 단계별 시간·토큰·비용이 완성됐다고 보지 않는다. 사용량 메타데이터를 유지하는 응답 관측을 별도로 준비한다. `.content()` 문자열만 보고 실제 usage를 복원했다고 표시하지 않는다.

## 데이터 준비

기존 고정 질문 중 서로 다른 법령의 정상 질문 4개와 근거 부족 질문 2개를 우선 선정한다. 근거 부족 질문의 목표는 근거 없는 답변 완성이 아닌 실제 계약에 맞는 거절/불충분 처리다. 과거 시행일의 법령 스냅샷이므로 기준일을 입력에 명시하며 현재 법률의 정확성 평가와 구분한다.

B에는 질문·채택 근거·인용 UUID·프롬프트·모델 설정을 고정한 fixture를 만든다. 근거 3/8개, 합산 입력 약 2k/8k토큰의 두 크기를 목표로 하되 실제 토크나이저로 측정해 확정한다. 부족한 분량을 같은 조문 복제로 채우지 않는다. 지연 비교용 정상 fixture와 인용 누락/잘못된 UUID/빈 답변의 실패 fixture를 구분한다. 법률 품질 정답셋으로 검증된 자료라고 표시하지 않는다.

출력 한도는 최초 smoke에서 4,096 완료 토큰을 시험용 제안값으로 사용한다. 소스 기본값과 다르므로 결과에 명시하며 정상 답변이 잘리거나 reasoning만으로 소진되면 조정하고 조건을 새로 기록한다. 정상 완료와 길이 제한 종료를 같은 성공으로 집계하지 않는다. 캐시가 있는 경우 실제 usage의 cached token 여부와 반복 순서를 보존한다.

## 실행 순서와 최초 상한 제안

1. **A — 비용 없는 기능 확인.** 1개로 NDJSON/SSE 각 1건을 파싱하고, NDJSON 중심으로 1→2→4→5개 요청을 실행한다. 느린 첫 출력·중간 정지·429/5xx·깨진/잘린 스트림·잘못된 인용·클라이언트 취소를 재현한다. 5개는 앱 슬롯 경계를 확인하는 짧은 기능 시험이다. 대역 처리량을 실제 모델 성능으로 보고하지 않는다.
2. **B smoke — 실제 3건 이내.** 동시 1개로 입력/출력 usage와 reasoning·빈 출력·인용·종료 사유·비용 추정을 확인한다. 예열도 유료 호출 수에 포함한다. usage 수집과 지출 제한이 작동하지 않으면 여기서 중단한다.
3. **B 단독 — 정상 최대 12건.** 동시 1개 6건, 동시 2개 6건을 두 입력 크기로 균등 분배한다. 고정 건수로 실행해 비용을 제한하며 최소 60초를 채우려고 추가 호출하지 않는다. 이 정도 표본의 p95/p99는 참고값이며 안정적인 백분위나 최대 수용량으로 선언하지 않는다. 4개 이상 실 모델 증량은 첫 결과 이후 계획을 갱신한다.
4. **C 고정 색인 RAG — 최대 5상담.** 먼저 동시 1개 정상 1상담으로 실제 호출 그래프를 확인한다. 나머지는 후보 5/20개 및 동시 1/2개를 남은 예산 안에서 비교한다. 전체 상담에는 질문 분석·근거 판단·최종 답변 등 여러 유료 호출이 발생할 수 있다. B에서 실패하거나 지역 모델 큐가 포화되면 증량하지 않는다.
5. **D 저장형 — 실제 최대 2상담.** 시험 계정/방에 한정해 검증 완료 후 저장과 completed 반환을 확인한다. 대역으로 검증 실패 시 방·메시지·근거 미저장, 저장 전 연결 종료, 커밋 후 응답 유실을 구분한다. 연결 종료만으로 롤백됐다고 단정하지 않고 DB를 재조회한다. 실패 요청을 자동 재실행하지 않는다.

첫 회 전체 한도는 **유료 공급자 요청 30회·예상 지출 USD 5·요청별 전체 180초**를 제안한다. 이는 설정·합의 전의 계획값이며 현재 적용된 제한이 아니다. 네트워크/SDK 재시도와 보조 모델 호출도 30회에 포함하고, 상담 수 상한이 남아 있어도 글로벌 한도에 먼저 도달하면 중단한다. 앱의 장시간 스트림 기본값을 임의로 바꾸지 않고 180초 발생기 제한으로 취소되는 사례를 별도 분류한다.

SDK 자동 재시도는 시험에서 명시적으로 제어하고, 프록시/HTTP transport 계층의 실제 공급자 시도 수로 상한을 집행한다. 논리적인 ChatClient 호출 수만 세서 내부 재시도를 누락하지 않는다.

실행 전 실제 모델별 당시 요금·프로젝트 RPM/TPM 제한을 확인해 기록하고, 입력+최대 출력(추론 포함)의 보수적인 예상 비용을 **동시 실행 중인 호출까지 예약**한다. 예약까지 포함한 예산을 넘을 새 요청은 시작하지 않는다. 공급자 과금 지연이나 취소 후 발생하는 비용 때문에 정확한 청구액 상한을 보장하는 방식은 아니며 마지막에는 실제 usage/청구와 대조한다. 누락 usage는 0원으로 정산하지 않고 보수적으로 예약을 유지한다. 공급자 키의 접근 가능한 프로젝트만 사용하고 키·응답 본문을 공용 로그에 남기지 않는다.

## 판정·관측·오류 처리

| 지표 | 측정 기준 |
| --- | --- |
| 사용자 첫 답변 시간 | HTTP 요청 시작→첫 비어 있지 않은 answer_delta. progress/info/heartbeat 제외 |
| 생성 단계 첫 출력 시간 | 답변 모델 호출 직전→첫 모델 텍스트. 검색 시간을 제외한 별도 계측 |
| 완료 시간 | 요청 시작→검증/필요한 저장을 마친 completed 수신 |
| 성공 상담 처리량 | 창 안 completed 수/초, 분당 완료 상담. 개별 모델 호출 RPS와 구분 |
| 토큰/비용 | 역할별 실제 input/output/reasoning/cache usage·호출/재시도 수. 추정치는 별도 표시 |
| 오류 | HTTP 인증/CSRF, 앱 busy, KURE full/timeout, 공급자 429/5xx, 인용 검증, 빈/잘린 출력, 연결 취소, 전체 시간 초과 |
| 자원 | KURE active/waiting/지연, 백엔드 CPU/heap/스레드·스트림 슬롯, DB 풀·저장 시간, 발생기 자원 |

HTTP 200만으로 성공 처리하지 않는다. `completed` 1회 수신과 최종 답변/인용/저장 계약 검증을 성공 조건으로 삼는다. `error`, completed 없는 EOF, 파싱 오류와 중복 완료는 실패로 분류한다. 실패·취소한 요청을 자동 재시도하지 않는다. 중간 delta는 검증 전 임시 답변이며 final 결과를 기준으로 검사한다.

예산/호출 상한 도달, usage 관측 유실, 예상 밖 저장·인용 누출, 연속 공급자 429 3회, 관측 유실 3회, 대상 working-set 85% 초과, 발생기 CPU 한도 85% 지속이면 새 호출을 중단한다. 정상적인 앱 busy·KURE 503도 비율을 보고하지만 같은 조건에서 계속 증량하지 않는다. 종료 후 단일 회복 호출도 예산에 포함하며 잔여 예산이 없으면 추가 유료 호출 없이 상태/슬롯 관측으로 회복 범위를 한정해 보고한다.

Grafana에는 첫 answer_delta·completed 시간, 성공/실패 상담 수, 연산별 큐와 모델별 호출/usage를 연결한다. 신규 계측은 미구현이며 작업 전까지 제공 중이라고 표시하지 않는다. metric label에는 질문·방 ID·사용자 ID·request ID를 넣지 않는다. 상세 요청 연결은 제한된 결과 파일의 run/request ID를 사용한다.

## 준비 작업과 완료 산출물

- 구현할 도구: NDJSON/SSE 파서와 단말 이벤트 판정, B용 고정 근거 실행 도구, 역할별 usage 관측·호출/비용 예약 제한, 비용 없는 장애 대역과 저장 검사, 전체 경과 시간/취소 처리.
- 환경: 유료 호출 전용 override·테스트 키·외부 통신 범위, 앱 호환 시험 색인과 수집 경로 고정, 실제 모델/가격/쿼터·토큰 한도 확인. 기존 dummy/internal 환경을 직접 덮어쓰지 않는다.
- 결과: run ID·커밋·모델/옵션·프롬프트/fixture 해시·각 역할 호출 수·usage/비용·성공/실패·첫 출력/완료·저장 검사·회복. AI 답변 원문은 Git 제외 제한된 자료로 보존하고 보고서에는 비식별 실패 예시만 넣는다.
- 첫 결과를 읽은 뒤 사용자 체감 목표(첫 글자/완료 SLO)와 허용 오류율을 정한다. 현재는 이를 정하지 않았으므로 성능 합격이나 운영 사용자 한도를 선언하지 않는다.

현재 A/B 도구와 동시 1/2개 재실행을 확인했고, [C 격리 준비](full-rag-preparation.md)에서 시험 색인·수집 차단·시험 게이트웨이 예산/관측·합성 배선을 검증했다. 운영 전역 예산 기능과 유료 C 실행을 완료했다고 표시하지 않는다. B의 간헐적 인용 실패 위험은 재실행 성공으로 해소됐다고 표시하지 않는다.
