# 임베딩 동시 처리 한계

2026-10-29. KURE 서버에 직접 요청하며 백엔드 전체 RAG·리랭킹 동시 실행·Qdrant 부하는 포함하지 않는다.
리랭커는 메모리에 로드돼 있지만 요청을 보내지 않았다. AI 답변 생성도 실행하지 않았다.

## 조건과 측정 기준

- CPU 4개 한도, 메모리 6GiB, float32, 추론 스레드 4, 고정 KURE-v1 revision.
- 요청당 텍스트 1개. 짧은 질문은 고정 법률 질문 30개를 순환하고 범위 밖 대조 질문은 제외한다.
- 문서 입력은 길이 시험 자료 12개로 511~512토큰이다. 특수 토큰을 포함한다.
- 동시 HTTP worker 1/2/4/5/8개를 탐색하고 필요한 중간 구간은 3개로 세분화한다.
- 단계마다 10초 예열 후 완전히 drain하고 별도 60초를 측정한다. 거부 없는 높은 구간은 120초 재검증한다.
- 성공 후 생각 시간은 없다. 503 후에는 0.25초 쉬고 다음 입력을 시작한다. 같은 요청을 자동 재시도하지 않는다.
- 503 중 queue_full/queue_timeout은 용량 보호 결과로 집계한다. 다른 상태·전송 실패·벡터 이상은 중단한다.
- 모든 성공 응답에서 개수·1,024차원·유한 값·unit norm을 확인한다.

성공 처리량은 측정 창 안에서 **완료된 성공 수/측정 초**다. 창 안에서 시작했지만 늦게 완료된 성공은
drainSuccesses로 따로 남긴다. 성공 p95/p99는 측정 창에서 시작한 요청 전체를 완료까지 기다려 계산한다.
빠르게 실패한 503을 성공 지연에 섞지 않는다. 거부율은 창 안에서 시작한 전체 요청의 응답 기준이다.
클라이언트 시간에는 요청 직렬화·왕복·응답 파싱과 벡터 검증이 포함된다.

모델 UP·준비·메모리와 발생기 CPU/메모리를 수집한다. 관측 손실/메모리 위험/발생기 포화는 중단한다.
사용자가 지정한 지연 SLO는 없으므로 ‘120초 거부 없음’과 ‘허용 지연 이내’를 같은 의미로 쓰지 않는다.

## 설정에서 계산하는 한도

KURE는 공유 inference lock으로 실제 추론 1개를 실행하고 대기 슬롯 4개를 둔다.
따라서 **입장 가능한 추론 요청은 실행 1+대기 4=5개**다. CPU 스레드 4개가 독립 추론 4개를 뜻하지 않는다.
소켓 접속 자체나 실제 사용자 수의 한도와도 다르다.

평균 단독 서비스 시간 S와 대기 한도 T=5초를 사용하면,
`min(5, 1 + floor(T/S))`를 초기 참고값으로 볼 수 있다. 일정한 서비스 시간·FIFO를 가정한 근사치이므로
길이 변동·락 스케줄링·실행 환경·꼬리 지연이 있는 실제 한도는 동시 요청 시험으로 확인한다.
거부 없는 폐회로에서는 `성공 RPS × 성공 평균 시간 ≈ 처리 중 요청 수`도 함께 대조한다.

백엔드의 `LawVectorProperties`도 기본 embeddingConcurrency=1, embeddingQueueCapacity=4,
embeddingWaitMillis=5000을 사용한다. 이번 시험은 이 백엔드 제한을 우회하므로 결과를 전체 RAG 사용자 수로 환산하지 않는다.
검색 흐름에서 한 질문이 몇 번 임베딩/리랭킹을 호출하는지도 별도 고려해야 한다.

## 짧은 질문 결과

실행 `embed-20261029T015051Z`, 요청당 입력 1개. 아래 거부 수의 분모는 시작 창의 전체 요청이다.

| 동시 요청 | 측정 | 성공/초 | 성공 p95 초 | 503 거부 |
| --- | ---: | ---: | ---: | ---: |
| 1 | 60초 | 5.650 | 0.246 | 0/340 |
| 2 | 60초 | 4.200 | 1.071 | 0/254 |
| 4 | 60초 | 3.650 | 1.645 | 0/223 |
| 5 | 60초 | 6.200 | 0.935 | 0/377 |
| 8 | 60초 | 6.083 | 0.980 | 710/1080 |
| 5 | 120초 | 5.842 | 1.093 | 0/706 |

현재 질문 분포에서 최대 입장 5개가 120초 동안 거부 없이 관측됐다. 8개로 늘려도 성공 처리량은 늘지 않았고
약 65.7%가 큐 포화로 거부됐다. 단계별 속도는 비단조적이므로 한 번의 최고값을 운영 최대 성능으로 보장하지 않는다.

## 511~512토큰 문서 결과

같은 실행의 기본 탐색 뒤 `embed-20261029T021256Z`에서 3개 요청을 추가 측정했다.
3개 구간의 거부는 queue_timeout이며 추가 120초 확인으로 승격하지 않았다.

| 동시 요청 | 측정 | 성공/초 | 성공 p95 초 | 503 거부 |
| --- | ---: | ---: | ---: | ---: |
| 1 | 60초 | 0.683 | 1.541 | 0/42 |
| 2 | 60초 | 0.717 | 3.000 | 0/45 |
| 3 | 60초 | 0.533 | 7.037 | 3/38 |
| 4 | 60초 | 0.417 | 7.853 | 18/45 |
| 5 | 60초 | 0.583 | 7.456 | 17/56 |
| 8 | 60초 | 0.650 | 6.327 | 714/757 |
| 2 | 120초 | 0.558 | 5.661 | 0/69 |

4/5개는 대기 만료, 8개는 입장 거부 700개+대기 만료 14개였다. 성공한 요청만의 p95가 낮아진다고
전체 서비스가 개선된 것으로 해석하지 않는다. 거부된 요청도 반드시 함께 본다.

**이번 조건에서 120초 거부 없는 동시 요청 수는 짧은 질문 5개, 문서 2개**다.
이는 대기를 포함한 요청 수다. 실제 동시 추론은 항상 1개이며 서버 지표에서 active 최대 1·waiting 최대 4를 확인했다.
문서 2개도 p95 5.661초이므로 낮은 지연 목표에 적합하다는 뜻은 아니다.

평균 단독 시간은 질문 약 0.1765초·문서 약 1.431초였다. 역수로 계산한 단독 참고 처리량은
약 5.665건/초·0.699건/초다. 문서의 평균값 기반 대기 계산은 4개까지를 시사하지만,
실제 시험에서는 3개부터 거부가 관측됐다. 평균값만으로 꼬리 지연·락 스케줄링·동시 부하에서의
서비스 시간 변동을 보장할 수 없으므로 관측된 낮은 구간을 기준으로 정리했다.

120초 확인의 `성공 RPS × 성공 평균 시간`은 질문 약 **4.999**, 문서 약 **1.985**로
각각 대기 포함 5개·2개의 폐회로 요청 수와 대체로 일치했다.

## 회복·관측과 해석 한계

모든 단계에서 예상하지 않은 HTTP/전송/벡터 오류는 0이었다. 기본 시험과 3개 세분화 시험 모두
부하 해제 뒤 단일 질문 10초 검사에서 거부 없이 회복했다. 503 보호 동작을 운영 장애나 성공 응답에 합치지 않았다.
발생기 CPU 관측 최고값은 약 0.176코어(한도 1코어), KURE working set/메모리 한도 비율은 약 32.4%였다.
이는 발생기의 CPU 한계로 처리량이 막힌 시험으로 해석하지 않는다.

프로브의 여러 지표를 합칠 때 동일 레이블의 metric이 set 연산에서 가려지지 않도록 `__name__` 매칭을
추가했다. 최초 요청 통계·모델 준비·메모리 보호 측정은 보존했고 서버의 active/waiting은
Prometheus 원시 시계열을 별도로 조회해 `server-gates.json`으로 저장했다.
수정된 관측 함수에서도 두 embed 게이트 지표의 존재를 확인했다.
예열·측정·회복을 합친 28개 phase의 요청 원본과 성공/거부/drain/처리량 집계를 대조했고 일치했다.
측정 종료 경계 이후 새로 시작된 요청은 0개였다.

지연·처리량은 이 CPU/입력/배치/단일 프로세스 조건의 관측치다. JVM 백엔드의 대기 제한,
질문당 호출 횟수, 리랭킹 경쟁, 긴 색인 배치와 혼합 트래픽은 추가 시험이 필요하다.
큐 상한을 늘리는 것만으로 단일 추론 처리량이 증가한다는 근거는 없다.

## 재현

```powershell
.\scripts\load-testing\run-embedding-capacity.ps1
# 중간 구간만 별도 확인
.\scripts\load-testing\run-embedding-capacity.ps1 -Workload document512 -Concurrency 3
```

원본은 Git 제외 `build/rag-dataset/legal-perf-v1/concurrency-runs/<run-id>/`에 보존한다.
각 단계의 요청별 JSONL·성공/거부 통계·서버/발생기 관측, 설정과 전체 result.json을 기록한다.
부하 해제 후 단일 질문 10초의 성공·거부 없음도 확인한다. 이 시험은 DB 데이터를 쓰거나 기존 벡터를 변경하지 않는다.
