# 조회 API 단계별 한계 탐색

실행일: 2026-10-28. 일반 방 목록·메시지 조회만 대상으로 하며 AI·Qdrant·RAG 요청은 보내지 않는다.
결과는 아래 실행 기록과 로컬 보고서에서 확인한다. 수용량은 데이터·장비·대기 시간에 종속되며 운영 사용자 수 보장이 아니다.

## 시험 조건

- 같은 PC의 Docker VM, 백엔드 CPU 2·RAM 2GiB, MySQL CPU 1·RAM 1.5GiB·버퍼 풀 512MiB.
- Hikari 최대 연결 10개·연결 대기 제한 5초. Redis maxmemory 128MiB·noeviction.
- Locust CPU 상한 3·RAM 1GiB. 발생기와 서버는 같은 호스트 자원을 공유한다.
- 데이터는 `lt-read-v1`: 계정 20개·방 200개·메시지 4,000개. VU가 20개를 넘으면 읽기 전용 계정 풀을 재사용한다.
- 요청은 목록/메시지 번갈아 실행, 요청마다 2~5초 휴식. VU는 동시에 계속 요청하는 수가 아니라 휴식 중인 사용자까지 포함한다.
- 낮은 단계는 워밍업 최소 15초 + 본측정 45초. 사용자 수/20초 이상으로 준비 시간을 늘려 모든 VU 배치 후 측정한다.
- 마지막 정상 단계는 워밍업 최소 30초 + 본측정 최대 180초로 재확인한다. 총 길이는 Access 5분 TTL보다 짧게 제한한다.

## 로그인과 조회의 구분

첫 탐색은 VU마다 로그인했다. 이때 로그인 집중이 조회 본측정 전에 병목을 만들 수 있다.
그래서 두 번째 탐색은 계정 20개를 먼저 순차 인증한 뒤 Access 토큰을 독립 쿠키 세션에 배분한다.
토큰은 메모리에만 보관하고 보고서에 저장하지 않는다. 이 모드는 로그인 처리량 평가가 아닌 인증된 조회 평가다.
종료 시 대량 로그아웃 부하를 만들지 않고 클라이언트 쿠키를 폐기한다. 서버 Access·Refresh 상태는 각 TTL을 따른다.
시험용 Redis에 인증 상태가 남을 수 있지만 FLUSHALL이나 다른 데이터 삭제는 수행하지 않는다.

워밍업과 본측정을 구분한다. 현재 스크립트는 측정 창 안에 완료된 조회로 처리량을 계산하고,
창 안에 시작한 요청의 지연은 종료 후 드레인까지 수집한다. 이 경계 처리는 오프라인 검증을 추가했다.
초기 탐색 스크립트는 창 안에 시작·완료한 요청만 세어, 지연이 긴 구간의 RPS를 낮게 계산했다.
기존 파일을 덮어쓰지 않고 CSV 이력의 완료 건수로 약식 재집계한 값도 함께 남겼다. 아래 포화 구간 RPS는 이 약식 완료 기준이다.
HTML·CSV는 경계 요청·드레인·주기적 파일 쓰기 시점 때문에 summary와 차이가 날 수 있다.
응답 HTTP 상태 외에도 소유 방·평문 복호화·USER/BOT 순서·INFO 개수를 검증한다.

## 확대 및 중단 조건

탐색은 2 → 4 → 8 → 16 → 32 → 64 → 128 → 256 → 512 → 1,024 → 2,048 → 4,096 순서다.
4,096은 실행 안전 상한이며 여기에 도달했다고 서버 최대 용량으로 선언하지 않는다.

- 요청/내용 검증 오류는 즉시 중단한다. 원인에 따라 로그인 집중과 본측정 오류를 구분한다.
- p95 1초 초과 또는 연속 두 단계에서 처리량 증가가 20% 미만이면 더 확대하지 않는다. 이 숫자는 탐색용 임시 기준이며 합의된 서비스 SLO가 아니다.
- JVM 사용 메모리 합 1.6GiB 초과는 메모리 보호 중단, 발생기 CPU 2.55코어 이상이 3회 연속 또는 메모리 900MiB 초과는 발생기 한계로 구분한다. 컨테이너 전체 메모리는 Docker stats에서 별도 관측한다.
- backend/mysql/redis 관측 대상이 연속 확인되지 않으면 시험을 중단한다.
- 같은 자원 설정을 유지하고 정상 직전 단계의 지속 시험을 수행한다. 단일 짧은 결과로 장시간 안정성을 보장하지 않는다.

## 실행 명령

명령을 실행하면 실제 부하를 발생시킨다. 전용 환경·합성 데이터·[MySQL/Redis 관측](database-monitoring.md)을 먼저 준비한다.

```powershell
# VU별 로그인 포함 탐색
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/load-testing/run-read-capacity.ps1
# 인증을 미리 완료하고 조회만 탐색 (현재 예시는 128명부터)
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/load-testing/run-read-capacity.ps1 -StartUsers 128 -Preauthenticate
```

StartUsers를 2보다 크게 지정하면 이전 단계가 다른 실행에서 검증됐다는 전제다. 앞선 결과를 함께 기록한다.
파일은 `build/loadtest-runs/capacity-<UTC>/explore-N`, `confirm-N`의 HTML·CSV·summary.json과 시리즈 result.json이다.
CPU·컨테이너 메모리·I/O 표본은 `observe-capacity.ps1`의 docker-observations.jsonl에 별도로 저장한다.
관측 값은 표본 간의 순간 스파이크를 모두 잡지 못하며 exporter 쿼리도 MySQL QPS에 포함된다.

## 실행 기록

**실제 확인된 안정 구간은 512 VU·약 146 RPS다. 1,024 VU는 지속 시험 실패, 2,048 VU는 처리량 증가 없이 지연이 커졌다.**
VU는 2~5초 쉬는 가상 사용자이므로 512개의 동시 쿼리나 실제 서비스 사용자 512명 보장을 의미하지 않는다.

| 구간 | 본측정 | 처리량 | p95 | 오류·판정 |
| --- | --- | --- | --- | --- |
| 64 VU 재검증 | 약 180초 | 약 18 RPS | 26ms | 오류 0 |
| 256 VU 재검증 | 약 180초 | 약 73 RPS | 18ms | 오류 0 |
| 512 VU 최종 재검증 | 약 180초 | 약 146 RPS | 17ms | 조회 26,246회·오류 0, 안정 구간 확인 |
| 1,024 VU 짧은 탐색 | 약 45초 | 완료 기준 약 279 RPS | 약 1초 | 짧은 시험은 오류 0, 경계 구간 |
| 1,024 VU 지속 재검증 | 180초 계획 중 약 167초 후 중단 | 약 270 RPS | 약 1.5~1.7초 | HTTP 500 1회, 안정 구간으로 인정하지 않음 |
| 2,048 VU 탐색 | 약 45초 | 완료 기준 약 284 RPS | 약 5초 | 오류 0이나 지연 기준 초과·처리량 포화, 추가 증량 중단 |

1,024→2,048로 늘려도 완료 처리량은 약 280 RPS에서 더 늘지 않았다.
초기 strict summary의 2,048 구간 254 RPS는 긴 응답이 창 경계에 걸려 제외된 값이다. 이를 실제 처리량 감소로 단정하지 않는다.
CPU 표본에서 백엔드는 2,048 구간 평균 약 202%(약 2코어), MySQL은 약 75%, Redis는 약 0.4%였다.
컨테이너 CPU는 짧은 관측 구간/스케줄링 때문에 quota 환산값을 일시 초과할 수 있다.
backend CPU quota 포화와 연결 경로가 우선 조사 대상이며, 개별 SQL·프로파일러 검증 없이 단일 근본 원인을 확정하지 않는다.
1,024 지속 시험의 HTTP 500 시각에는 Hikari 연결 10개가 모두 사용 중이고 대기 180개·획득 timeout 약 5,059ms가 로그에 남았다.

### 해석에서 제외하거나 분리한 두 제한

1. `capacity-20261028T065523Z`: VU별 로그인 포함. 128 VU 준비 중 Hikari 전체 10개 사용·대기 78·5초 획득 timeout을 기록했다.
   준비 구간 오류이므로 조회 최대를 64명이라고 결론 내리지 않았다. 당시 백엔드 CPU는 약 2코어까지 사용했다.
2. `capacity-20261028T070608Z`: 미리 인증한 풀로 조회. 128/256은 통과했지만 512에서 연결 timeout이 발생했다.
   HAProxy의 시험용 maxconn=512가 영향을 준 것으로 판단해 8192로 올리고, gateway CPU/RAM 상한도 0.5코어/256MiB로 맞췄다.
   수정 뒤 같은 512 목표는 오류 없이 통과했다. 인위적 게이트웨이 제한을 백엔드 용량으로 해석하지 않았다.
3. `capacity-20261028T071241Z`: 게이트웨이 제한을 보정한 최종 탐색과 `recovery-512` 재검증.
   백엔드·MySQL·Hikari 자원 설정과 데이터는 변경하지 않았다. 사전 인증 토큰은 메모리에만 두었다.

### 원본 결과와 검증 제한

- `build/loadtest-runs/capacity-20261028T065523Z/`: 2~128 탐색·64 재검증.
- `build/loadtest-runs/capacity-20261028T070608Z/`: 사전 인증 128/256/512 탐색·256 재검증.
- `build/loadtest-runs/capacity-20261028T071241Z/`: 수정 후 512/1024/2048 탐색·1024 재검증·512 최종 재검증.
- 최종 안정 보고서: `build/loadtest-runs/capacity-20261028T071241Z/recovery-512/report.html`, `summary.json`.
- `completed-window-summary.json`은 CSV 초 단위 관측 시각으로 재집계한 약식 완료 처리량이다. 측정 경계 약 1초의 오차가 있다.
- 마지막 Locust 종료 시 CSV writer의 닫힌 파일 경합 경고를 관측했다. 워크로드 오류 0·summary/HTML 생성·종료 코드 0과는 구분한다.
  CSV는 마지막 기록 주기까지만 반영될 수 있어 최종 합계는 summary를 기준으로 읽는다. 데이터 파일 JSON/CSV 파싱을 확인했다.
- 콜드 캐시·큰 데이터·쓰기·AI·RAG·장시간 soak 시험은 하지 않았다. 20개 계정과 작은 데이터의 반복 조회 결과다.
- 컨테이너 cAdvisor는 시험 완료 뒤 설치했다. 과거 CPU·메모리는 docker-observations.jsonl에서 확인하고 새 대시보드로 소급 수집하지 않는다.

다음 성능 작업은 로그인 시 DB 연결 유지 범위·조회 SQL 수/트랜잭션·CPU 프로파일을 확인하고,
데이터 규모와 실제 요청 혼합을 늘리는 것이다. 현 수치를 전체 상담 또는 RAG 동시 사용자 수로 사용하지 않는다.
