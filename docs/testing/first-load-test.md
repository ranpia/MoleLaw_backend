# Locust 사용자 1명 첫 실습

2026-10-28 첫 실행을 완료했다. 조회 흐름과 지표 연결을 확인하는 소규모 시험이며 최대 처리 용량 측정이 아니다.

## 무엇을 실행하는가

사용자 1명이 합성 계정으로 로그인한 뒤 아래 요청을 번갈아 실행한다. 각 조회 다음에는 2~5초 기다린다.

1. `GET /api/chat-rooms?page=0&size=20`: 본인 방 10개와 평문 미리보기 확인.
2. `GET /api/chat-rooms/{roomId}/messages`: 본인 방 하나를 무작위 선택하고 USER/BOT 20개·INFO 1개, 복호화 내용·역할 순서 확인.

로그인은 시작 시 1회이며 끝에는 로그아웃한다. 초기화·정리 요청은 `setup:`·`cleanup:`, 실제 조회는 `read:`로 구분한다.
HTTP 200뿐 아니라 응답 내용도 검증한다. 오류가 발생하면 조기에 중단하며 재시도해 오류를 숨기지 않는다.
AI·RAG·상담 생성 API는 호출하지 않는다. 사용자 수는 1명, 실행 시간은 60초, 대상은 테스트 게이트웨이로 제한한다.

## 실행과 결과 파일

최소 환경과 [합성 데이터](test-data.md)를 준비한 다음 저장소 루트에서 실행한다. **명령을 다시 실행하면 새 1분 시험을 시작한다.**

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/load-testing/run-one-user.ps1
```

스크립트가 사전 상태를 확인한 뒤 일회성 Locust 컨테이너를 실행하고 종료 시 제거한다. 실행 중 데이터 볼륨은 삭제하지 않는다.
기본 `docker compose up`은 이 부하를 자동 실행하지 않는다. Locust 서비스 기본 명령은 여전히 버전 확인뿐이다.

결과는 Git 제외된 `build/loadtest-runs/one-user-<UTC시각>/`에 남는다.

| 파일 | 읽는 방법 |
| --- | --- |
| report.html | 브라우저에서 요청별 시간·실패·분포 확인 |
| summary.json | 조회만 집계한 건수/RPS, 초기화·정리 포함 요청별 시간과 성공 판정 |
| requests_stats.csv | Locust 전체 집계. setup/cleanup이 포함되므로 조회와 구분 |
| requests_stats_history.csv | 시간별 변화 |
| requests_failures.csv·requests_exceptions.csv | 실패·예외 유무 |

성공 판정은 요청 오류 0·조회 응답 존재·약 1분 실행 여부다. 응답 시간 SLO 합격 기준은 아직 정하지 않았다.
최초 연결·로그인도 포함하며 별도 워밍업이나 캐시 초기화는 하지 않았다. 다음 단계에서 정식 워밍업·반복 시험을 구분한다.

## 첫 실행 결과

- 실행 ID: `one-user-20261028T063028Z`
- 한국 시각: **2026-10-28 15:30:29 ~ 15:31:29**, 실제 기록 약 59.7초.
- Locust 2.47.0, 가상 사용자 1명, 요청 사이 2~5초 휴식.
- 데이터: 사용자 20명·방 200개·저장 메시지 4,000개의 `lt-read-v1`. 이번 요청은 첫 계정의 방만 조회했다.
- 경로: 같은 PC/Docker VM의 Locust → HAProxy gateway → 백엔드 → 전용 MySQL. 개발 환경 중지, RAG 비활성.

| 요청 | 횟수 | 실패 | 평균 | p95·p99 (근사) |
| --- | --- | --- | --- | --- |
| 방 목록 | 9 | 0 | 31.5ms | 43ms |
| 메시지 조회 | 9 | 0 | 23.5ms | 39ms |
| 로그인 | 1 | 0 | 69.8ms | 70ms |

조회 **18회**, CSRF·로그인·로그아웃 포함 전체 **22회**, 실패 **0회**, Locust 종료 코드 **0**이었다.
전체 실행 시간 기준 조회는 약 **0.30 RPS**다. 휴식 시간을 포함한 값이므로 서버 최대 처리량과 다르다.
요청별 표본이 9개뿐이라 p95·p99는 반올림된 큰 값에 가까우며 장기 지연을 판단할 자료로는 부족하다.

Prometheus를 해당 시간 범위·5초 간격으로 조회한 12개 관측점에서 backend UP은 모두 1, Hikari pending은 모두 0이었다.
관측점 사이에 매우 짧은 대기가 없었다고 단정하지 않는다. JVM 힙은 약 230~271MiB였다.
실행 중 단일 Docker 관측에서 Locust는 약 43MiB로, 발생기 자원 포화 징후는 보이지 않았다. 지속 최대값 측정은 아니다.
관측 요약은 같은 결과 폴더의 `prometheus-observations.json`에 보관했다.

Grafana 확인 범위: [첫 시험 시간대로 열기](http://localhost:13000/d/molelaw-loadtest-backend?from=1793169029189&to=1793169088899).
Prometheus 보존 정책은 3일이므로 이후에는 로컬 HTML·CSV·요약 결과를 사용한다.
