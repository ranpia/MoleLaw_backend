# Redis 성능 시험 계획

2026-10-29 실행 완료. 실제 범위와 결과는 [Redis·Refresh API 결과](redis-performance.md)를 따른다.
아래는 실행 전 수립한 계획이며 재사용할 시나리오를 보존한다.

## 후속 Refresh API 부하와 오류 검증

MySQL·Redis 직접 시험이 끝나면 실제 `POST /api/auth/refresh`를 Locust로 검증한다.
CSRF 조회와 로그인은 준비 단계에서 수행하고 사용자별 쿠키 저장소·family를 분리한다.
정상 부하는 매 응답의 새 Refresh로 다음 요청을 보내며 토큰·Set-Cookie 원문을 기록하지 않는다.
현재 `UserService.reissue`는 Redis 회전 전에 `findByIdForUpdate`로 사용자 행을 잠근다.
서로 다른 계정과 같은 계정의 여러 family를 별도 측정해야 DB 직렬화를 Redis 병목으로 오인하지 않는다.

| 시나리오 | 응답과 상태 확인 |
| --- | --- |
| 정상 순차 갱신·독립 세션 증원 | 200, Access 발급·Refresh 교체, 최초 절대 만료 유지, 처리량·p95/p99·DB/Redis 대기 |
| 같은 Refresh 동시 요청 | 쿠키 복제 후 동시 전송. 최대 한 번 회전 성공, 재사용 탐지 401 및 family 폐기 |
| 이전 Refresh 재사용 | REFRESH_TOKEN_REUSED 401, 발급된 다음 Refresh도 거부, 다른 family 유지 |
| 누락·변조·만료·로그아웃 | 401·실제 오류 코드, 신규 인증 쿠키 미발급 |
| CSRF 누락·불일치 | 403, 토큰 미소비. 올바른 CSRF로 재시도해 상태 확인 |
| Redis 지연·단절·쓰기 OOM | AUTH_STORE_UNAVAILABLE 503, 잘못된 성공·인증 쿠키 발급 없음, 복구 후 상태 확인 |
| 회전 후 응답 유실 | 서버 처리 후 응답 차단. 이전 토큰 재시도로 재사용 탐지·family 폐기 확인 |
| DB 지연·연결 고갈 | 사용자 조회 실패의 실제 응답과 회전 여부 확인, Redis 장애와 분리 |

동시 요청에서는 먼저 200을 받은 세션도 뒤따른 재사용 탐지로 폐기될 수 있다. 응답 코드만 세지 않고
발급된 다음 Refresh로 재갱신하여 상태를 검증한다. 응답 유실 후 무조건 재시도는 현재 계약상 세션 폐기를
유발할 수 있으므로 재로그인 필요 조건도 보고한다. Redis Lua 오류는 이전 쓰기를 자동 롤백하지 않으므로 OOM 이후 상태도 조사한다.

장애는 별도 테스트 백엔드·Redis에만 주입한다. 네트워크 프록시로 지연·단절·응답 차단을 재현하고
TTL 단축은 테스트 데이터에만 적용한다. 정상과 장애 부하는 별도 실행하며 예상 401·403·503을 정상 부하 오류율과 구분한다.
잘못된 200·재사용 성공·폐기 family 재활성화는 한 건도 허용하지 않는다. 장애 해제 후 자원·연결 회복과
독립 정상 세션의 갱신 성공까지 확인한다. 이 항목의 실제 실행 결과는 위 보고서에서 확인한다.

상태: **Redis 직접 부하·Refresh API 검증 완료**. MySQL 직접 부하와 별도로 수행했다.
Redis는 캐시가 아니라 Refresh 상태 저장소이므로 GET/SET 수치와 인증 흐름을 구분한다.

## 격리와 도구

전용 redis-bench 컨테이너를 새로 사용한다. Redis 7.4.11·CPU/메모리·maxmemory=128MiB·noeviction·비영속 설정을 현재 인증 Redis와 맞춘다.
다른 logical DB 번호만 쓰는 방식은 메모리·퇴출 정책을 분리하지 못하므로 사용하지 않는다.
실제/개발/기존 테스트 로그인 상태에는 부하·FLUSHALL·키 삭제를 보내지 않는다. 합성 키와 토큰만 사용한다.
별도 exporter job과 cAdvisor service 레이블로 기존 Redis와 구분한다. 키 이름·토큰 값은 지표 레이블이나 보고서에 넣지 않는다.

| 시험 | 도구·방법 | 확인할 내용 |
| --- | --- | --- |
| 명령 기준 | 같은 Redis 버전의 redis-benchmark | PING, GET, SET, SETEX, payload 64B/1KiB/4KiB |
| 동시성 | clients 1→10→50→100→200, 단계별 준비 후 본측정 | OPS, p50/p95/p99, 오류·발생기 한계 |
| 파이프라인 | pipeline 1 기준 후 10·100 별도 시험 | 배치 처리량 이득. 명령 왕복 지연과 배치 지연을 동일시하지 않음 |
| Refresh 정상 흐름 | 앱의 실제 rotation Lua와 같은 계약을 사용하는 합성 family | 새 토큰·TTL·이전 토큰 소비·Lua 실행 시간 |
| 동시 재사용 | 같은 토큰에 의도적으로 동시 rotate | 단 하나의 성공·나머지 재사용 판정·family 폐기. 정상 처리량과 별도 |
| TTL 만료 | 짧은 TTL 합성 자료, 만료 전후 회전·조회 | 만료 토큰 거부·expired_keys·메모리 회수·만료 집중 시 지연 |
| 메모리 압박 | 키 공간을 일정 크기로 늘려 maxmemory 도달 | noeviction의 명령 OOM 오류·쓰기 실패·기존 상태 유지 |
| 회복 | 부하 감소와 TTL 만료 후 재시도 | 연결·지연·메모리 회복과 잘못된 성공 응답 여부 |

Refresh 시험은 동일한 소모된 토큰을 계속 호출해 빠른 실패만 측정하지 않는다.
측정 전에 각 작업자가 사용할 독립 family를 준비하고 성공·재사용·만료·오류 결과를 나눠 집계한다.
앱 API 통합 시험은 Redis 단독 Lua 시험 이후에 진행해 BCrypt·DB·HTTP 비용을 별도로 본다.

## 순서와 관측

1. redis-bench 격리 구성·더미 인증·관측 연결과 기능 확인.
2. pipeline 1·payload 고정의 낮은 동시성 기준 측정.
3. 동시성 증량·포화 근처 반복 측정. 새 단계 전 워밍업, 측정 구간은 최소 60초로 구분.
4. pipeline·payload 변화는 한 변수씩 바꿔 별도 실행.
5. 실제 Refresh Lua·재사용/만료 실패 경로·메모리 압박을 각기 실행.
6. 정상 조건 복구 후 지속 시험. 최초 탐색과 장시간 soak 결과를 구분.

Grafana는 Redis OPS·사용/최대 메모리·연결·거부·만료·퇴출·commandstats/Lua 지표와 컨테이너 CPU·메모리·네트워크를 함께 본다.
가능하면 Redis의 LATENCY HISTOGRAM을 명령별로 수집하되 benchmark 클라이언트의 왕복 지연과 구분한다.
비밀번호는 전용 env/비밀 파일에서 읽고 실제 도구 버전의 인증 전달 방식을 검증한 뒤 사용한다.

## 중단·판정

- 예기치 않은 인증/연결 오류·관측 상실·컨테이너 메모리 보호 한도 도달 시 증량 중단.
- 메모리 시험에서는 Redis maxmemory의 명령 오류는 예상 결과로 분리한다. 프로세스 OOM-kill까지 계속 채우지 않는다.
- 성능 합격 지연 수치는 아직 미확정이다. 낮은 오류율·완료 처리량·지연·보안 계약을 함께 보고 판단한다.
- 발생기 CPU/네트워크 포화는 Redis 최대 용량으로 선언하지 않는다.
- 결과에는 버전·자원·정책·명령·키 수·TTL·값 크기·동시성·pipeline·시각·오류 유형·회복 상태를 기록한다.

완료 조건은 단순 OPS 숫자뿐 아니라 실제 Refresh 원자성·실패 처리·만료/메모리 부족 시 정합성을 증명하는 것이다.
RedisInsight는 개별 키·TTL 조사용 보조 도구이며 부하 기록은 Prometheus/Grafana와 로컬 결과에 보존한다.
