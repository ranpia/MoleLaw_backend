# 실제 임베딩 생성과 초기 벡터 적재

`legal-perf-v1`의 질문 32개와 1,000개 코퍼스를 실제 KURE-v1로 생성하는 순차 작업이다.
[데이터셋](rag-dataset.md)과 [구성요소 관측](rag-monitoring.md)을 먼저 준비한다.
이번 단계는 색인 준비와 연결 확인이며 동시 사용자 한계·전체 RAG·AI 답변 생성 시험은 아니다.

## 실행 순서

```powershell
.\scripts\load-testing\generate-rag-embeddings.ps1
.\scripts\load-testing\index-rag-data.ps1
```

1. 데이터셋 파일·해시·질문 후보 참조를 검증한다.
2. 질문 1개와 법령 4종의 조문을 각각 단독으로 생성해 차원·유한 값·정규화를 확인한다.
3. 질문 32개와 코퍼스 1,000개를 요청당 8개씩, 한 번에 한 요청으로 생성한다.
4. 저장한 벡터 파일을 다시 읽어 모든 입력 ID·텍스트 해시·토큰 수와 1,024차원·unit norm을 검증한다.
5. 검증된 결과만 별도의 Qdrant 컬렉션에 적재하고 자기 벡터 조회 및 질문 검색을 확인한다.

512토큰 이하 입력만 사용한다. 길이 시험용 2,048/4,096토큰 자료와 8,193토큰 한도 초과 자료는
이번 생성에 섞지 않는다. 서버는 CPU·float32·4스레드, 내부 인코더 batch_size=16이며,
클라이언트 요청 batch는 8개로 구분한다. 고정 모델 revision은 데이터셋 잠금 파일과 대조한다.

## 보존과 중단·재개

출력은 Git 제외 `build/rag-dataset/legal-perf-v1/embeddings-v1/`에 둔다.

| 파일 | 내용 |
| --- | --- |
| `identity.json` | 데이터/모델 revision·입력 파일 해시·실행 설정 |
| `smoke.json` | 첫 단독 입력들의 토큰 수·요청 시간·정규화 확인 |
| `queries.jsonl`, `corpus.jsonl` | 입력 ID·텍스트 해시·토큰 수·벡터·norm |
| `batches.jsonl` | 배치별 종류·위치·개수·총 토큰·HTTP 소요 시간·완료 시각 |
| `progress.json` | 가장 최근에 저장 완료한 위치 |
| `result.json` | 전체 완료 시 파일 해시·행 수·실행 시간·관측 기록 |

벡터는 응답의 개수·유한 숫자·차원·norm을 확인한 뒤 배치별로 flush/fsync한다.
중단 후 같은 명령은 저장된 순서·입력 해시·벡터를 검사하고 남은 입력부터 재개한다.
마지막 줄이 손상됐거나 설정이 다르면 자동 삭제/덮어쓰기하지 않고 중단한다.
이미 완료된 결과는 해시·벡터 검증 후 재사용하며 추론을 반복하거나 최초 결과를 덮어쓰지 않는다.

모델 UP/준비와 메모리 working set을 확인하며 요청 timeout은 120초, 실행당 시간 한도는 20분이다.
자원 보호와 시간 한도는 모든 장애를 보장하는 장치가 아니다. 요청 실패 시 자동 재시도하지 않는다.
벡터 생성은 순수 추론이므로 유효하게 저장된 이전 배치를 보존해 이어갈 수 있다.

## Qdrant의 격리 경계

대상은 테스트 Compose의 `qdrant`와 고정 컬렉션 `molelaw_perf_legal_v1_kure_1024`뿐이다.
기존 애플리케이션 컬렉션이나 MySQL 법령 원문/색인 테이블을 변경하지 않는다.
차원 1,024·Cosine과 데이터셋/모델/코퍼스/벡터 해시 metadata가 모두 일치해야 재사용한다.
기존 이름의 컬렉션이 다른 자료이면 덮어쓰지 않는다.

각 청크의 의미 있는 문자열 ID를 UUIDv5로 매핑하고 64개씩 wait=true로 적재한다.
payload에는 출처·조문·법령 버전·원문·텍스트 해시·토큰 수를 기록한다.
전체 point 수 1,000개와 자기 벡터 3개의 ID/코사인 보존을 확인한 뒤 질문 32개에 top-5 검색을 실행한다.
조회 결과는 `qdrant-result.json`에 저장한다.

질문의 후보 조문 포함 여부는 진단용이다. 후보 라벨은 전문가 검수가 없으므로 이를 검색 정확도로 발표하지 않는다.
범위 밖 질문도 최근접 이웃을 반환할 수 있으며 자동으로 빈 결과를 기대하지 않는다.
1,000개에서의 순차 조회는 대규모 ANN 처리량 검증이 아니다. `indexed_vectors_count`도 함께 기록한다.

혼합 길이 8개는 패딩 때문에 짧은 입력만 8개인 경우보다 느릴 수 있다. 전체 색인 생성 시간과 짧은 질문의
응답 시간을 구분한다. 다음 성능 단계에서 길이·batch·동시성을 각각 고정해 비교한다.

## 2026-10-29 실행 결과

고정 데이터셋·CPU float32·4스레드에서 단독 smoke 5건을 거쳐 질문 32개와 코퍼스 1,000개를 모두 생성했다.
총 실행 시간은 **977.238초(약 16분 17초)**였다. 모든 벡터의 출처 해시·개수·1,024차원·유한 값·norm을
파일에서 재검증했고 완료 명령 재실행도 추론 없이 같은 파일을 검증·재사용했다.

| 구간 | 입력 수 | 요청 수 | HTTP 시간 합 | 배치 p95 | 가장 긴 배치 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 질문 일괄 생성 | 32 | 4 | 2.592초 | 0.839초 | 0.839초 |
| 코퍼스 생성 | 1,000 | 125 | 966.173초 | 16.921초 | 26.088초 |

표의 p95는 **요청당 최대 8개 입력인 배치 전체의 HTTP 지연**이다. 개별 질문 지연이나 동시 사용자 RPS가 아니다.
먼저 보낸 단독 질문은 30토큰·1.026초였고, 법령별 단독 조문은 41/72/222/147토큰에서
각 0.446/0.428/1.348/0.701초였다. 표본이 적어 안정적인 SLO나 최대 성능으로 사용하지 않는다.

임베딩 500/503 카운터는 0이었다. 생성 구간에서 KURE 서비스의 메모리 working-set/제한 최대 비율은
약 26.3%였고 CPU는 대체로 4코어 한도를 사용했다. 최초 생성 도구는 KURE one-off로 실행돼
자원 그래프에 작은 도구 프로세스도 같은 서비스 이름으로 포함됐다. 이후 재사용/검증·적재 도구는
별도 rag-data 서비스로 분리했고 메모리 보호 쿼리는 대상의 최대 비율을 사용한다.

벡터 파일 크기는 질문 약 0.70MB, 코퍼스 약 21.89MB(JSON 표현)이며 Git에 포함하지 않았다.
적재와 35개 조회(자기 확인 3건+질문 32건)의 작업 시간은 약 1.634초였다. point 수는 정확히 1,000개,
`indexed_vectors_count=0`으로 이 규모에서는 ANN/HNSW 인덱스 성능 결과라고 표시하지 않는다.
전체 백엔드 RAG·AI 답변 생성·긴 입력/동시 부하는 실행하지 않았다.

현재 공유 추론 게이트와 5초 대기 한도에서 긴 색인 배치가 짧은 질문과 동시에 들어올 때의 영향은
후속 시험 대상이다. 이번 생성은 순차 처리이므로 그 상황의 오류율을 확인한 것으로 해석하지 않는다.
