# Redis 직접 부하와 Refresh API 검증

2026-10-29 중지했던 시험을 재개했다. 계획은 [Redis 시험 계획](redis-performance-plan.md),
어제 완료한 SET과 중지 지점은 [중지 기록](redis-checkpoint.md)에 보존한다.

## 실행

```powershell
.\scripts\load-testing\run-redis-capacity.ps1 -ResumeFrom redis-20261028T082541Z
# Redis 직접 시험 완료 후에만 실행
.\scripts\load-testing\run-refresh-capacity.ps1
# 단일 발생기의 CPU 경고가 있으면 4프로세스 확인
.\scripts\load-testing\run-refresh-distributed.ps1
```

재개 실행은 기존 SET 1/10/50/100/200 연결의 완료 결과를 검증해 출처 run ID와 함께 가져온다.
원본 파일을 덮어쓰지 않는다. 다른 날짜의 결과를 새로 측정한 것으로 표시하지 않는다.
전용 Redis가 비어 있어야 실행하며 앱 Redis의 키를 삭제하지 않는다.
새 직접 시험 전에 이미 벤치 데이터가 있으면 refresh-backend를 중지하고 redis-bench만 재생성한다.
이는 합성 벤치 상태를 초기화하며 기존 redis 서비스나 MySQL 볼륨은 초기화하지 않는다.

```powershell
docker compose --env-file docker/loadtest/.env -f docker/loadtest/compose.yml --profile refreshbench stop refresh-backend
docker compose --env-file docker/loadtest/.env -f docker/loadtest/compose.yml --profile redisbench up -d --force-recreate redis-bench
```

네이티브 도구는 Redis 7.4.11의 redis-benchmark다. 비밀번호를 프로세스 인자에 노출하지 않기 위해
호스트 포트가 없는 전용 Redis에만 named ACL user `loadbench`를 사용한다. 이 계정은 비밀번호 없이
bench:*에 GET/SET/SETEX, PING/SELECT와 도구 초기화용 CONFIG GET·CLIENT SETNAME/SETINFO를 허용한다.
default 계정은 별도 비밀번호를 유지한다. 기본 명령 측정이 끝나면 loadbench를 비활성화한다.

명령별 요청 수를 짧게 보정하고 지속 샘플은 최소 60초를 확보한다. 60초보다 짧으면 재보정하며
시도별 CSV를 보존한다. p95/p99는 완료된 개별 샘플의 네이티브 통계다.
값 크기·pipeline 비교는 짧은 탐색으로 구분한다. pipeline 지연은 단일 요청 왕복 지연으로 해석하지 않는다.

GET은 준비된 키 10,000개를 사용해 미스 조회만 반복하지 않는다. Lua 부하는 실제 원본 스크립트를
읽기 전용으로 마운트하며 서로 다른 family를 사용한다. 회전마다 64자 합성 해시를 전달하고
100회마다 새 family를 준비한다. 처리량에는 family 준비 비용이 포함되지만 지연은 EVALSHA 왕복만 측정한다.
지연 히스토그램은 0.1ms 구간의 상한값이다. 기능 검사의 짧은 합성 문자열과 지속 부하를 구분한다.

Redis UP·컨테이너 메모리를 5초마다 확인하며 관측 누락 3회 또는 메모리 한도의 90% 초과 3회면 중단한다.
명령 OOM은 maxmemory 정책 검증의 예상 오류이며 프로세스 OOM-kill과 구분한다.
원본과 요약은 Git 제외 `build/redis-loadtest-runs/`에 저장한다.

## 실제 API 환경과 판정

기존 백엔드를 변경하지 않고 `refresh-backend`를 별도로 실행한다. 같은 합성 사용자 DB를 쓰지만
Redis는 redis-bench로 분리한다. Toxiproxy는 이 백엔드의 Redis·MySQL 경로와 응답 유실용 HTTP 경로에만 적용한다.
프록시 관리 API와 시험 백엔드의 호스트 포트는 공개하지 않는다.

Locust는 CSRF 조회와 로그인을 준비 단계에서 수행한다. 사용자별 쿠키 저장소와 family를 유지하고
응답의 새 Refresh로 다음 요청을 보낸다. 20명까지 서로 다른 계정, 50/100명은 계정 20개에 분산한다.
같은 계정 20개 family도 따로 측정해 사용자 행 잠금에 따른 직렬화를 비교한다.
생각 시간은 0.05초이며 실제 사람의 갱신 간격을 재현하는 수치는 아니다.

워밍업과 측정 사이에는 요청을 비운 뒤 통계를 초기화한다. 측정 종료 후 이미 시작한 요청의 완료를 기다린다.
요약 RPS는 드레인 완료 수를 측정 시간으로 나눈 근사치로 표시한다. 정상 부하의 예상하지 않은 실패는 즉시 중단한다.
예상 401·403·503·DB 장애 500은 별도 기능·장애 검사로 분리하며 정상 부하 오류율에 합치지 않는다.
HTTP 코드와 함께 쿠키 발급, family 상태, 다음 갱신 성공·거부, 장애 해제 후 회복을 확인한다.

Redis 지연으로 503이 반환돼도 명령이 나중에 실행될 가능성이 있어 결과 상태를 재조회한다.
회전 후 응답 유실을 재현하면 이전 토큰의 재시도가 재사용 탐지와 family 폐기를 유발하는지 확인한다.

Redis 단독 시험과 API 시험은 동시에 실행하지 않는다. 결과는 해당 자원·데이터·시나리오에만 유효하다.
프록시 설정은 [Toxiproxy 공식 문서](https://github.com/Shopify/toxiproxy)를 따른다.

실행 ID `redis-20261029T000953Z`. SET 기본 동시성 5개 결과는 10월 28일 실행에서 가져왔고
아래 항목은 재개 후 새로 측정했다. 모든 값은 Redis 직접 요청이며 HTTP RPS와 다르다.

| 명령 | 연결 | 값 크기 | pipeline | OPS | p95 ms | 구분 |

| PING | 50 | 해당 없음 | 1 | 43,446 | 0.511 | 60초 이상 |
| GET | 50 | 1KiB | 1 | 40,556 | 0.575 | 60초 이상 |

pipeline 100이 10보다 빠르지 않았고 지연은 커졌다. 이 조건에서 큰 배치가 항상 유리하다는 결론은 낼 수 없다.
Redis CPU 0.5개 한도에서 관측했으며 같은 호스트의 발생기·관측 서비스 영향도 포함한다.

Lua 연결 1개는 약 4,869회전/초·p95 상한 0.3ms, 10개는 약 8,901회전/초·p95 상한 1.2ms였다.
Python의 단일 이벤트 루프가 한 코어 가까이 사용되는 구간을 관측했다. 컨테이너 CPU 상한 3개에
도달하지 않았어도 단일 루프가 발생기 한계가 될 수 있으므로 Lua 결과를 Redis 최대 성능으로 주장하지 않는다.

Lua 50개 연결은 약 9,478회전/초·p95 상한 5.8ms였고, 세 단계 모두 회전 오류는 0건이었다.
메모리 검사는 `redis-20261029T001930Z`에서 완료했다. 완료된 명령·Lua 결과는 이전 실행의 출처를 유지해 재사용했다.
1MiB 값 89개 이후 큰 쓰기가 거부됐고, 256B 값 5,216개로 남은 공간을 채운 뒤 회전도 OOM으로 거부됐다.
이때 used_memory=134,221,200B, maxmemory=134,217,728B, family 변경 없음·evicted_keys=0을 확인했다.
TTL 만료 후 메모리는 약 15MiB로 내려갔고 원래 유효 토큰의 회전이 다시 성공했다.

최초 메모리 검사는 큰 SET 거부를 작은 Lua도 거부되는 상태로 가정해 중단됐다. 그때 회전은 정상 성공했다.
애플리케이션 오류로 분류하지 않았으며, 작은 값까지 채우도록 검사 조건을 수정한 뒤 별도 실행에서 재검증했다.
`redis-20261029T001930Z/result.json`이 전체 Redis 직접 시험 완료 기록이다.

## 실제 Refresh API 탐색

`refresh-20261029T002031Z`에서 원본 이미지의 실제 HTTP 요청을 보냈다.
단일 Locust 프로세스의 결과이며 50/100 세션에서 발생기 CPU 경고가 발생해 최대 API 용량으로 해석하지 않는다.
초기 1명 단계에는 JVM 예열 영향도 있다. 생각 시간은 0.05초다.

| 세션 수 | 계정 분산 | 약식 RPS | p95 ms | 실패 |
| --- | --- | ---: | ---: | ---: |
| 1 | 1계정 | 15.7 | 29 | 0 |
| 10 | 10계정 | 174.1 | 10 | 0 |
| 20 | 20계정 | 345.4 | 12 | 0 |
| 50 | 20계정 | 633.7 | 45 | 0 |
| 100 | 20계정 | 644.0 | 120 | 0 |
| 20 | 같은 1계정 | 349.0 | 12 | 0 |

같은 계정과 분산 계정 20개는 이번 생각 시간·부하 범위에서 큰 차이가 없었다.
사용자 행 잠금이 모든 부하에서 무시 가능하다는 뜻은 아니다.
실제 API에서도 동시 같은 토큰 16요청은 성공 1·재사용 탐지 1·폐기 거부 14였고 다른 family는 유지됐다.
CSRF 거부 후 정상 갱신, 만료·변조·누락·로그아웃된 토큰 거부와 절대 만료 유지도 통과했다.

100 세션의 단일 발생기 120초 확인은 약 659.7 RPS·p95 110ms·실패 0이었다. 발생기 CPU 경고가 있어
이 수치를 최종 한계로 사용하지 않고, 별도 다중 프로세스·동기화된 120초 확인을 추가했다.
`run-refresh-distributed.ps1`은 워밍업 뒤 시작 장벽을 공유하고 각 프로세스의 지연 히스토그램을 합쳐
p95/p99를 계산한다. 각 프로세스의 p95를 평균하지 않는다.

2프로세스·각 50세션의 `refresh-20261029T003349Z`는 약 834.1 RPS·p95 130ms·p99 170ms·실패 0,
발생기 CPU 경고 없음이었다. 다만 Toxiproxy CPU 0.5개 제한에서 throttled periods 비율이 약 98%로
관측돼 프록시의 제한이 포함된 결과로 분류했다. 시험 도구인 프록시만 CPU 2개로 높이고
백엔드 CPU 2개·MySQL CPU 1개·Redis CPU 0.5개는 유지한 채 4프로세스·각 25세션 확인을 추가했다.
최종 4프로세스는 계정 20개에 각각 5세션을 분산한다.

최종 `refresh-20261029T003635Z`는 **100세션·120초·105,980회 완료·약 883.1 RPS·p95 160ms·p99 280ms·실패 0**이었다.
4개 발생기 모두 CPU 경고가 없었고 지연 히스토그램의 건수 합과 완료 수 105,980건이 일치했다.
30초 CPU rate의 측정 구간 최고값은 백엔드 1.970코어, 발생기 합 2.648코어,
프록시 0.624코어, MySQL 0.608코어, Redis 0.126코어였다. 프록시의 제한 대기는 0을 확인했다.
이 조건에서는 백엔드 CPU 2개 한도에 접근했다. Redis 자체의 처리 한계로 해석하지 않는다.
2분 검증이며 운영 최대 수용량이나 장시간 안정성을 보장하는 결과는 아니다.

종료 후 모든 부하 발생기와 관측 스크립트는 종료했다. 앱·DB·Redis·Grafana 등 테스트 환경은 유지한다.
앱 데이터는 사용자 20·방 200·메시지 4,000·스냅샷 200개로 유지됐다. 기존 인증 Redis의 데이터에
직접 부하나 키 삭제를 수행하지 않았다. 원본 CSV·JSON·컨테이너 관측 파일은 build 아래에만 보존한다.

## 오류와 복구 결과

완료 기록: `refresh-20261029T003246Z/result.json`. 정상 부하 7개 단계는 002031Z의 완료 결과를 출처와 함께
재사용했고, 기능·장애 검사 10개를 재검증했다. 원본 이미지·Redis Lua·애플리케이션 Java 코드는 변경하지 않았다.

| 장애 | 실제 결과 | 상태·복구 |
| --- | --- | --- |
| Redis 쓰기 OOM | 503 AUTH_STORE_UNAVAILABLE, 신규 인증 쿠키 없음 | family 유지, TTL 이후 원래 토큰 갱신 성공 |
| Redis 연결 단절 | 503 AUTH_STORE_UNAVAILABLE | 경로 복구 후 갱신 성공 |
| Redis upstream 3초 지연 | 2초 command timeout 후 503 | 늦게 회전이 실행됨. 이전 토큰 재시도는 401 REFRESH_TOKEN_REUSED |
| 서버 회전 후 HTTP 응답 유실 | 호출자는 ReadTimeout | 이전 토큰 재시도는 401 REFRESH_TOKEN_REUSED, family 폐기 |
| DB 경로 단절 | 500 INTERNAL_SERVER_ERROR | 회전 전 사용자 조회 실패, family 유지, 경로 복구 후 갱신 성공 |

**503은 회전이 실행되지 않았다는 보장이 아니다.** 현재 fail-closed 계약에서는 Redis 지연·응답 유실 후
이전 토큰의 자동 재시도가 세션 폐기로 이어질 수 있다. 클라이언트의 무조건 재시도 정책에 이 동작을 반영해야 한다.
기존 Access는 별도 만료 전까지 유효할 수 있으며, 이 시험은 Refresh의 폐기·재발급 상태를 검증했다.

API OOM 검사는 큰 값과 256B 작은 값으로 채웠다. 최종 재검증은 1MiB 값 77개·작은 값 949개 후
503과 family 유지, TTL 이후 회복을 확인했다. 수치는 이전 시험의 키·메모리 잔여 상태에 따라 달라질 수 있다.
검사 구현은 지속 연결을 유지하고 HGETALL을 필드별 맵으로 비교한다. 초기 검사의 연결 버퍼 해제와
해시 반환 순서 가정을 수정했으며, 중단된 실행을 전체 성공으로 표시하지 않는다.
