# MySQL 직접 부하 시험

API를 거치지 않고 sysbench로 MySQL의 읽기·읽기/쓰기·락 경합을 구분한다.
애플리케이션의 쿼리나 API 처리량을 재현하는 시험은 아니다. Redis와 Refresh API는
[별도 계획](redis-performance-plan.md)에 따른다.

## 실행과 데이터

전용 Compose의 MySQL·Prometheus·mysql-exporter·cAdvisor가 실행 중이어야 한다.
기존 개발 DB 대신 `molelaw-loadtest` 프로젝트의 MySQL만 사용한다.

```powershell
.\scripts\load-testing\prepare-sysbench.ps1
docker compose --env-file docker/loadtest/.env -f docker/loadtest/compose.yml --profile dbbench build sysbench
.\scripts\load-testing\run-db-capacity.ps1
```

준비 스크립트는 비밀값을 Git 제외 `.env`에 저장하고 `molelaw_sysbench` 스키마와 해당 스키마에만
권한이 있는 전용 계정을 만든다. 실행 컨테이너 내부의 임시 설정 파일로 인증하며 비밀번호를 명령 인자에 넣지 않는다.
sysbench 1.0.20은 워밍업 옵션을 지원하지 않아 워밍업과 본 측정을 별도 프로세스로 실행한다.

4개 테이블에 각 50만 행, 총 200만 행을 생성한다. 기존 동일 데이터는 행 수 확인 후 재사용하며
부분 데이터나 다른 행 수는 자동 삭제하지 않고 중단한다. 앱 스키마·로그인 데이터는 변경하지 않는다.
혼합 시험은 이 전용 데이터만 갱신한다. 시험 후에도 데이터는 보존된다.

| 단계 | 동시 연결 | 워밍업 / 본 측정 |
| --- | --- | --- |
| OLTP 읽기 | 1, 4, 8, 16, 32 | 10초 / 30초 |
| 읽기 확인 | 탐색 최고 TPS의 95% 이상인 가장 작은 연결 수 | 15초 / 120초 |
| OLTP 읽기·쓰기 | 1, 4, 8, 16, 32 | 10초 / 30초 |
| 혼합 확인 | 탐색 최고 TPS의 95% 이상인 가장 작은 연결 수 | 15초 / 120초 |
| 단일 행 경합 | 1, 8, 32 | 10초 / 30초 |

읽기는 트랜잭션당 14개 조회와 BEGIN/COMMIT을 포함한 16개 SQL이다. 혼합은 기본 OLTP 시나리오이고
단일 행 경합은 BEGIN → 동일 행 UPDATE → COMMIT이다. TPS는 트랜잭션 완료 수이며 HTTP RPS와 다르다.
데드락 1213은 sysbench 재시도 대상으로 지정하되 ignored errors에 기록한다. 다른 오류와 연결 재접속도 확인한다.

5초마다 MySQL UP과 메모리를 확인한다. 관측 누락 3회 또는 메모리 working set이 한도의 92%를
3회 연속 넘으면 중단한다. 각 프로세스 실행 시간도 제한한다. 이 보호는 모든 장애를 자동 판정하지는 않는다.
연결 수 상한은 32이며 MySQL 전체 max_connections=60에서 앱·관측용 연결 여유를 남긴다.

원본 출력·요약·실제 DB 설정은 Git 제외 `build/db-loadtest-runs/db-<UTC>/`에 보존한다.
`result.json`이 있어야 전체 완료이며, 중간 `summary.json`만으로 전체 성공을 선언하지 않는다.
Grafana DB·컨테이너 대시보드와 함께 TPS·p95·오류·CPU·메모리·I/O를 읽는다.
버퍼 풀뿐 아니라 OS 페이지 캐시 영향도 있으므로 데이터 크기만 보고 디스크 성능이라고 단정하지 않는다.

## 2026-10-28 측정 환경

MySQL 8.4.11, CPU 1개·메모리 1.5GiB, InnoDB 버퍼 풀 512MiB,
max_connections=60, REPEATABLE-READ, innodb_flush_log_at_trx_commit=1,
sync_binlog=1, binlog 활성화, redo 용량 100MiB를 그대로 사용했다.
준비 직후 information_schema의 데이터·인덱스 추정 합은 약 265MiB였다.
이 통계는 근사치이고 버퍼 풀보다 작으므로 이번 시험은 디스크 한계를 검증하는 시험으로 해석하지 않는다.
발생기는 별도 컨테이너 CPU 3개·메모리 1GiB이며 MySQL과 같은 Docker Desktop 호스트를 공유한다.
버전·설정은 로컬 `dataset.json`에 함께 저장한다.

15개 측정 단계를 모두 완료했고 데드락 재시도·재접속은 각각 0건이었다. 최종 200만 행 검증을 통과했다.
측정 구간의 메모리 보호 샘플 최대값은 한도의 약 79.6%로 중단 기준을 넘지 않았다.
Prometheus 30초 CPU rate의 관측 최고값은 MySQL 약 1.003코어, 발생기 약 0.505코어였다.
발생기 CPU 상한 3개에는 여유가 있었으나 동일 호스트의 I/O·스케줄링 영향까지 배제한 것은 아니다.
앱 사용자 20·방 200·메시지 4,000·스냅샷 200개도 유지됐다. 부하 발생기·관측 스크립트는 종료하고
MySQL·관측 서비스와 벤치마크 데이터는 보존했다.

읽기는 CPU 1개 제한에서 연결 증가가 처리량 개선으로 이어지지 않았고 지연이 늘었다.
혼합은 32개까지 증가했으므로 전역 최대 성능을 찾았다고 주장하지 않는다.
단일 행 갱신은 직렬화로 연결을 늘려도 처리량보다 대기 시간이 크게 증가한다.
실제 Refresh API도 사용자 행을 잠그지만 SQL·Redis·HTTP 작업이 다르므로 이 TPS를 API 용량으로 환산하지 않는다.

최초 실행 `db-20261028T075417Z`는 데이터 생성 후 미지원 warmup 옵션으로 첫 측정 전에 실패했다.
옵션 수정·이미지 재빌드 후 새 실행 ID로 전체 시험을 다시 시작했으며 실패 실행을 성공 결과에 합치지 않았다.
