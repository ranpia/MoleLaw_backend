# 문서·검증 작업 방법

이 문서는 문서를 관리하는 사람과 에이전트의 작업 방법을 다룬다. 폴더별 README는 해당 기능의 목적·현재 구현·핵심 제한과 상세 문서 링크를 요약한다. 저장소 전체 개발 규칙은 [AGENTS.md](../AGENTS.md)를 따른다.

## 문서 배치와 갱신

- 현재 기능은 해당 기능 폴더, 추가 작업은 `plans/`, 정책 선택은 `decisions/`, 과거 기록은 `archive/`에 둔다.
- README에 작업 절차·도구 사용법·편집 규칙을 반복하지 않는다. 공통 방법은 이 문서, 개별 API/실행 계약은 해당 상세 문서로 연결한다.
- 커밋 이력과 현재 컨트롤러·서비스·DTO·설정·마이그레이션·테스트를 대조한다. 소스 구현, 실행 증거, 정책 결정, 미실행 계획을 구분한다.
- 검토일과 기준 커밋을 적는다. 2026-10-30 문서 대조 기준은 `b0b37d8`이며 [대조 기록](validation/documentation-review.md)에 범위를 남겼다.
- 과거 실측 수치·실패·중지 기록은 당시 조건과 함께 보존한다. 코드 수정이나 재실행 성공을 이유로 이전 실패를 지우지 않는다.
- 문서 이동·추가 시 README 목차, 상대 링크, 관련 코드·스크립트의 경로를 함께 갱신한다. 예제는 [스트림 JS](examples/initial-answer-stream.js), 실행 환경은 [Docker](../docker/README.md)를 따른다.
- 문서 정적 검증은 로컬 링크·UTF-8·제어문자·`git diff --check`를 포함한다. 외부 URL·내부 앵커 검사 여부와 실제 테스트 재실행 여부를 따로 기록한다.

## 검증 결과의 기록

2026-10-28~29의 성능·실제 모델 시험 묶음은 [1차 테스트](testing/first-round.md)로 명명한다. 코드 리팩토링 후 회귀와 성능 재측정은 별도 날짜·코드·환경으로 기록하며 기존 집계값을 덮어쓰지 않는다. 보일러플레이트 검사에서는 정확한 텍스트 반복과 의미상 비슷한 로직을 구분한다. 중복 횟수만으로 DTO·엔티티·보안 경계를 공통화하지 않는다.

모킹·HTTP 대역·실제 저장소·실제 모델을 분리해 날짜·명령·환경·성공/실패/건너뜀·남은 제한을 [검증 현황](validation/validation-status.md)에 남긴다. 과거 테스트 건수나 Git 병합 사실은 현재 회귀·배포 성공의 근거가 아니다. Git 제외 `build/` 자료의 존재·해시를 재확인하지 않았다면 보고서 집계만 인용했다고 표시한다.

기본 `test`는 외부 API·Docker가 필요한 tag를 제외한다. `answerStreamSimulationTest`는 HTTP 대역 스트림, `answerGenerationLiveTest`는 유료 opt-in 최종 생성, `ragPreparationContractTest`는 고정 색인 자료 계약을 별도로 확인한다. 세부 태스크와 실행 조건은 [검증·전달 계획](plans/delivery-validation.md)을 따른다.

CI는 dev push와 dev/main PR에서 `test bootJar`·`mysqlIntegrationTest`·`redisIntegrationTest`를 실행하고 실패 보고서를 7일 보존한다. 유료 모델·부하 시험은 기본 CI에 포함되지 않는다. 정의된 워크플로와 특정 실행의 성공을 구분한다.

## 계획·결정 기록

현재 모델·70점 기준·상위 2개는 평가 시작값이다. 다음 단계에 앞서 실제 계측과 실패 사례를 남긴다. 모델 확대·예산 증액·수집 증가가 계약 오류나 부족한 원문을 해결했다는 근거로 사용되지 않도록 원인을 확인한다.

사용자가 정책을 결정하면 날짜·선택·적용 범위·이유·연결 작업 ID를 [확정 결정](decisions/confirmed.md)에 기록한다. 구현 완료와 사용자 승인을 구분한다. 계획 문서는 실 API 재시도·배포·데이터 삭제의 포괄 승인이 아니다.

## 시각화 갱신

```powershell
node scripts/render-test-results.mjs
```

Node 기본 모듈만 사용한다. 명령은 Git에 저장된 테스트 보고서의 표를 읽어 `docs/testing/figures/`의 SVG와 `data.json`을 재생성하며 서버·DB·외부 API를 호출하지 않는다. 표 제목·열이 변경되면 [생성 스크립트](../scripts/render-test-results.mjs)의 매핑도 함께 수정한다.

1. 원본 문서의 날짜·실행 ID·단위·측정 창을 먼저 확인한다. 원시 로그를 재검증했는지 보고서 집계만 사용했는지 표시한다.
2. 처리량과 지연처럼 단위가 다른 지표는 별도 그래프로 표시한다. 성공 지연 옆에는 실패·503 거부·성공 표본 수도 제공한다.
3. 탐색과 지속 확인, 단일/다중 발생기, 실제 모델과 대역, 생성 단독과 전체 RAG를 구분한다. 조건이 다른 수치를 하나의 추세선으로 연결하지 않는다.
4. 범위값은 임의 중간값으로 바꾸지 않는다. 단계 progress 간격을 내부 trace나 전체 시간의 정확한 분해로 표시하지 않는다.
5. SVG 제목·축/단위·범례·출처·제한 문구와 계산값을 확인한다. 표본이 적으면 p95·최대 운영 수용량을 새로 계산하지 않는다.
6. 생성 결과와 [시각화 안내](testing/visual-results.md)를 함께 검토한다. 그림 추가 시 목차와 재현 가능한 데이터를 보존한다.

## 부하 시험 방법과 도구

아래는 기존 테스트 README의 개념·도구·실습·결과 해석 안내를 이관한 내용이다. 현재 완료 범위는 [테스트 요약](testing/README.md), 실행별 명령과 측정값은 각 상세 결과를 우선한다.


### 1. 무엇을 알아보려는가

기능 테스트는 “답변과 저장이 올바른가”, 부하 테스트는 “여러 사람이 동시에 사용해도 올바르게 처리되는가”를 확인한다.
첫 목표는 최대 사용자 수를 선언하는 것이 아니라, 느려지는 구간과 그때의 처리량을 찾는 것이다.
기존 JUnit·H2 테스트 통과는 실제 MySQL·모델 서버의 처리 용량을 의미하지 않는다.

| 용어 | 쉬운 설명 | 읽을 때 주의할 점 |
| --- | --- | --- |
| 가상 사용자(VU) | 도구가 흉내 내는 사용자 | 10명이 항상 초당 10번 요청한다는 뜻은 아니다 |
| 처리량(RPS) | 초당 처리한 HTTP 요청 수 | 시도·성공·실패를 나누고 완료 상담 수/분도 기록한다 |
| 지연 시간 | 요청 후 응답까지 걸린 시간 | 평균만 보면 일부 사용자의 긴 대기를 놓친다 |
| p95 | 측정값의 95%가 이 시간 이하 | 요청 100개라면 대략 느린 5개의 경계다 |
| 오류율 | 전체 시도 중 실패 비율 | 빠른 실패가 많으면 평균 시간이 짧아질 수도 있다 |
| 워밍업 | 모델·연결·캐시를 미리 준비하는 구간 | 측정 구간과 분리하고 최초 시작 지연도 따로 남긴다 |
| 포화 | 더 요청해도 성공 처리량은 늘지 않고 대기·오류가 증가하는 상태 | 부하 발생기 자체가 한계인지도 확인한다 |

### 2. 사용할 도구

현재 사용 중인 도구와 추가 검토 대상을 함께 정리한다. Locust·Micrometer·Prometheus/Grafana·sysbench·Postman 대역은 제공 중이며 OpenTelemetry·k6는 별도 도입 검토다.

| 도구 | 역할 | 도입 시점과 한계 |
| --- | --- | --- |
| Locust | Python으로 사용자별 인증·조회·Refresh 흐름을 실행하고 동시 사용자를 늘린다 | 주 HTTP 부하 발생기. 스트림 완료·오류·첫 답변은 별도 대역 검사·NDJSON probe와 구분한다 |
| Spring Boot Actuator + Micrometer | HTTP·JVM·커넥션 풀 등 백엔드 지표를 제공한다 | 의존성·loadtest 전용 관리 포트 구현. 별도 HTTP 테스트에서 지표·인증 경계를 검증 |
| Prometheus + Grafana | 지표를 일정 간격으로 수집하고 시간별 그래프로 비교한다 | 전용 Compose·MySQL/Redis exporter·cAdvisor·모델 게이트웨이 지표 제공. 과거 미수집 구간을 소급 생성하지 않는다 |
| MySQL Performance Schema·slow query log | 실제 느린 SQL·락 대기를 조사한다 | DB 분석 단계. 수집 설정과 오버헤드를 기록하고 민감한 SQL 값을 공유하지 않는다 |
| sysbench | MySQL에 직접 읽기·쓰기 부하를 보내 기준 성능을 본다 | API 기준 측정 이후. 기본 OLTP 테이블 결과는 MoleLaw의 실제 쿼리 성능과 다르다 |
| OpenTelemetry 추적 | 요청 내부 단계의 시간과 외부 호출을 연결한다 | RAG 상세 계측 단계. 자동 추적만으로 검색·추론 내부 대기까지 모두 보이지 않으므로 사용자 정의 구간 필요 |
| Postman | 기존 API 계약·응답 검증과 외부 서비스 대역을 재사용한다 | 보조 도구. 기존 simulation은 기능 검증용이므로 지연·처리량·동시성을 별도로 검증한 뒤 사용 |
| k6 | 일정한 비율로 시나리오를 시작하는 부하 시험에 활용한다 | 후속 선택. 처음부터 Locust와 중복 운영하지 않는다 |

Locust의 기본 사용자 반복에서는 응답이 늦어지면 다음 요청도 늦어진다. 따라서 동시 사용자 시험 결과를 고정 RPS 보장으로 표현하지 않는다.
k6 arrival-rate도 시나리오 시작률이며 시나리오당 요청 수가 여러 개라면 HTTP RPS와 같지 않다.

### 3. 처음 실습할 순서

1. [Docker 실행 안내](../docker/README.md)로 구성 요소의 역할부터 확인한다. 기존 서버·데이터를 그대로 부하 시험에 사용하지 않는다.
2. 테스트 전용 계정·DB·Redis 공간·Qdrant 컬렉션과 대상 주소를 준비한다. 공유 추론 서버라면 다른 작업과의 자원 경쟁도 확인한다.
3. 실제 로그인 방식으로 테스트용 Access 쿠키를 준비하고 `/api/auth/csrf` JSON 토큰을 받는다. POST에는 `X-XSRF-TOKEN` 헤더를 붙인다. 사용자마다 쿠키 저장소와 방 ID를 분리한다.
4. 읽기 API 하나를 수동으로 한 번 호출해 정상 응답을 확인한다. OAuth 공급자를 반복 호출하는 부하는 만들지 않는다.
5. Locust 가상 사용자 1명으로 같은 흐름을 실행한다. 응답 내용까지 맞는지 확인한다.
6. 짧은 소규모 부하를 실행하며 성공 수·오류·p95와 서버 자원을 함께 본다. 처음에는 조회 API부터 시작한다.
7. 결과를 저장한 뒤에만 RAG와 동시 사용자 수를 늘린다. 상세 수치와 중단 조건은 계획 문서를 따른다.

실행 도구는 `scripts/load-testing/`에 제공한다. 준비 조건은 [전용 Docker 환경](../docker/loadtest/README.md), 첫 실행은 [사용자 1명 실습](testing/first-load-test.md)을 따른다. 유료 모델 실행은 별도 opt-in이며 일반 조회 명령에 포함되지 않는다.
기존 인증·CSRF·프로필 정책을 유지하며 테스트 편의를 위한 공개 로그인 우회 API는 만들지 않는다.

### 4. 결과를 읽는 예

가령 사용자를 2명에서 4명으로 늘렸는데 성공 상담 수/분은 비슷하고 p95와 모델 대기 시간이 증가했다면 모델 구간의 포화를 의심한다.
이때 Qdrant 지연과 MySQL 대기가 그대로인지 확인해 원인을 좁힌다. 이 예시는 실제 측정 결과가 아니다.

SSE/NDJSON은 HTTP 200 이후에도 실패할 수 있다. 첫 progress·heartbeat 수신을 답변 시작으로 세지 않고, 첫 `answer_delta`와 `completed`까지의 시간을 각각 측정한다.
`error`나 완료 전 연결 종료는 실패로 집계한다. 저장형 API는 완료 결과와 실제 저장도 표본 확인한다.
상세 계약은 [상담 스트림](chat/initial-answer-stream.md)을 따른다.
