# 최초 상담 예산 설계 검토

2026-10-24 사용자 요청에 따른 검토안이다. 연결 작업은 P03/P05, 금액·지연 상한 선택은 D01이다.
이 문서는 실행 한도를 늘리거나 비용 차단을 이미 구현했다는 의미가 아니다.

## 관측한 병목과 현재 한계

직전 요청은 약 220초 뒤 `PROCESSING_TIME / BUDGET_EXHAUSTED`로 종료했다.
충분성 판단 단계 네 번에 약 195초를 사용했고 법령 세 건·495청크의 저장 검증은 성공했다.
따라서 GPU 임베딩 속도보다 판단 반복과 늦은 응답 검사가 지배적인 문제였다.
법령 목록 리랭커를 60점/3개로 완화했지만 해당 요청은 조건별 후보가 한 건이어서
그 변경만으로 판단 반복이나 지연이 줄어든다고 볼 수 없다.

| 예산 | 현재 동작 | 빈틈 |
| --- | --- | --- |
| 일반 처리 시간 | collector 생성 시 3분. 호출 경계에서 검사 | HTTP 요청 전체가 아니며 이미 실행한 LLM 호출을 즉시 취소하지 못함 |
| 임베딩 시간 | 실행 누적 기본 900초, 대기 포함. 사용 시간을 일반 deadline에 가산 | 별도 제한은 있지만 사용자가 기다리는 전체 시간 상한은 아님 |
| 외부 호출 수 | 검색/수집 128, 임베딩/색인 각각 1024 | LLM API 호출 수·토큰 비용과 다른 척도 |
| 의사결정 반복 | round 0~4, 일반 안내 재검토와 계약 교정 가능 | 한 round 안의 본문 선택/판단/교정은 여러 LLM 호출이 될 수 있음 |
| 모델 HTTP | 공통 읽기 timeout 기본 120초 | 남은 실행 시간이 짧아도 긴 호출을 시작할 수 있음 |
| 역할 완료 토큰 | 호출별 max_completion_tokens | 여러 역할/재시도를 합친 요청당 비용 상한이 아님 |
| 조문 리랭크 | 후보 50, 대표 청크, 쌍 1024토큰, 추론 배치 2, HTTP 30초 | 단계/실행 누적 GPU 비용 계측과 독립 상한은 아직 없음 |

키워드 추출은 collector 이전이고 최종 답변 생성·DB 저장은 이후다.
따라서 현재 3분을 전체 상담 API timeout으로 안내하면 안 된다.
로컬 cross-encoder는 유료 OpenAI 토큰을 쓰지 않지만 GPU 대기·추론 시간과 처리량 예산을 사용한다.
이번 구현은 리랭크 HTTP를 기존 검색 호출 수와 일반 처리 시간에 포함한다.

## 제안: 시간·토큰·호출·GPU 네 종류를 분리

1. **전체 요청 deadline**: 키워드 추출부터 답변/저장까지 취소·마감의 부모 경계를 둔다.
   임베딩 제외 시간을 이 부모 deadline에 더하지 않는다. 단계별 시간은 자식 예산으로 별도 기록한다.
   시간 측정에는 단조 시계를 사용하고 실행 ID로 모든 단계의 시작/종료를 연결한다.
2. **호출 전 예약**: 최종 답변·저장 몫을 먼저 확보하고 남은 시간/토큰으로 추가 검색을 시작한다.
   HTTP timeout은 `min(단계 상한, 남은 부모 시간 - 필수 마무리 예약)`으로 제한한다.
   시간이 부족하면 새 호출을 하지 않는다. 경계 검사만으로 서버측 LLM 추론/과금 취소를 보장하지 않는다.
3. **실제 토큰 정산**: prompt/output/cache/reasoning usage를 구분한다.
   공급자의 reasoning tokens가 completion에 포함된 경우 이중 합산하지 않는다.
   가격표는 모델/버전별 외부 설정으로 관리한다. 성공·재시도·교정·빈 출력·실패도 같은 ledger에 기록한다.
   usage가 없으면 0으로 환급하지 않고 예약을 유지하거나 보수적으로 실패 정산한다.
4. **로컬 추론 제한**: 요청별 rerank 호출 수, 누적 후보 수/쌍 토큰 수, 대기/추론 시간을 기록한다.
   CPU/CUDA에 같은 수치를 강제하지 않고 실측 기반 운영 설정으로 둔다.
   GPU 모델 상주 메모리와 배치 peak는 프로세스 자원 한도로 관리하며 API 토큰 예산과 합치지 않는다.

금액·전체 지연·최종 답변 예약량은 D01 수치가 미정이므로 여기서 운영 정책으로 확정하지 않는다.
실측 전에 3분을 크게 늘리거나 모델을 자동 승격하는 방식으로 실패를 숨기지 않는다.

## 반복을 줄이는 기준

- 동일 query/필터/색인 세대/리랭커 revision의 후보 재정렬은 요청 안에서 재사용하는 방안을 검토한다.
  새 세대 적재 후에는 재검색/재정렬이 필요하므로 이전 결과를 그대로 재사용하지 않는다.
- 후보 ID 집합과 본문 읽기 결과가 변하지 않는 판단은 재호출 전에 차단한다.
  새 근거·새 질의·새 사실 중 무엇이 바뀌었는지 progress signature로 검증한다.
- 요청당 판단 호출 수를 round 수와 별도로 제한한다. 본문 선택 두 번과 계약 교정도 각각 센다.
- 답변 예약을 침범할 추가 검색은 수행하지 않는다. 이미 충분한 근거가 있다는 검증 없이
  비용 부족을 이유로 ANSWER_READY를 강제하거나 모델에 비용 결정을 맡기지 않는다.
- 예산 소진은 단계/이유/사용량을 구조화하고 성공 턴을 저장하지 않는다.
  불충분 응답/비동기 전환 UX는 D04와 별도 계약으로 다룬다.

## 구현 경계와 우선순위

1. 먼저 메타데이터 계측: 실행 ID·역할·model/revision·단계 지연·usage·재시도·캐시 적중·종료 이유.
   상담 원문·키·본문·원시 추론은 계측 로그에 넣지 않는다. 현재 local 판단 디버그의 원문 노출 범위도 별도 점검한다.
2. `common.ai`에 업무 독립적인 호출 예약/실제 usage 정산을 두고, `chat`이 전체 상담 예산을 소유한다.
   `law`는 전달받은 자식 예산으로 검색/ETL/리랭크를 수행한다. 전역 가변 singleton 카운터는 사용하지 않는다.
3. 요청 내 progress/재사용을 먼저 검증한 뒤 남은 시간에 맞춘 HTTP timeout과 취소를 연결한다.
4. D01 상한이 정해지면 요청/사용자 동시성의 원자적 예약을 적용한다.
   다중 인스턴스에서 프로세스별 semaphore만으로 전체 예산을 보장하지 않는다.
5. 정답 법령/조문 고정 셋에서 품질·p50/p95·LLM 실제 비용·GPU 사용량을 함께 비교한다.

## 필요한 회귀

가짜 시계와 공급자 대역으로 호출 전 부족·응답 중 만료·늦은 응답 거부·usage 누락·중복 정산·
실패 후 예약 유지·재시도 누적·답변 예약 보존·임베딩 제외와 부모 deadline 분리·동시 요청을 검증한다.
새 색인 세대에서 재정렬 캐시를 무효화하고, 예산 소진 시 미완료 색인/답변이 공개되지 않는지도 확인한다.
검토 단계에서는 전체 상담을 자동 재요청하거나 추가 유료 LLM 평가를 실행하지 않는다.
