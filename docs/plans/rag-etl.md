# RAG·ETL·대화 메모리 실행 계획

최신화: 2026-10-22. 구현과 운영 후속 계획을 구분한다. 동기 ETL 연결·완료 세대 공개·수동 재색인은 구현했다. 영속 작업 큐·자동 재개·물리 정리는 후속이다. [현재 실행 계약](../law-etl-local.md)을 우선하며 아래 과거 체크리스트는 전체 완료를 뜻하지 않는다.

## 확정한 경계

2026-10-21 Advisor·근거 연결: 후속 상담에 답변 전용 `MessageChatMemoryAdvisor`를 연결하고 방별 최초 근거 사본·ID를 별도로 전달한다. 최초·후속 인용 형식·ID 소속을 검증하고 성공 기록만 저장한다. [근거 계약](../room-evidence.md)과 [Client 경계](../role-chat-clients.md)를 따른다. 의미상 인용 충실성·법령 시행 버전·동시 요청 제어·수집 판단 반복은 미완료다.

2026-10-22 구현: 기존 벡터화 Tool을 Spring AI DocumentReader·DocumentTransformer·DocumentWriter로 분리했다. 최초 상담도 같은 경로를 사용한다. 완료 세대만 공개하고 실패 후 저장 원문 수동 재처리와 완료 세대 재사용을 지원한다. [설정·사용·제한](../law-vector-tools.md)을 따른다.

- MySQL은 업무 데이터·법령 원문·수집/색인 상태·대화·근거 스냅샷의 원본이다. Qdrant 색인은 재생성 가능한 검색 데이터다.
- 최초 질문은 기존 색인 검색 → 필요한 페이지/후보 수집 → ETL → 재검색 → 판례 검토 → 근거 확정 → 답변 순서다. 고정 2라운드 제한 대신 진행 여부와 실행 예산으로 종료한다.
- 후속 질문은 최초 근거 + Advisor 대화 + 현재 질문만 사용한다. 수집·ETL·법령/판례 조회·검색용 질의 변환을 실행하지 않는다. 새 쟁점은 새 상담방을 안내한다.
- Java 17·Spring Boot 3.5·Spring AI 1.0.9를 기준으로 API 호환성을 확인한다. 초기 ETL에 LLM 요약·키워드 보강을 추가하지 않는다.

2026-10-19 추가 계획: 근거 충분성 판단 → 기존 자료 재검색 또는 누락 법령 수집·벡터화 → 재검색의 구체적인 분기와 검증은 [법령 추가 수집·재검색 계획](adaptive-law-retrieval.md)을 따른다.

## 1. 법령 수집과 파서

### 법령·판례 API Tool 구성 (확정)

2026-10-13 구현: 네 내부 Tool·실행별 입력/ID/호출 예산 검증·원문 스냅샷 저장과 모킹/H2 테스트를 추가했다. 실제 API의 법령·판례 목록/상세 4회 호출과 응답 매핑도 확인했다(`openLawLiveTest`). [사용 계약과 남은 범위](../legal-api-tools.md)를 따른다. ETL·상담 연결·영속 페이지 재개·실제 저장소 통합과 API 예외 경로 실검증은 미완료이며 아래 전체 완료 조건을 충족한 것으로 표시하지 않는다.

기존 API 클라이언트·수집 서비스를 재사용하는 Tool 어댑터를 구현한다. Tool은 외부 조회 계약이고, 원문 저장·ETL·색인·근거 확정은 서버 서비스가 담당한다. 별도 MCP 서버는 초기 도입 범위에 포함하지 않는다.

| Tool 이름 | 입력 계약 | 반환 계약 |
| --- | --- | --- |
| `searchLaws` | 검색어·허용 필터·페이지·페이지 크기 | 법령ID/MST·법령명·확보한 시행일·페이지 정보·후보 목록 |
| `getLawDetail` | 서버가 확인한 MST | 원문 참조 ID·법령 버전·조문 메타데이터·수집 상태 |
| `searchCases` | 쟁점 검색어·허용 필터·페이지·페이지 크기 | 판례 ID·제목·사건번호 등 후보 메타데이터·페이지 정보 |
| `getCaseDetail` | 서버가 확인한 판례 ID | 원문 참조 ID·상세 확보 여부·출처 메타데이터 |

이름은 애플리케이션 내부 Tool 계약이며 외부 HTTP API 경로 변경을 의미하지 않는다. 필드의 실제 매핑은 기존 API 계약과 fixture로 확인한다.

- **실행 방식:** 초기에는 모델이 쟁점·검색 조건·후보를 구조화해 제안하고 서버 오케스트레이터가 Tool을 호출한다. 모델의 자동 tool-calling 루프는 초기 구현에 넣지 않는다. 기본 ETL/RAG는 모델 없이 같은 어댑터를 사용할 수 있다.
- **호출 권한:** 최초 질문 처리와 명시적인 사전 수집 작업에만 허용한다. 후속 ChatClient에는 Tool을 등록하지 않으며 서버 실행 계층에서도 후속 요청을 거절한다.
- **입력 검증:** 임의 URL·API 키·SQL을 받지 않는다. 허용 필터·길이·페이지 범위를 검사하고 상세 ID는 서버의 후보/수집 기록과 대조한다. 인증·방 ID·실행 예산은 서버 문맥으로 전달한다.
- **응답 크기:** 계획 모델에는 후보·참조 ID와 필요한 짧은 정보만 반환한다. 상세 원문은 MySQL에 보존하고 ETL·근거 검토에 필요한 범위만 전달한다. 전체 원문을 매 호출 반복 주입하지 않는다.
- **진행·오류:** 조건별 다음 페이지·중복 후보·API 호출을 추적한다. 정상 결과 없음·API 오류·예산 소진을 구분하고 조회 시각·출처·재시도 가능 여부를 기록한다. 새 페이지/다른 후보 탐색은 전체 예산 안에서 허용한다.

완료 조건: 네 Tool의 계약·외부 호출 모킹 테스트, 잘못된 ID/필터 거부, 다중 페이지·중복·예산 종료, 원문 참조 복원, 후속 요청의 Tool 실행 0회를 검증한다. Tool·자동 호출 관련 Spring AI API는 구현 시 고정 버전에서 확인한다.

### 수집·파서 작업

검색 Tool은 정확명/부분 후보 검색, 제목/본문, 법령ID·부처·종류·상태와 정렬·시행일/공포일 범위 옵션을 제공한다. `민법`에 `난민법`이 섞이는 경우 정확명 검사와 ID 재조회로 구분한다. [검색 옵션 계약](../legal-api-tools.md#검색-옵션-선택)을 따른다.

법령 API 장애 시 SerpApi로 공식 문서 후보를 찾는 방안은 [별도 검토](search-fallback.md)로 관리한다. 도입 미확정이며 정상 빈 결과/낮은 유사도와 장애를 구분하고, 채택하더라도 후속 검색 금지와 원문 검증 규칙을 유지한다.

- [ ] `LawSearchService`의 제목/본문·부처 fallback 순서와 MST 상세 조회를 fixture로 고정한 뒤 페이지 계약을 확장한다.
- [ ] 검색어·검색범위·부처·정렬·페이지 크기를 탐색 조건으로 저장한다. `page`·`display`·`totalCnt`와 처리 MST·마지막 성공 위치를 기록한다. 페이지 순서를 관련성 순위로 취급하지 않는다.
- [ ] 마지막/빈/반복 페이지·새 MST 없음은 해당 조건을 종료한다. 전체 시간·페이지·상세 조회·API 호출·임베딩 예산 소진은 **부분 수집**으로 표시하고 다른 조건의 진행 여부와 구분한다.
- [ ] 법령ID+MST로 후보·버전을 구분한다. 재개 시 앞 페이지를 재확인하고 중복 제거하여 목록 변동에 따른 누락을 점검한다.
- [ ] 실제 응답의 조·항·호·목, 단일 객체/배열, 가지번호·삭제 조문·부칙·시행일을 fixture로 검증한다. 기존 파서가 보존하지 못한 구조는 원문에서 복구하며, 파서 변경을 검색 기준선 변경과 분리한다.
- [ ] 현재 법령명+법령ID 재사용 경로가 다른 MST의 본문을 덮어쓰지 않도록 버전 식별자를 데이터 모델에 반영한다. 적용 기준일이 불명확하면 확인 질문 또는 답변 범위 제한으로 처리한다.
- [ ] API 오류·429·시간 초과는 제한적 재시도와 대기 정책으로 처리한다. 빈 정상 결과와 오류를 구분하고 응답 크기·동시 요청도 제한한다. 장시간 외부 호출을 DB 트랜잭션에서 분리한다.

완료 조건: 다중 페이지·총건수 변경·중복·반복 응답·중간 실패/재개를 재현하고, 새 페이지 자료가 최초 질문의 근거에 포함된다. 현행/연혁 버전 혼합과 파서 누락을 테스트로 탐지한다.

## 2. Reader → Transformer → Qdrant writer

수집 진입점은 구현된 법령 API Tool을 재사용한다. `searchLaws → getLawDetail → legal_source 원문 저장 → Reader → Transformer → Qdrant writer`로 연결하며, 별도의 법령 API 클라이언트나 수집 경로를 중복 구현하지 않는다. 서버가 페이지·후보·호출 예산을 관리하고 상세 Tool이 반환한 원문 참조 ID를 ETL에 전달한다. Reader는 해당 MySQL 원문을 읽으므로 저장된 자료의 재색인은 API 재호출 없이 수행한다.

**구현 상태:** 원문 참조 → Spring AI Document → 조문 청킹 → 로컬 임베딩 → Qdrant 적재를 연결했다. 실패 세대 비공개·완료 원문 재사용·저장 원문 재색인과 local 검증 API를 제공한다. 영속 실행/자동 복구는 미구현이다.

| 단계 | 구현 계약 |
| --- | --- |
| Reader | MySQL에 저장한 원문/수집 결과를 읽는다. 외부 API 없이 같은 Document를 재구성할 수 있어야 한다. |
| Transformer | 조문 경계를 보존하고 항·호·목 본문을 포함한다. 긴 조문은 Unicode 코드 포인트와 겹침 기준으로 분할한다. 법령명·조문 제목을 임베딩 입력에 포함하고 청크 본문과 전체 조문을 구분한다. |
| Writer | 기존 Python/Ollama 호환 HTTP 서버에서 임베딩을 한 번 생성하고 Qdrant REST로 적재한다. `QdrantVectorStore.add`는 호출하지 않는다. MySQL 세대 상태로 공개 여부를 관리하며 재시도는 새 세대의 전체 재처리다. |

- [ ] 메타데이터: `sourceType`, `lawId`, `mst`, `lawName`, `articleNumber`, `clauseNumber`, `itemPath`, `sourceUrl`, `collectedAt`, `contentHash`, `indexVersion`. 확보한 시행일·개정 정보와 누락 여부도 저장한다.
- [ ] 법령 버전·조문 경로·분할 순번·색인 버전으로 결정적 UUID를 만든다. MySQL에 ID 목록·본문 해시·모델·차원·작업 상태를 보관하고 변경 없는 문서의 임베딩을 생략한다.
- [ ] 삭제 조문/법령의 청크 제거와 본문 갱신을 검증한다. 모델·차원·청킹 정책 변경은 새 색인 버전으로 분리한다.
- [ ] `initializeSchema(false)`에 맞춰 컬렉션·차원·거리 함수·필터용 payload 인덱스를 명시적으로 준비하고 시작 시 불일치를 감지한다.
- [ ] 두 DB의 단일 트랜잭션을 가정하지 않는다. 부분 실패는 작업 ID와 청크 ID로 재실행한다. 준비 중인 색인은 검색에서 제외하고 검증 후 활성 버전을 전환하며 이전 버전으로 복구 가능하게 한다.
- [ ] 로컬 법령 목록/MST 지정 작업부터 검증한다. 서버 시작 시 전체 수집, 공개 관리 API, 스케줄링은 후속 범위다. 기존 MySQL 벡터 경로/테이블 제거는 전환 검증 후 별도 마이그레이션으로 수행한다.

완료 조건: 실제 Qdrant 색인·검색, 동일 입력 재실행, 변경/삭제, 부분 실패 복구, 버전 전환/복구가 통과한다. 검색에서 준비 중인 청크나 서로 다른 모델 벡터가 섞이지 않는다.

## 3. Ollama 임베딩 선정

CPU 테스트 이미지·독립 Compose·실행/지연 검사는 [Ollama 테스트 가이드](../../docker/ollama/README.md)를 사용한다. 이는 Spring 연동이나 법률 검색 품질 평가 완료를 의미하지 않는다.

아래는 기존 계획의 **비교 후보**이며 최종 선정이 아니다.

| 후보 | 기본 차원 | 시작 용도 |
| --- | --- | --- |
| `bge-m3` | 1,024 | 초기 기준선 |
| `qwen3-embedding:0.6b` | 1,024 | 소형 모델 비교 |
| `embeddinggemma` | 768 | 자원/품질 비교 |

- [ ] 시작안: `bge-m3`, 목표 상한 512토큰, 긴 조문 중첩 64토큰, 임베딩 동시성 1. 법령 10~30개·청크 1만 개 이하와 평가 질문 30~50개로 시작한다. 여유가 있으면 Qwen3 4B를 추가한다.
- [ ] 1차는 동일 청크 본문으로 모델을 비교한다. 2차는 선정 모델의 청크 256/512/1,024토큰과 중첩 32/64/128토큰을 비교한다. 짧은 조문은 분할하지 않는다.
- [ ] 법령명·상위 맥락·모델별 질문/문서 접두문을 포함한 실제 토큰 수와 입력 잘림을 확인한다. Spring AI 기본 토큰 계산을 모든 모델의 정확한 계산으로 간주하지 않는다. 초기 비교는 dense 검색으로 통일한다.
- [ ] 모델·태그/digest·차원·입력 형식·청킹 버전별 컬렉션을 분리한다. 질문과 문서 모델을 일치시키고, 차원이 같아도 다른 모델 벡터를 혼합하지 않는다.
- [ ] `topK=5/10` Recall@K·무관한 결과 비율·질문 지연·색인 시간·RAM/VRAM·벡터 용량을 기록한다. 모델별 점수 분포가 다르므로 공통 유사도 임계값으로 비교하지 않는다.
- [ ] 동일 하드웨어에서 한 모델씩 측정하고 초기 로딩/준비 후 지연을 분리한다. Ollama 메모리는 Docker·JVM 외 별도 예산이다. 선정 후 1.0.9 임베딩 연동·프로필을 구현하며 test는 Ollama 없이 실행한다.

모델 입력 계약은 [BGE-M3](https://huggingface.co/BAAI/bge-m3), [Qwen3](https://huggingface.co/Qwen/Qwen3-Embedding-0.6B), [EmbeddingGemma](https://huggingface.co/google/embeddinggemma-300m)의 공식 모델 카드를 기준으로 구현 시 다시 확인한다.

## 4. 검색·판례·근거 스냅샷

- [ ] 벡터 검색 → 메타데이터 필터 → 중복 제거 → 상위 조문 맥락 확장을 기준선으로 만든다. 법령명/조문번호 질의가 약하면 정확 일치·키워드 결합을 비교하고 별도 인프라는 필요성이 확인된 뒤 결정한다.
- [ ] 빈 색인·미수집·낮은 관련성·오래된 자료·차원 불일치를 구분한다. 유사도는 정확도나 충분성의 확률이 아니다. `topK`·임계값·컨텍스트 상한은 평가로 정한다.
- [ ] 동일 질문 임베딩은 요청 내 재사용한다. 같은 질의·필터·색인 상태를 반복하지 않되 새 색인 이후 재검색은 허용한다. 같은 법령의 다른 조문도 후보로 유지한다.
- [ ] 판례는 최초 질문에서 쟁점 기반으로 검색하고 후보 ID로 중복 제거한다. 본문 검색·참조법령 필터와 상세 API 계약을 확인한다. 목록 확장은 실행 예산으로 관리하며 상세 3건·채택 0~2건은 초기 제안이다.
- [ ] 판시사항·판결요지·참조조문·판례내용을 확보해 관련성을 확인한다. 제목/사건번호만으로 판결 내용의 근거를 만들지 않는다. 실패·결과 없음·관련성 탈락을 구분하고 판례 실패만으로 법령 답변을 막지 않는다.
- [ ] 상담방 최초 조회는 `미시작 → 진행 중 → 완료/실패`로 저장한다. 원자적 상태 전이·중복 요청 ID·중단 작업 복구를 정의한다. 정상 빈 결과와 예산 종료도 완료 결과로 보존하고 검색 미실행 오류와 구분한다.
- [ ] 근거 ID·조문 원문·검증 판례·원문 링크·법령 버전/시행일·조회 시점·부족 사유를 스냅샷에 저장한다. 답변 실패는 같은 근거로 재시도하고 완료된 근거를 새 색인으로 교체하지 않는다.
- [ ] 답변을 본문·근거 ID·부족 여부로 받고 ID 소속과 링크를 서버가 검증한다. ID 검증은 주장과 원문의 의미 일치를 보장하지 않으므로 근거 충실성도 평가한다. 외부 문서의 지시문은 실행하지 않는다.

완료 조건: 빈 결과·예산 종료·동시 최초 요청·판례 실패·답변 재시도에서 검색 중복/허위 출처가 없다. 적용 법령의 기준일과 스냅샷 조회일을 구분해 표시한다.

## 5. Advisor와 성공 턴 저장

- [ ] 소유권 검증 후 서버가 방 ID를 `ChatMemory.CONVERSATION_ID`로 설정한다. JWT 로그인 sessionId와 대화 ID를 혼용하지 않는다.
- [ ] MySQL JPA Message를 원본으로 읽는 `ChatMemoryRepository` 어댑터와 `MessageChatMemoryAdvisor`/윈도우 메모리를 검증한다. USER→user, BOT→assistant, 복호화 후 timestamp+ID로 정렬한다. INFO·검색 원문·예시·보조 호출 결과는 제외한다.
- [ ] 대화 원본과 모델 입력 윈도우를 분리한다. 최근 완결 턴·필요한 최초 사실관계·별도 근거의 전체 토큰 상한을 정한다. memory clear/윈도우 축소가 원본 메시지를 삭제하지 않게 한다.
- [ ] Advisor 호출 전후 저장 시점을 확인하고 요청 임시 메모리/저장 조정으로 출처 검증까지 성공한 질문·답변 쌍만 확정한다. 현재 질문 선저장·Advisor 저장으로 인한 중복을 제거한다.
- [ ] 상담방별 턴 순서를 보장한다. 재시도·동시 요청·낙관적 버전 충돌 시 오래된 메모리로 생성한 답변을 그대로 확정하지 않는다. 외부 호출 동안 DB 트랜잭션은 유지하지 않는다.
- [ ] 상담용 ChatClient에만 메모리 Advisor를 붙인다. 후속은 최초 원문 근거를 별도로 전달하고 자동 검색 Advisor/도구를 제공하지 않는다. 보조 키워드·step-back 호출은 기록을 읽거나 쓰지 않는다.
- [ ] 재로그인/서버 재시작 후 DB 기록을 복원한다. 로그아웃은 인증만 폐기하고 기록/근거를 보존한다. 방 삭제는 기록·근거·메모리를 정리하며 진행 중 작업의 결과가 삭제된 방을 되살리지 못하게 한다.
- [ ] 기존 방은 근거 스냅샷이 없을 수 있다. assistant 답변을 원문으로 승격하거나 후속에서 재수집하지 않는다. 검증 가능한 기존 근거 이관 여부와 이관 불가 시 새 상담 안내를 정한다.

완료 조건: 방별 격리·소유권·복원·동시 요청·실패 재시도·현재 질문 중복·삭제 경쟁을 검증하고, 후속/보조 호출의 금지된 검색·메모리 쓰기를 호출 횟수로 확인한다.

## 6. 답변 전략과 평가

- [ ] zero-shot을 먼저 완성하고 one-shot 예시 1개, step-back 검색을 독립 옵션으로 비교한다. 예시를 실제 사실/근거로 섞지 않는다. 정상 최종 답변은 턴당 1회이며 실패 재시도와 보조 호출은 별도 집계한다.
- [ ] 평가 질문 30~50개에 기대 법령/조문·판단 기준을 기록한다. 법령명/조문 지정·일상 표현·복합 쟁점·기준일·근거 부족·사실 정정·주제 변경을 포함하고 프롬프트 예시와 평가셋을 분리한다.
- [ ] 동일 문서·모델·수집 예산에서 기존 방식/zero-shot/one-shot/step-back을 비교한다. 고정 색인 검색과 동적 수집 평가는 분리한다. 역할별 에이전트 추가는 기본 RAG 이후 별도 계획을 따른다.
- [ ] 검색 Recall@K·무관 문서, 인용/근거 충실성·부족 처리, p95 지연·외부 호출·토큰/비용·실패를 기록한다. 프롬프트/모델/색인 버전을 결과에 포함한다.
- [ ] fixture·모킹 회귀, 실제 MySQL/Qdrant 통합, 실제 모델 품질 평가를 분리한다. 토큰·질문 원문·민감 사실을 로그에 남기지 않는다. 합격 수치는 기준선 확보 후 결정한다.

## 구현 전 미결정

1. 초기 법령 분야, 현행/연혁/시행예정과 사건 기준일 정책, 파서 보완 범위.
2. 임베딩 모델/차원·거리 함수·청킹·활성 색인 전환과 복구 정책.
3. 최초 요청의 전체 시간/호출/토큰 예산, 충분성 판정, 동기 응답 또는 비동기 상태 API.
4. 판례 상세/채택 상한, 스냅샷 용량과 컨텍스트 선별 정책.
5. Advisor 쓰기 계약·윈도우·완결 턴/동시성, 최초/턴 재시도 식별과 중단 복구.
6. 기존 근거 없는 상담방 이관, 데이터 보존/삭제와 진행 작업 취소 정책.
