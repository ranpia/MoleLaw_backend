# 모델·오케스트레이션 작업 상세

상태·순서의 기준은 [P01·P02·P03](README.md), 모델의 현재 값은 [역할별 Client](../role-chat-clients.md)다. 사용자 선택은 [D01·D02](../decisions/README.md)에 둔다.

## 이미 구현한 경계

검색 계획·법령 후보 평가·근거 충분성·최초/후속 답변 Client를 분리했다. 별도 에이전트 프레임워크 없이 Java 서버가 순차 호출한다. 인증·Tool 실행·ETL·예산·종료·인용·저장은 서버 책임이다. 후속 Client만 대화 Advisor를 사용한다. 새 판례 검색은 요청별 사용자 동의와 방 법령 근거로 제한하며 법령 수집·ETL 도구는 제공하지 않는다.

역할별 모델·추론 수준·완료 토큰 한도는 .env로 설정한다. 자동 상위 모델 승격·병렬 토론·경쟁 답변·영속 오케스트레이터는 구현하지 않았다.

## P01 — 실 API 호환성

각 역할의 최소 합성 입력으로 model·reasoning_effort·max_completion_tokens·usage를 확인한다. temperature/max_tokens가 추론 요청에 섞이지 않는지 실제 요청 계약을 확인한다. 최대 토큰 소진·빈 출력·JSON 실패·timeout·접근 거절을 구분한다. 기존 Advisor·서버 인용 검증을 우회하지 않는다.

실 호출 결과에는 입력·출력·추론 usage, 지연, 실패·재시도 횟수를 남긴다. 비밀 키·상담 원문·원시 추론은 로그에 남기지 않는다. 실 API 정상 응답 확인 전 설정 성공을 품질 합격으로 표시하지 않는다.

## P02 — 모델 평가

동일한 질문·원문·색인·실행 예산에서 역할별 모델과 low/medium을 교체 비교한다. 어려운 실패 사례에서만 high의 추가 비용 대비 효과를 본다. 분류 누락·잘못된 법령 수집·근거 충분성 오판·무근거 주장·인용 충실성·p95·실제 비용을 측정한다.

페이지별 평가 점수는 확률이 아니다. 페이지 순서·후보 조합을 바꿔 점수와 상위 법령이 안정적인지도 측정한다. 합격 기준은 D02로 확정하며 자동 승격이나 최종 통합 리랭크를 이미 채택한 것으로 간주하지 않는다.

## P03 — 예산 계측 연결

모델/API·Spring AI·수집기 재시도의 책임과 최대 횟수를 한 번에 계산한다. 계약 교정·거절·실패 응답도 usage 정산 대상이다. 호출 전 예약과 최종 답변 몫을 확보하고 실제 usage로 정산한다. usage 누락을 0으로 처리하지 않는다.

상세 예산 정책은 D01 확정 후 구현한다. LLM이 예산이나 실행 권한을 결정하지 않으며 현재 완료 토큰 한도는 요청 전체 비용 한도와 다르다.
