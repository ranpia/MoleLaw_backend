# 역할별 오케스트레이션과 모델 계획

상태: **계획·비교 후보**. 상위 문서: [재구축 요약](../backend-rebuild-plan.md). 기본 ETL·검색·Advisor 검증 후 도입한다. 모델 배정은 기존 계획의 실험 제안이며 최신 모델 순위나 구현 완료를 뜻하지 않는다.

## 목표와 경계

Java 서버 오케스트레이터가 검색 계획·근거 검토·답변 역할을 순서대로 호출한다. 처음에는 Spring AI `ChatClient`와 역할별 프롬프트·DTO로 구성하며 별도 에이전트 프레임워크를 필수로 도입하지 않는다.

- 서버 책임: 인증·소유권, 상태 전이, 외부 도구 실행, 수집·색인, 실행 예산, 출처 검증, 저장.
- 모델 책임: 검색 후보 제안, 제공된 근거 검토, 검증된 근거 기반 답변.
- 법령·판례 API는 `searchLaws`·`getLawDetail`·`searchCases`·`getCaseDetail` Tool로 구성한다. 초기에는 모델 제안 → 서버 검증 → Tool 실행 방식으로 고정하고 자동 tool-calling 루프는 도입하지 않는다. 상세 계약은 [RAG·ETL 계획](rag-etl.md#법령판례-api-tool-구성-확정)을 따른다.
- 최초 질문은 다음 페이지·다른 법령 후보를 수집하고 재검색할 수 있다. 고정 2라운드 제한을 두지 않는다.
- 후속 질문은 Advisor 기록과 최초 근거만 사용한다. 검색 계획·근거 수집·ETL 도구를 제공하지 않는다.

## 역할별 모델·추론 후보

| 역할 | 초기 후보 | 추론 수준·비교 조건 |
| --- | --- | --- |
| 서버 조정·수집·ETL·권한·출처 검증 | Java 서비스 | 모델 호출 없음 |
| 검색 계획 | `gpt-5.4-mini` | low, 복합 쟁점은 medium 비교 |
| 근거 검토 | `gpt-5.4-mini` | medium, 법령 충돌·판정 실패 사례는 `gpt-5.4` medium 비교 |
| 최초 답변 | `gpt-5.4-mini` | medium 기준선, `gpt-5.4` medium 품질 비교 |
| 후속 답변 | `gpt-5.4-mini` | low, 복합 적용·사실 정정은 medium 비교 |
| 제목·단순 키워드 | `gpt-5.4-mini` | none 또는 low 비교, 상담 메모리에 저장하지 않음 |
| 임베딩 | Ollama 비교군 | `bge-m3`, `qwen3-embedding:0.6b`, `embeddinggemma`; 답변 추론 수준과 별도 선정 |

high는 medium의 실패 사례와 평가 개선이 확인될 때만 검토한다. 높은 추론 수준으로 부족한 원문을 대체하지 않는다. 계정 접근과 Spring AI **1.0.9** 호환성을 확인한 뒤 모델 ID 또는 지원 snapshot을 고정한다.

## 단계별 도입 게이트

| 단계 | 작업 | 다음 단계 진입 조건 |
| --- | --- | --- |
| 0. 기본 RAG | 단일 답변·출처 검증·Advisor, 같은 자료의 평가 기준선 | 최초/후속 경계·성공 턴 저장·예산 종료·소유권 테스트 통과 |
| 1. 검색 계획 | 구조화된 쟁점·검색 후보만 추가 | 서버가 잘못된 조건을 거부하고 중복 탐색을 막음, 쟁점 누락 감소 여부 측정 |
| 2. 근거 검토 | 근거별 관련성·충족/부족 항목 추가 | 근거 ID 검증·종료 테스트 통과, 추가 지연·비용 대비 품질 개선 |
| 3. 모델 배정 | 같은 역할에서 모델·추론 수준 교체 비교 | 사전 합의한 품질·비용·p95 지연 기준 충족, 기준선으로 복귀 가능 |

초기 호출은 순차 처리한다. 병렬 검토·경쟁 답변·에이전트 토론은 필요성이 검증된 뒤 별도 계획으로 다룬다.

## 입출력 계약과 상태

다음은 구현할 계약의 예시이며 최종 DTO 이름은 구현 시 정한다.

| 계약 | 필수 항목과 서버 검증 |
| --- | --- |
| 공통 입력 | `requestId`, `schemaVersion`, 질문, 허용 근거 목록, 남은 예산. 소유권은 서버에서 이미 확인 |
| 검색 계획 출력 | `issues`, `queries`, `filters`, `missingFacts`. 질의 수·길이와 허용 필터 검사 |
| 근거 검토 출력 | `evidenceId`, 관련 쟁점, `supported/insufficient/conflicting`, 부족 항목, 종료 제안. 제공한 ID만 허용 |
| 답변 출력 | 본문, 인용 `evidenceId`, 근거 부족·범위 이탈 표시. 실제 원문과 인용 위치를 서버가 검증 |

모델의 계속/종료 제안은 서버의 결정 입력 중 하나다. 충분성은 자기 확신 점수만으로 판정하지 않는다. 법령 시행일·개정 버전·사실관계의 기준일 충돌을 검토 항목에 포함한다.

처리 상태는 예를 들어 `PLANNING → RETRIEVING → REVIEWING → ANSWERING → COMPLETED`로 구분하고, 실패·취소·예산 소진과 부족한 근거를 별도로 기록한다. 답변 실패 재시도는 저장된 근거를 재사용한다. 상담방별 동시 실행과 동일 요청의 중복 제출은 서버에서 제어한다.

## 실행 예산과 실패 처리

- 요청 전체의 deadline·모델/API 호출 수·입출력/추론 토큰·임베딩량·비용 상한을 역할들이 공유한다. 역할별 timeout·한도는 전체 예산 안에서만 배정한다.
- 재시도·스키마 교정·상위 모델 승격도 같은 예산에 포함한다. 호출 전에 예약하고 호출 후 실제 사용량으로 정산하며 사용량 누락 시 보수적으로 처리한다. 구체 수치는 기준선 측정 후 확정한다.
- 중첩된 HTTP/Spring AI/역할 재시도로 호출 수가 곱해지지 않도록 최종 재시도 책임을 정한다. timeout·일시 장애와 잘못된 입력·권한 오류를 구분한다.
- 동일 탐색 조건·페이지·후보 반복을 기록해 차단하고, 새 후보 없음·탐색 소진·근거 확보·예산 소진을 종료 사유로 남긴다.
- 구조화 결과 오류·없는 ID는 제한적으로 재시도한다. 실패 시 역할 우회 허용 여부를 사전에 정하고 조용히 검증을 생략하지 않는다. 최종 답변 실패·출처 오류는 성공 턴으로 확정하지 않는다.
- 최종 답변은 정상 요청당 한 번 생성한다. 재시도·승격은 별도 계측하며 검증을 통과한 응답 한 개만 저장한다. 취소·deadline 이후 늦게 도착한 결과는 저장하지 않는다.

## 설정·추적·보안

- 역할별 모델·추론 옵션·입출력 한도·timeout·재시도·승격 정책을 설정으로 분리하고 모델/프롬프트/스키마 버전을 추적한다.
- `temperature=0.5`를 모든 후보에 일괄 적용하지 않는다. API 옵션 매핑, structured output, Advisor, 토큰 사용량 반환을 작은 연동 테스트로 확인한다. 지원하지 않는 추론 옵션은 보내지 않는다.
- `requestId`·실행 ID·역할별 호출 ID로 시간, 사용 모델, 토큰 수, 비용, 종료/오류 사유를 기록한다. 원시 추론 내용·인증 토큰·민감한 상담 원문을 일반 로그에 저장하지 않는다.
- 검색 계획·근거 검토에는 상담 Advisor를 연결하지 않는다. 최종 답변만 방별 메모리를 읽고, 출처 검증 후 성공 턴을 저장한다.
- 사용자·법령·판례 본문의 지시문은 데이터로 취급한다. 모델은 임의 URL·SQL·도구를 실행할 수 없고 허용 API와 검증한 근거 ID만 서버가 처리한다.
- 외부 답변 모델에는 역할에 필요한 최소 정보만 전달한다. 상담 중 개인 식별 정보의 전달·가림·보존 정책을 정하고 외부 전송 정책을 문서화한다.
- 역할 설정으로 단일 RAG 기준선에 복귀할 수 있게 한다. 복귀 후에도 소유권·예산·출처 검증·후속 검색 금지 규칙을 유지한다.

## 평가와 완료 조건

- 동일 자료·질문·예산으로 단일 RAG → 검색 계획 추가 → 근거 검토 추가 → 모델/추론 교체를 비교한다. 고정 색인 평가와 동적 수집 평가는 분리한다.
- 30~50개 질문에 복합 쟁점, 사실 정정, 시행일 충돌, 잘못된 출처 ID, 문서 내 지시문, 근거 부족, 취소·timeout·반복 후보를 포함한다.
- 쟁점 누락·관련성 오판·인용 정확도·무근거 주장·부족 근거 안내, 종료 성공률·p95 지연·호출/토큰/비용을 측정한다. 변동을 확인하도록 모델 평가는 반복 실행한다.
- 결과 보고서에 자료·모델·프롬프트·설정 버전과 실패 사례를 남긴다. 품질 합격선과 비용·지연 상한은 기준선 확보 후 도입 전에 수치로 합의한다.
- 완료 조건: 역할 계약·경계 테스트, 실제 옵션 호환성, 중복/예산/취소 검증, 비교 보고서, 단일 RAG 복귀 절차가 준비됨. 현재 이 단계들은 미구현이다.

## 기존 후보의 참고 자료

기존 계획에서 검토한 공급자 자료다. 구현 시 접근 가능 모델·지원 옵션을 다시 확인한다.

- [Spring AI ChatClient](https://docs.spring.io/spring-ai/reference/api/chatclient.html), [Advisors](https://docs.spring.io/spring-ai/reference/api/advisors.html): 저장소 고정 버전에서 별도 확인
