# 임베딩 벡터 실험 검토

> 이 문서는 2026-10-15 당시의 검토 기록입니다. 현재 완료 결과는 [네 모델 통합 비교](../evaluation/legal-retrieval/reports/chunk-experiments/comparison.md)를 따릅니다.

기준: 2026-10-15, `experiment/legal-embedding-evaluation`, `674a98d`. 최초 검토 시작 시 작업 트리는 깨끗했다. 범위는 `evaluation/legal-retrieval`의 실행기·검증기·C# 벡터 색인·결과와 `docker/ollama`다. 애플리케이션 전체 보안 감사나 법률 정답의 재심사는 아니다. 실험 코드는 변경하지 않았다.

## 재검토 결론: 모델 선정 실험으로 평가

사용자 요청에 따라 두 검토 에이전트가 모델 선정·평가 방법과 로컬 실험 보안을 별도로 재검토했다. **현재 실험은 계속 진행할 수 있다.** 아래 보강 항목 전체를 구현해야 모델 비교를 재개할 수 있다는 이전 판단은 철회한다. 전제는 개인 로컬 환경, 공개 법령·작성 질문, 단독 순차 실행, 실행 중 모델·입력 데이터 고정이다.

검증기 자체의 방어 부족과 현재 데이터 오류는 구분한다. 추가 대조 결과 500/300/700문자 데이터 모두 5,486개 source unit이고, 질문·정답 unit·분할은 동일하며 정답 unit/그룹/flat chunk 표현의 불일치는 0건이다. 완료된 Gemma·BGE-M3 500문자 보고서도 질문 해시와 코퍼스 해시가 일치한다. **현재 비교가 오염됐거나 잘못됐다는 증거는 발견하지 않았다.**

캐시 재사용과 중단 후 재개는 비용을 줄이는 적절한 실험 기능이다. 기존 정상 캐시를 삭제하거나 모두 재임베딩할 필요는 없다. 모델별 접두문 차이도 각 모델의 검색 입력 계약을 따른 것이므로 그 자체는 불공정한 비교가 아니다. 현재 결과의 범위를 dense 임베딩 모델 선정으로 한정하며 전체 RAG·운영 보안 완성을 합격 조건으로 요구하지 않는다.

## 모델 선정의 다음 판단 기준

1. 현재 두 모델의 300/500/700문자 구성을 동일 데이터로 완료하고 **development** 지표로 후보를 좁힌다. 실행 중 모델 교체·동시 평가·데이터 편집을 피한다. 사용자가 중단한 실행은 별도 재개 지시 없이 재개하지 않는다.
2. 비교의 1차 지표와 보조 지표를 미리 정한다. 예를 들어 Recall@5를 1차로 두고 MRR·Recall@10·양성 수용률·음성 수용률을 함께 검토한다. 현재 development 양성은 30개이고 Recall@5 차이는 약 1.78%p이므로 단일 숫자로 확정적인 우열을 주장하지 않는다.
3. 한국어 추가 학습 후보는 revision·라이선스·입력/pooling/정규화·추론 가능 여부를 확인하고 같은 데이터로 별도 평가한다. 기존 모델의 벡터 공간을 재사용하지 않는다. 공개 벤치마크 성적을 이 법령 실험의 성적으로 대체하지 않는다.
4. 성능·비용은 같은 하드웨어·threads·batch 조건에서 비교한다. warm 질문 지연과 차원/벡터 용량을 고려하되, 캐시 재사용량이 다른 실행의 indexingWallMs를 모델 자체의 속도 차이로 해석하지 않는다. 반복 지연 측정·paired bootstrap 등은 우열이 가까울 때 추가할 실험이다.
5. 후보를 고른 뒤 held-out을 최종 확인에 사용한다. 현재 이미 공개된 held-out으로 반복 선택하면 탐색 결과로 표시하고, 최종 검증이 필요할 때 새 독립 질문셋을 마련한다. 서비스 ANN·답변 품질·배포 검증은 모델 선정 이후 단계다.

## 결과 해석

완료된 비교는 500문자 청크의 두 모델뿐이다. 300·700문자 데이터는 준비됐지만 모델 평가는 완료되지 않았다. 기록된 held-out Recall@5는 Gemma 79.93%, BGE-M3 75.40%, MRR은 각각 0.7861·0.7226이다. 개발용 Recall@5는 BGE-M3 64.06%, Gemma 62.28%로 방향이 다르다. held-out 결과를 반복적으로 보고 모델·청크를 고르는 것은 피해야 한다.

held-out 음성 수용률은 Gemma 3/5, BGE-M3 2/5다. 음성이 5개뿐이고 검색 점수 분류이므로 안전한 답변 거절이나 법률 상담 안전성을 입증하지 않는다. 현재 비교는 정확 전수 dense 검색이며 Qdrant ANN·서비스 RAG·권한 분리 성능 검증도 아니다. 기존 문서는 이 제한을 대체로 정확히 구분한다.

### 1. 실패한 모델 digest 변경 실행의 벡터가 공유 캐시에 남음

근거: `evaluation/legal-retrieval/scripts/evaluate.ps1:30`, `:88`, `:92`, `:131`.

시작 시 `latest` 태그의 digest로 캐시 경로를 정하고 각 배치를 즉시 저장한다. digest 변경 검사는 모든 평가가 끝난 뒤 수행한다. 같은 태그가 실행 도중 교체되어 동일 차원의 다른 모델 응답이 저장되면 종료 시 오류를 내더라도 그 배치는 원래 digest의 공유 캐시에 남는다. 원래 모델을 복원해 재개하면 잘못된 벡터를 정상 캐시로 재사용할 수 있다. 이는 코드상 확인한 경로이며 실제 모델 교체는 수행하지 않았다.

개선: 실행별 staging 캐시에서 작업하고 검증 성공 시 확정한다. 실패한 실행의 신규 배치를 격리하며 모델 태그 변경을 평가와 경합하지 못하게 한다. 성공 배치 재사용을 유지하려면 모델 불변성 확인과 배치별 provenance를 함께 설계한다. 종료 시 digest 확인만으로 이미 저장된 캐시의 무결성이 보장되지는 않는다.

현 단계 대안: 실행 중 모델 pull/create/delete를 하지 않고 전용 Ollama를 순차 사용한다. 일반적인 사용자 중단·timeout을 모델 교체와 동일시하거나 정상 완료 배치를 전부 삭제하지 않는다.

검증: mock Ollama에서 중간 digest 변경→실행 실패→원래 digest 재개 순서로 잘못된 배치가 재사용되지 않는지 확인한다.

### 2. 동시에 실행하면 중복 캐시가 다음 실행을 막음

근거: `evaluation/legal-retrieval/scripts/evaluate.ps1:33`, `:37`, `:78`, `:92`; `scripts/lib/DenseIndex.cs:61`, `:75`.

공유 캐시 단위 잠금이 없다. 두 실행이 같은 missing input을 관찰하면 서로 다른 GUID 파일에 같은 키를 저장한다. 다음 실행의 `ReadBatch`는 `Dictionary.Add`에서 중복 키 오류로 중단한다. 서로 다른 프로세스가 같은 키를 저장한 상태를 격리된 두 배치로 만들어 재로딩 실패를 재현했다. 현재 사용자가 중단한 배치가 실제로 손상됐다는 뜻은 아니다.

개선: 캐시별 exclusive lock 또는 입력 키별 원자 저장을 적용한다. 읽을 때 동일 키·동일 벡터 중복은 멱등 처리하되 다른 벡터는 명시적인 무결성 오류로 거절한다. 동시 실행의 메타데이터 쓰기도 같은 정책으로 보호한다.

현 단계 대안: `run-model.ps1`의 순차 실행을 유지하고 같은 공유 캐시에 별도 평가 프로세스를 동시에 실행하지 않는다. 병렬 평가를 도입할 때 잠금/멱등성을 구현한다.

검증: 동일 모델의 두 실행이 일부 입력을 공유할 때 둘 다 완료·재개 가능한지, 충돌 벡터는 거절하는지 확인한다.

### 3. 평가에 사용하는 정답 필드와 검증하는 필드가 불일치

근거: `evaluation/legal-retrieval/scripts/validate-evaluation.ps1:28`, `:30`, `:36`; `scripts/evaluate.ps1:111`, `:125`.

검증기는 주로 `relevantChunkGroups`와 `relevantChunkIds`를 확인하지만 지표 계산은 `relevantUnitIds`를 사용한다. 세 표현의 집합 일치, 정답 unit 존재, 중복 unit을 검사하지 않는다. 원본 복사본에서 첫 양성 질문의 `relevantUnitIds`만 존재하지 않는 ID로 바꿔도 PASS였다. 잘못된 분모·누락 정답·분할 검사 우회 또는 평가 실패를 사전에 막지 못한다. 현재 원본 라벨이 틀렸다고 판단한 것은 아니다.

개선: 실제 corpus의 unit 집합을 만들고 정답 unit·그룹 unit·flat chunk 목록의 집합 일치를 검사한다. 분할 누수도 canonical unit 집합으로 확인한다. unitCount·chunkCount와 실제 데이터의 일치, 중복 정답도 검증한다.

검증: 존재하지 않는 unit, 다른 unit으로 교체, 그룹 삭제, 중복 unit, 분할 간 같은 정답 unit을 넣은 변조 fixture가 모두 실패해야 한다.

### 4. 비교표가 동일 질문·분할·원문인지 확인하지 않음

근거: `evaluation/legal-retrieval/scripts/compare-results.ps1:6`, `:17`.

`reports` 아래 `summary.json`을 재귀 수집하고 chunkingVersion만 있으면 비교표에 포함한다. 질문·정답·분할 해시와 원문 단위 버전의 공통 기준을 검증하지 않는다. 이후 일부 모델만 수정된 질문으로 다시 실행하면 다른 평가 조건의 결과를 같은 비교표로 내보낼 수 있다. 현재 두 모델 결과가 서로 다른 조건이라는 증거는 아니다.

개선: 청크 크기와 무관한 source-unit·질문/정답/분할 canonical 해시를 보고서에 기록하고 비교 전에 동일성을 강제한다. 현재 run-model의 실행별 질문 해시 확인과 별도로 비교 집합 전체를 확인해야 한다. 구성별 완료된 두 split·질문 수·결과 파일도 검증한다.

### 5. PDF 추출은 호스트에서 자원 제한 없이 실행됨

근거: `evaluation/legal-retrieval/scripts/fetch-special-sources.ps1:31`, `:32`.

네트워크 다운로드에는 timeout이 있지만 `java -jar ... export:text`에는 최대 실행 시간·heap 제한·격리가 없다. 악성 또는 손상 PDF가 파서를 오래 실행시키거나 과도한 메모리를 사용하면 개발 PC에서 실험이 멈출 수 있다. 현재 입력은 저장소가 지정한 공식 PDF 두 개로 공격 표면이 작으며, 임의 사용자 업로드 API는 아니다.

개선: `-Xmx`와 프로세스 timeout을 설정하고 전용 저권한 실행 환경 또는 격리 컨테이너를 사용한다. 입력 크기 상한·다운로드 완료 확인도 추가한다. Ollama 컨테이너의 8 GiB 제한은 호스트 PDFBox 프로세스에는 적용되지 않는다.

Apache도 비신뢰 PDF의 무한 실행·자원 소비 가능성을 설명하고 호출 애플리케이션의 timeout·메모리·격리를 권고한다. 이는 PDFBox 자체 원격 실행 취약점을 확인했다는 뜻은 아니다. [PDFBox 보안 모델](https://pdfbox.apache.org/security.html)

### 6. PDFBox 실행 파일 무결성·완료 검증 없음

근거: `evaluation/legal-retrieval/scripts/fetch-special-sources.ps1:24`, `:26`, `:32`.

HTTPS Maven Central에서 버전 고정 JAR을 받지만 신뢰된 해시/서명을 검사하지 않고, 기존 경로에 파일이 있으면 즉시 실행한다. 부분 다운로드는 이후 반복 실행을 막고, 캐시가 변조되거나 공급 경로가 훼손되면 실행 파일을 검증할 장치가 없다. 로컬 파일 쓰기 권한을 가진 공격자가 이미 다른 코드도 바꿀 수 있다는 한계가 있으므로 이를 독립적인 원격 취약점으로 단정하지 않는다.

개선: 신뢰된 SHA256/서명 검증 후 임시 파일을 원자적으로 rename하고, 재사용 시에도 검증한다. 모델 이미지도 버전 태그뿐 아니라 이미지 digest를 기록·고정하는 것을 검토한다.

PDFBox 3.0.5에 해당하는 공식 path traversal 공지는 `ExtractEmbeddedFiles` example 경로다. 현재 스크립트는 `export:text`를 호출하므로 그 CVE가 이 경로에서 악용된다고 보고하지 않는다. 버전 업데이트 시 추출 텍스트가 바뀔 수 있으므로 코퍼스 버전·재현성도 확인한다. [공식 취약성 범위](https://pdfbox.apache.org/security.html)

## 보안상 유지할 구성과 경계

- 평가 URL은 `127.0.0.1`로 고정되며 Compose도 `127.0.0.1:11435`에 게시한다. 컨테이너 내부 `OLLAMA_HOST=0.0.0.0`만 보고 호스트 인터넷 공개로 판단하지 않는다.
- Ollama 로컬 API는 인증이 없다. 같은 PC의 프로세스·공유 Docker 네트워크는 신뢰 경계 안에 있으며 모델 교체·추가 요청으로 평가를 방해할 수 있다. 전용 실험 환경을 유지하고 LAN/터널 공개 시 인증 게이트웨이를 추가한다. [Ollama 인증 문서](https://docs.ollama.com/api/authentication)
- 현재 코퍼스는 공개 법령·직접 작성 질문이고 평가에 OpenAI 키·애플리케이션 DB가 필요하지 않다. 실제 상담·개인정보로 확장할 때 CSV 원문 질문·벡터 캐시·보고서의 접근과 보존 정책을 별도로 설계한다. Git ignore는 접근 제어나 비식별화가 아니다.
- C# 캐시는 차원·유한값·0 벡터·파일 형식을 검사한다. 다만 올바른 형식의 벡터가 올바른 모델에서 생성됐는지 암호학적으로 증명하지 않는다. 비신뢰 캐시를 받아 실행 결과에 섞지 않는다.

## 이번 검증과 남은 작업

- 원본 500문자: 110개 질문·6,634개 청크 검증 PASS.
- 300문자: 110개 질문·8,497개 청크 검증 PASS.
- 700문자: 110개 질문·6,031개 청크 검증 PASS.
- `test-evaluator.ps1`: cosine 1/0/-1, 정규화, 캐시 왕복, unit 집계, 768/1024차원 분리 PASS.
- 임시 디렉터리의 복사본으로 정답 unit 변조 허용과 중복 캐시 재로딩 실패를 재현했다. 첫 캐시 재현 시 PowerShell 배열 바인딩 오류가 있어 수정된 jagged array로 다시 확인했다. 실제 실험 캐시는 변경하지 않았다.
- 모델 실행·모델 교체·PDF 다운로드·운영 공격·Spring 전체 테스트는 수행하지 않았다. 사용자가 중단한 모델 평가는 재개하지 않았다.

재검토에서 현재 데이터의 정답 표현·variant별 질문/정답/분할과 완료 보고서 입력 해시를 추가 대조했다. 모두 일치했다. 에이전트들의 재검토는 읽기 전용이며 모델을 실행하지 않았다.

우선 작업은 단독 실행·모델/데이터 고정 조건에서 모델·청크 비교를 완료하는 것이다. 3~4는 데이터 확장 전 평가 자동화 보강으로 권장하고, 1~2는 동시 실행·모델 자동 교체 시점에 강화한다. 5~6은 현재 모델 선정을 막는 조건이 아니며 수집 경계가 확대될 때 적용한다. 최종 선정 판단에는 검색 품질뿐 아니라 로컬 자원·추론 가능성·라이선스도 함께 기록한다.
