# 질문 분류와 검색 계획

최초 상담에서 전용 `questionPlanningChatClient`가 원문 전체를 읽고 요청 분석과 검색 계획을 함께 생성한다. HTTP 요청은 기존 `POST /api/chat-rooms`의 `content`를 그대로 사용한다.

## 요청 분석 계약

`QuestionRetrievalPlan.analysis`에는 다음 자료를 보존한다. 특정 분야나 법령명을 코드로 고정하지 않는다.

| 필드 | 의미 |
| --- | --- |
| `title`, `purpose` | 상담방 제목과 사용자가 원하는 결과 |
| `facts` | 사용자가 제공한 사실과 원문의 정확한 인용 |
| `issues` | 최대 8개 독립 질문: ID·요구사항·원문 인용·검색 표현·언급된 명칭·검색 후보·미확인 사실 |
| `relations` | 질문 ID 사이의 비교·충돌·선행 조건·예외·시간 관계 |
| `ambiguities` | 해석이 갈리는 표현 |

인용과 언급된 명칭은 실제 원문에 존재해야 하며 중복 ID·없는 질문을 참조하는 관계를 거부한다.
검색 후보 명칭은 확인된 법령이나 답변 근거가 아니다. 원문과 분석을 함께 유지하며 예시를 필수 요구사항으로 승격하지 않는다.
서버 검증은 인용·구조의 정합성을 확인하며 LLM이 모든 의미를 빠짐없이 추출했다는 보장은 아니다.

첫 검색과 색인 후 검색은 **각 질문의 첫 `searchTerms`**를 사용한다. 대표 `searchQueries` 3개가 질문 개수의 제한이 되지 않는다.
나머지 검색 표현·명칭 후보·관계는 충분성 판단에 유지하여 재검색/수집에 사용한다.
모든 질문을 검토하도록 판단·답변 프롬프트에 전달하지만 쟁점별 근거 충족을 서버에서 강제하는 상태 기계는 후속 작업이다.

분석 단계에서는 사실과 질문의 인용을 검증하고, 이후 단계는 원문을 그대로 전달하면서 중복 인용과 방 제목만 제외한 분석을 사용한다.
요청 목적·사실 내용·질문·관계·모호함·검색 표현·미확인 정보는 삭제하지 않는다.
최종 답변에는 원문·요청 목적·제공 사실·모든 질문·관계·모호함·미확인 사실을 전달하고 검색 가설을 법적 근거로 사용하지 않는다.
분석 제목은 일반/스트림 상담방 저장에 재사용하여 제목만을 위한 키워드 호출을 생략한다.
별도 키워드 API와 이전 서버 생성 결과에 대한 제목 생성 호환 경로는 유지한다.

분석 자료가 추가된 기본 입력 상한은 판단 기본 자료와 읽기 입력 각각 8,000토큰, 본문을 합친 판단 입력은 32,000토큰이다.
기존 `.env`가 더 작은 `APP_AI_EVIDENCE_MAX_INPUT_TOKENS` 또는 `APP_AI_EVIDENCE_CATALOG_MAX_INPUT_TOKENS`를 지정했다면
`APP_AI_EVIDENCE_DECISION_MAX_INPUT_TOKENS`와 함께 배포 전에 새 입력이 들어갈 수 있는지 확인한다.
이는 실제 토큰 사용량이나 최종 예산 확정값이 아니라 정보 전달을 위한 안전 상한이다.
초과 시 원문·질문·조문을 조용히 잘라내지 않고 기존 오류 경로로 종료한다.

## 유형별 검색

| 유형 | 목적 | 쿼리 방향 |
| --- | --- | --- |
| `LAW_DISCOVERY` | 적용 법령 찾기 | 규제 대상·법률 쟁점 |
| `LAW_EXPLANATION` | 법령·조문 의미 설명 | 법령명·조문·핵심 개념 |
| `CASE_ASSESSMENT` | 구체 사건 판단 | 요건·예외·제한 |
| `PROCEDURE_GUIDANCE` | 절차 안내 | 신청·신고·담당 기관 |
| `OUT_OF_SCOPE` | 법률 상담 범위 밖 | 검색 없이 기존 422 근거 부족 응답 |

계획은 검색 쿼리 1~3개, 법령 검색 조건 0~3개, 누락 사실 최대 6개를 포함한다. 법령 조건은 충분성 판단의 제안이며 즉시 실행 명령이 아니다. 알 수 없는 필드·잘못된 enum·누락 필드·실행 권한 지시는 엄격한 JSON 검증으로 거절한다.

예: “공항 근처에 15층 건물을 지으려는데 필요한 법령”은 `LAW_DISCOVERY`로 분류하고 공항 주변 장애물 제한·건축물 높이 제한을 검색하도록 유도한다. 실제 쿼리는 모델이 생성하므로 고정 문자열을 보장하지 않는다.

## 답변 범위

- `GENERAL_GUIDANCE`: 관련 법령·확인 항목을 안내한다. 위치·실제 높이가 없어도 수집을 진행하되 건축 허용 여부는 단정하지 않는다. 층수에서 미터 높이를 추정하지 않는다.
- `SPECIFIC_ASSESSMENT`: 누락 사실이 없는 `CASE_ASSESSMENT`에만 허용한다. 제공된 사실과 검증한 근거 안에서 답한다.

## 실행과 재계획

### 승인된 법령 수집 대기열

QDRANT 경로에서는 `COLLECT_LAW.lawSearches` 전체를 요청별 대기열에 넣는다. 첫 법령을 색인했다는 이유로 나머지 조건을 버리지 않는다.
조건마다 모든 페이지 심사→선정→법령 한 건의 상세/저장 검증→질문별 재검색을 수행하고 다음 승인 조건으로 넘어간다.
조건 묶음 처리가 끝나면 LLM이 다음 행동을 판단한다. 초기 계획의 후보 조건은 승인 없이 수집하지 않는다.

조건의 정규화 키와 TITLE/BODY·완전 일치·부처 필터로 중복을 검사한다. 처리한 같은 조건을 다시 실행하지 않고,
다른 후보나 명칭이 필요하면 LLM이 변경한 조건을 제안한다. 상태는 `PENDING`, `INDEXED`, `EXHAUSTED`, `DEFERRED_LIMIT`으로 구분한다.
상세 6건 한도로 처리하지 못한 조건은 `DEFERRED_LIMIT`이며 검색 결과 없음으로 위장하지 않는다.
대기열은 요청 내 메모리 상태이며 서버 재시작 후 작업 재개/영속 작업 큐를 구현한 것은 아니다.

판단 입력의 `retrievalProgress`는 질문별 첫 검색 실행 여부와 모든 승인 수집 조건의 최신 상태를 담는다.
최근 검색 이력이 8개 이하로 줄어도 수집 상태는 유지하며, 상태 기록은 외부 호출 횟수에 포함하지 않는다.
검색 실행·후보 존재·색인 완료는 관련성이나 답변 충분성을 보증하지 않는다.

### 후보 근거 균형

질문별 검색 결과 묶음을 요청 내에서 유지하고 여러 질의의 결과를 합칠 때 순환 배분한다.
같은 법령이 여러 질의에 중복 등장해 RRF 점수를 독점해도 다른 쟁점의 후보가 배제되지 않도록 법령별 선택 수를 고려한다.
명시한 조문은 우선하고, 이미 읽은 근거는 같은 배분 조건 안에서 우선한다. 추가 질의의 결과는 별도 보완 묶음으로 합친다.
가용 후보와 전체 조문 크기 제한 안에서 서로 다른 조문 최대 15개를 남긴다. 없는 근거를 생성하거나 관련성을 점수만으로 확정하지 않는다.
구세대 제거·동일 조문 중복 제거·전체 본문/출처 검증은 유지하며 본문을 잘라서 후보 수를 채우지 않는다.

최종 답변이 모든 질문에 답했는지 별도로 검사하는 완결성 검증은 사용자 요청으로 보류한다. 기존 충분성 판단과 인용 검증만 유지한다.

일반 처리 시간은 `APP_LAW_RETRIEVAL_PROCESSING_TIMEOUT`으로 조정할 수 있으며 기본 3분, 임베딩 시계는 별도다.
여러 법령과 CPU 리랭크를 품질 검증하는 현재 로컬 환경은 임시로 15분을 사용한다. 최종 예산 정책·전체 요청 deadline 확정은 후속 작업이다.

분류 쿼리별 Qdrant 상위 15개를 조회하고 중복·버전을 정리해 최종 후보 최대 15개를 유지한다. 판단 Client는 근거와 최근 검색 결과를 보고 답변·재검색·법령 수집·종료를 선택한다. 빈 결과는 대체 조건을 판단할 기회이며 API 장애와 구분한다. 정확 제목 검색을 부분 검색으로 조용히 완화하지 않는다.

서버가 최대 4회 추가 행동, 조건별 전체 페이지(호출·시간 예산 내), 상세 최대 6건, 호출·시간 예산을 통제한다. 검색 피드백은 최근 최대 8개를 토큰 예산 안에서 전달한다. 최종 인용은 실제 제공한 근거 ID로 검증한다. 후속 상담에는 재분류·새 수집을 연결하지 않고 기존 Advisor와 최초 근거 스냅샷을 사용한다.

## 검증

`QuestionAnalysisTest`는 4개 질문 검색·원문 인용·명칭·관계 검증을, `QuestionRetrievalPlannerTest`는 공백 없는 복합 질문의 분석 계약 전달을 검증한다.
`QuestionPlanInputTest`는 후속 입력에서 중복 인용만 제외하고 분석 내용이 유지되는지 확인하며 토큰을 로컬 추정한다.
기본 테스트는 외부 모델을 호출하지 않는다. 실제 모델 검증은 명시적인 유료 작업인 `.\gradlew.bat questionAnalysisLiveTest`로 분리한다.
이 검증은 복합 질문 1건을 첫 분석만 수행하며 DB·법령 API·임베딩을 사용하지 않고 원문 대신 실제 usage와 항목 개수만 출력한다.

2026-10-26 실제 `gpt-5.4-mini`/low 검증: 공백 없는 건축·소방 복합 질문에서 질문 2개·검색 질의 2개·관계 1개를 생성하고
원문 인용 및 언급된 명칭 검증을 통과했다. 동의/사용승인과 기존 건물의 소급 적용 요구사항을 모두 유지했다.
실제 usage는 입력 1,539·완료 2,166토큰(추론 포함), 약 9초였다. 전체 RAG 답변의 법률 정확도나 모든 질문의 추출 품질을 보장하는 결과는 아니다.
검증용 클라이언트의 기본 temperature가 API에서 거절된 초기 시도는 별도이며, 실제 검증은 역할 Client와 동일한 옵션으로 수행했다.

분류 계약·쿼리 전달·일반 안내 범위·빈 검색 재계획·반복 종료·장애 전파를 단위 테스트로 검증한다. `initialConsultationSimulationTest`는 LLM/OpenLaw를 모킹하고 Postman 임베딩 HTTP 모의 서버·격리 Qdrant를 연결해 분류부터 저장까지 확인한다. 실제 모델의 분류 정확도·법률 답변 품질은 별도 평가 대상이다.

## 판단 오류 진단

판단 Client에 Java 계약에서 생성한 JSON 스키마를 전달한다. 실패 시 Evidence decision failed의 stage=MODEL_CALL은 모델 호출 경로, stage=DECISION_VALIDATION은 응답 JSON·상태별 필드·근거 ID 검증 경로를 뜻한다. 로그에는 예외 클래스·응답 길이·건수만 남기며 질문·본문·모델 응답·제공자 예외 메시지를 기록하지 않는다. 검증 오류를 정상 판단으로 바꾸지 않는다. ACTION_CONTRACT에 한해 아래의 최대 1회 계약 교정을 허용하며 다른 오류는 자동 교정하지 않는다.

## 일반 법령 탐색의 조기 종료 방지

LAW_DISCOVERY + GENERAL_GUIDANCE의 최초 판단이 INSUFFICIENT이면 같은 근거·계획·검색 이력으로 최대 한 번 재검토한다. 누락 위치·높이는 구체 허용 판단만 제한한다는 서버 지시를 제공한다. 재검토도 INSUFFICIENT이면 종료하며 모델 판단을 임의로 답변이나 수집 명령으로 바꾸지 않는다. 최초 분류 외에 이 조건에서 LLM 호출이 최대 1회 추가되고 기존 시간·탐색 예산은 유지된다. 다른 유형이나 이후 라운드에는 적용하지 않는다.

### 로컬 충분성 판단 확인

local 프로필에서 EvidenceDecisionPlanner DEBUG 로그를 활성화한다. Evidence decision diagnostic JSON의 candidateCount는 검색 후보 수, visibleCount는 토큰 예산 내 실제 전달 수다. visibleEvidence에는 전달한 조문의 ID·제목만 포함한다. decision.reason·missingIssues로 종료 사유를, reconsider로 최초 판단/재검토를 구분한다. 질문과 조문 본문, 검증되지 않은 모델 응답 원문은 기록하지 않는다. 판단 사유가 사용자 사실을 요약할 수 있으므로 로컬 진단 로그도 외부에 그대로 공개하지 않는다. 운영 기본 로그 수준은 변경하지 않는다.

## 수집 전환의 판단 주체

수집 전환은 LLM의 COLLECT_LAW 선택으로 실행한다. 재검색 횟수나 점수만으로 서버가 행동을 변경하지 않는다. 판단 입력의 executionState는 remainingActions(4부터 0), 누적 vectorSearchCount/lawSearchCount, EXISTING_INDEX_ONLY 검색 범위를 제공한다. 검색 이력이 토큰 예산으로 줄어도 누적 횟수는 유지된다. AVAILABLE은 관련성 판정이 아니며 Qdrant 질의 변경으로 미색인 법령이 생기지 않음을 프롬프트에 명시한다. LLM은 남은 행동과 이전 결과를 보고 재검색·외부 수집·종료를 선택한다. 0회에서는 최종 충분성 판단만 허용하며 서버의 기존 예산·중복·인용 검증은 유지한다.

응답 검증 실패는 validationCode로 구분한다: JSON_CONTRACT(JSON 구조·필수 필드·타입), FIELD_CONSTRAINT(문자열·목록·법령 조건 제약), ACTION_CONTRACT(행동에 필요한 목록 조합), UNKNOWN_EVIDENCE_ID(전달하지 않은 근거 ID). 검증 예외에는 모델 응답이나 제공자 메시지를 보관하지 않으며 외부 오류 응답은 기존 계약을 유지한다.

중복 벡터 질의는 HTTP·임베딩을 재실행하지 않고 DUPLICATE 피드백을 다음 판단에 전달한다. 중복만 제안했다는 이유로 즉시 종료하지 않으며 같은 4회 행동 한도 안에서 다음 선택을 맡긴다. SEARCH_SKIPPED reason=DUPLICATE_QUERY 로그로 실행 생략을 구분한다. vectorSearchCount는 실제 실행만, skippedDuplicateQueryCount는 중복 생략만 집계한다. 이 변경이 COLLECT_LAW를 강제하지는 않는다.

ACTION_CONTRACT 오류에만 판단 호출당 최대 1회 계약 수정을 요청한다. 수정 요청에는 실패한 행동 이름·목록별 건수만 추가하고 원래 근거·남은 행동을 유지한다. 서버는 행동·검색어를 채우지 않는다. 수정 응답도 동일 검증을 거치며 재실패·알 수 없는 근거 ID·JSON 오류·제공자 장애는 자동 재호출하지 않는다. 최대 1회 추가 LLM 비용이 발생할 수 있으며 기존 상담 시간 예산은 유지한다.

## 일반 법령 검색 리랭크

AI Search에는 적용하지 않는다. COLLECT_LAW의 일반 법령 검색은 hasNext가 false가 될 때까지 모든 페이지를 조회한다. 페이지별 전용 LLM이 모든 후보에 0~100점 관련성과 사유를 반환하며, 서버는 누락·중복·알 수 없는 ID·범위 밖 점수를 거부한다. 중복 법령 ID는 한 번만 평가한다. 전체 페이지 검토 후 설정된 최소 점수 이상의 후보를 점수 내림차순으로 정렬해 최대 개수까지 상세 조회 대상으로 보관한다. `APP_LAW_CANDIDATE_MINIMUM_SCORE`(1~100, 기본 70)와 `APP_LAW_CANDIDATE_MAX_CANDIDATES`(1~6, 기본 2)가 선택기·수집기·모델 입력에 함께 적용된다. 별도 환경은 60점·3개로 완화했다. 동점은 검색 순서를 유지한다. 법령 1건 색인·검증 후 재검색과 충분성 판단으로 복귀한다.

기존 페이지별 즉시 선택과 3페이지 제한은 이 방식으로 대체한다. 검색·수집 128회 및 별도 임베딩·색인 호출/시간 예산 또는 API 페이지 상한으로 전체 검토가 불가능하면 부분 결과를 색인하지 않고 중단한다. 점수는 LLM의 관련성 평가이며 법적 정확성이나 확률이 아니다. 제목 기반 평가이므로 실제 조문의 충분성은 색인 후 판단한다. 페이지 수에 비례해 LLM 비용과 응답 시간이 증가한다. 후보별 사유는 실행 중 검증하며 DB에 별도 저장하지 않는다.

정책 판단·미완료 작업은 [사용자 판단](../decisions/README.md)과 [작업 계획](../plans/README.md)으로 분리한다. 리랭크 개선·통합 후보 재평가는 현재 구현이 아닌 P04 평가 대상이다.

## 읽은 근거로 충분성 판단

최초 충분성 판단은 후보 전체 목록→본문 읽기 선택→MySQL 원문 확인→실제 읽은 본문 입력으로 변경했다. 기존 2500토큰은 판단 기본 JSON의 상한이며 본문을 그 안에서 한 조문만 남기는 방식은 사용하지 않는다. 후보 목록 4000·본문 누적 12000·결합 판단 입력 20000토큰의 추정 상한과 최대 2회 읽기 선택을 적용한다. [현재 계약과 제한](evidence-reading.md)을 따른다.
