# 판례 검색 범위·전체 페이지·최종 답변 분리

2026-10-24 최신 사용자 선택을 반영한다. 검색 범위를 매번 모두 실행하던 이전 설계는 아래 도구 선택 방식으로 대체했다.

2026-10-26: 사건 식별어의 유무를 서버 규칙으로 분류하지 않고 LLM이 검색 의도·범위·읽을 후보·본문 동일성을 판단한다.
후속 요청 원문은 일반/스트림 경로 모두 계획에 전달하며, 방 법령은 맥락으로 유지한다.
지정 사건을 새로 찾아야 하는데 이번 요청의 동의가 없으면 서버가 검색 동의 메시지를 반환한다.
이전 턴의 동의를 현재 턴으로 자동 승계하지 않으며 다른 사건의 기존 판례를 지정 사건의 판결처럼 소개하지 않는다.
최종 작성 입력도 최초 상담의 조문 설명 우선 지시와 분리해 현재 후속 요구를 우선한다.

기본 테스트는 모의 모델을 사용한다. `.\gradlew.bat caseSearchIntentLiveTest`는 명시적인 유료 검증으로,
실제 모델의 의도 판단과 공개 API 목록 11건에서 뒤쪽 후보를 선택하는지만 확인한다. 메타데이터 선택은 판결 본문 검증을 대신하지 않는다.

2026-10-26 실제 모델 검증: 최신 사건 지정 요청을 `SPECIFIC_CASE`/`BODY`로 판단하고 관측한 식별어를 유지했다.
공개 목록 11건에서 기존 첫 4건을 넘어선 직접 관련 판결의 읽기 후보를 선택했다.
의도 판단과 후보 선택의 실제 usage는 각각 입력 820/완료 180, 입력 1107/완료 323토큰이었다.
형사 판결 한 건으로 정답을 고정하지 않고 사용자 요청 범위에 맞는 직접 민사 판결도 후보로 인정한다.
이 결과는 목록 선택 검증이며 실제 판결 동일성은 본문 리랭크와 읽기에서 확인한다.

## 처리 흐름

### 후속 검색 진입 보장

후속 시작에 `FollowUpCasePlanner`가 최신 사용자 메시지와 실행용 방 법령 ID 목록만 받는다. 이 Client에는 대화 Advisor·이전 질문·기존 판례 본문을 전달하지 않는다.
요약·정리·재설명 요청은 `ANSWER_FROM_ROOM`이며 과거 판례 요청이나 근거 부족만으로 검색 동의를 제안하지 않는다. 최신 메시지가 명시적으로 판례·판결 조회나 검색을 요청할 때 `SEARCH_CASES`를 선택한다.
LLM은 `ANSWER_FROM_ROOM` 또는 `SEARCH_CASES`를 구조화해 반환한다. 검색 필요성을 동의 여부와 혼동하지 않는다.
서버는 `SEARCH_CASES`를 수락하면 동의가 없는 요청에서 검색 동의 메시지를 바로 구성하고 `caseSearchRequested=true`를 반환한다.
동의가 있으면 답변 준비 모델에 맡겨 두지 않고 실제 검색 파이프라인을 먼저 실행해 후보 결과를 전달한다.
서버는 리랭크에서 선정한 판례 본문을 읽고, 읽기에 성공하면 추가 도구 선택 단계 없이 최종 작성 단계에 전달한다.
일반/스트림 경로가 같은 규칙을 사용하며 새 검색 요청을 일반 법령 검토사항으로 대신하지 않는다.
`ANSWER_FROM_ROOM` 이후의 준비·답변 모델에는 `readRoomCase`만 제공한다. 검색·동의 요청 도구는 노출하지 않으며 세션 내부에서도 실행계획과 다른 검색·동의 호출을 거부한다. 답변 작성의 Advisor는 같은 방 대화 맥락을 유지한다.
검색 필요성은 LLM이 판단하고 서버는 방 법령 ID 소속·명시적 동의·실행·인용을 통제한다.

검색은 사용자 요청을 우선하며 방의 법령·조문과 일치해야 한다는 자격 제한을 두지 않는다.
현행 법령 제목과 맞지 않는 과거 사건도 찾는다. 참조법령 필터는 사용자가 해당 범위로 좁히길 원할 때 LLM이 선택하는 옵션이다.
판례 후보를 읽고 답변 근거로 편입할 때 사용자 요청·사실관계·법률 쟁점과의 관련성을 확인한다.
검색에 성공했다는 이유만으로 본문을 읽지 않은 목록을 법적 근거로 삼지 않으며, 인용한 검증 본문만 방에 누적한다.

실행계획 Client는 `APP_AI_FOLLOW_UP_PLAN_MODEL`/`REASONING_EFFORT`/`MAX_COMPLETION_TOKENS`로 설정하며 기본 mini/low/2048이다.

검색어 계획은 엄격한 JSON Schema를 사용한다. 형식·계약·관측 식별어 검증에 실패하면 원래 요청과 실패 단계만 제공해 한 번 수정한다. 수정 후에도 검증을 통과하지 못하면 검색을 실행하지 않고 미완료로 처리한다. 로그에는 실패 단계·시도 횟수·예외 유형만 남기며 질문 원문이나 모델 출력은 기록하지 않는다.

법령 질문 분석 방식을 응용해 목적(`intent`), 관측한 사건 식별어(`targets`), 짧은 검색 키워드(`queries`)를 구분한다. 직접 사건 요청은 식별어 자체를 우선 검색하고 법률 쟁점을 후속 질의로 보완한다. 최신 발화가 단순 검색 동의일 때는 상위 실행계획자가 대화에서 해소한 `issue`의 목적·대상을 유지하며, 동의 문장의 ‘관련 판례’를 유사 쟁점으로의 전환으로 해석하지 않는다. 법령 키워드 API의 소관 부처 필드는 판례 검색에 강제하지 않는다.

성수대교 직접 판례 요청 뒤 동의 발화만 전달한 실제 모델 테스트에서 `SPECIFIC_CASE`와 사건 식별어 보존을 확인했다. 이는 검색 계획 검증이며 실제 외부 판례 확보와 최종 답변의 성공을 보장하는 검증은 아니다.

1. 후속 상담은 먼저 근거 준비 단계를 실행한다. 이 단계의 모델 텍스트는 사용자 답변으로 보내지 않고 progress/info만 전달한다. 외부 판례 검색은 이번 요청의 allowCaseSearch=true일 때만 허용한다.
2. 후속 LLM이 scope를 제안하고 CaseQueryPlanner가 최신 사용자 질문·대화 쟁점·방 법령을 함께 보고 최종 범위와 목적을 판단한다. BODY는 본문(search=2), TITLE은 사건명(search=1), LAW_REFERENCE는 방 법령의 JO 필터를 적용한 본문 검색이다. 모든 범위를 강제로 호출하지 않는다.
3. 검색 계획은 `intent`, `targets`, `scope`, `queries`를 포함한다. `SPECIFIC_CASE`는 지정 사건 자체의 판결, `SIMILAR_ISSUE`는 유사 쟁점의 판례다. 질의는 최대 3개이며 지정 사건의 관측한 식별어·사건번호를 보존한다. 서버는 이름 규칙으로 의도를 분류하지 않는다. 원문/쟁점에 없는 식별어나 식별어를 모두 잃은 지정 사건 질의는 거부한다. 앞 검색이 비거나 무관하면 다음 용어를 시도한다.
4. 선택 범위에서 display=100으로 첫 페이지부터 hasNext=false까지 목록을 수집한다. 원문 식별자로 중복을 제거한다. 시간·API 호출·후보 수 제한으로 중단하면 searchComplete=false를 반환하고 로그에 미완료를 남긴다.
5. 지정 사건은 LLM이 최대 100개 목록의 사건번호·법원·선고일·공식 사건명을 비교해 읽을 후보 ID를 선정한다. 8번째 후보도 선택할 수 있으며 목록 밖 ID는 거부한다. 100개를 넘겨 전부 비교하지 못하면 미완료를 표시한다. 유사 쟁점 검색은 기존 제목 우선순위를 사용한다. 원문 확보는 회차당 최대 4건, 요청당 최대 6건이다. 목록 선별은 판결 확인이나 인용 허용이 아니다. 본문 리랭크는 목적과 식별어를 받아 지정 사건 자체를 직접 판단한 판결인지 평가하고 단순 언급·인용·다른 유사 사건으로 대체하지 않는다. 긴 본문은 머리·꼬리와 식별어 주변을 발췌하되 전체 원문은 유지한다.
6. 검색 자체는 방 법령의 연관성으로 차단하지 않는다. 본문을 사용자 요청·사건·법률 쟁점과 대조해 기본 관련성 60점 이상 상위 2개를 근거 읽기 후보로 제공한다. 기존 법령명·동일 조문 일치는 필수 조건이 아니다. readRoomCase로 실제 읽은 판례만 최종 인용 근거가 되며 인용한 검증 본문만 방에 누적한다.
7. 준비가 끝나면 도구 없는 최종 작성 단계에서 실제 답변만 스트리밍한다. 이미 읽은 판결 본문과 자연어 검색 요약을 제공한다. 내부 상태 코드가 조각으로 생성돼도 사용자 문장으로 치환한다. 동의 질문은 서버가 구성한 근거 포함 문구를 한 번만 보낸다.
8. UUID 인용·길이 검증 후 질문·답변·새 인용 판례를 원자적으로 저장한다. 중간 인용은 근거 번호로 표시하고 최종 인용 계약은 유지한다. 새 판례를 읽으면 info에는 출처·요지가 추가되며 마지막에는 실제 인용한 판례만 남긴다.

## 공식 가이드 대조

- [판례 목록 API](https://open.law.go.kr/LSO/openApi/guideResult.do?htmlName=precListGuide): search=1/2는 사건명/본문, JO는 참조법령명이다. 특정 사건번호는 nb이며 search=3은 참조판례 항목의 검색이다. 현재 상담 도구의 세 범위와 사건번호 조회를 구분해야 한다. 사건번호/참조판례 전용 경로는 이번 변경에 추가하지 않았다.
- 같은 목록 가이드의 기본 정렬은 선고일 내림차순이다. 첫 페이지 결과는 관련도 순위가 아니므로 전체 페이지 목록 수집과 후속 평가를 분리한다. 여러 용어를 한 질의에 넣었을 때의 불리언 의미를 가이드가 정의하지 않으므로 모델이 만든 짧은 변형 질의를 개별 요청한다.
- [판례 본문 API](https://open.law.go.kr/LSO/openApi/guideResult.do?htmlName=precInfoGuide): ID로 본문을 받고 판시사항·판결요지·참조조문을 활용한다. 일부 데이터 출처는 JSON 본문 제공에 제약이 있으므로 본문 수집 실패를 판례 부재로 처리하지 않는다.
- [시행일 법령 목록 API](https://open.law.go.kr/LSO/openApi/guideResult.do?htmlName=lsEfYdListGuide): 현재 법령 수집의 target=eflaw, 법령명/본문 범위, 현행 nw=3 사용을 대조했다. 법령과 판례의 같은 이름 파라미터도 대상별 의미를 구분한다.

## 제한과 환경 설정

| 환경변수 | 기본값 |
| --- | --- |
| APP_CASE_SEARCH_MAX_API_CALLS | 64회 |
| APP_CASE_SEARCH_MAX_CANDIDATES | 5000개 목록 후보 |
| APP_CASE_SEARCH_MAX_DETAILS | 요청당 본문 6건 |
| APP_CASE_SEARCH_DETAILS_PER_SEARCH | 회차당 본문 4건 |
| APP_CASE_SEARCH_MAX_SELECTED | 채택 2건 |
| APP_CASE_SEARCH_MINIMUM_SCORE | 60점 |
| APP_CASE_SEARCH_EXCERPT_CHARS | 본문당 4000자 발췌 |
| APP_CASE_SEARCH_MAX_RERANK_CALLS | 리랭크 2회 |
| APP_AI_CASE_QUERY_MODEL / REASONING_EFFORT / MAX_COMPLETION_TOKENS | gpt-5.4-mini / low / 2048 |
| APP_AI_CASE_RERANK_MODEL / REASONING_EFFORT / MAX_COMPLETION_TOKENS | gpt-5.4-mini / low / 4096 |

도구 최대 8회·판례 실행 컨텍스트 90초·새 인용 판례 최대 2건·방 최대 20건을 유지한다. 전체 판례 읽기는 `APP_CASE_SEARCH_BODY_MAX_INPUT_TOKENS`로 관리하며 기본 32000토큰, 허용 범위는 1~64000이다. 기존 12000 고정값은 검색에 성공한 긴 판결을 제외하는 문제가 있었다. 한도를 넘는 긴 판결은 예산 안에서 쟁점 주변·앞뒤 내용을 발췌해 읽고 partial=true 및 일부 발췌 표시를 제공한다. 두 판결을 함께 읽을 때는 남은 예산을 나눠 뒤 판결이 통째로 제외되지 않게 한다. 발췌에서 확인한 내용은 인용할 수 있지만 생략된 내용이나 전체 판결을 읽었다고 주장하지 않는다. 프롬프트에는 발췌본을, 인용 검증·저장에는 변경하지 않은 전체 원문을 사용한다. 예산이 완전히 소진된 경우만 추가 읽기를 중단한다. 동의 후 사전 검색을 마친 요청은 추가 도구 준비 단계를 반복하거나 다시 동의를 요청하지 않는다. 목록 전체 수집과 판결 본문 검토량은 별도 제한이다. 판례 리랭크는 LLM이며 조문 검색의 로컬 BGE와 별도다. 수집 원문은 기존 legal_source 불변 스냅샷으로 저장하고 새 DB 테이블이나 판례 벡터 컬렉션은 만들지 않는다.

## 로그

상담·판례 요약 줄마다 같은 traceId, 유형=최초/후속, 방 번호를 표시한다. 선택 범위·법률용어 생성 개수·질의 시도 순번·페이지별/누적 후보·전체 수집 완료 여부·본문 확보·리랭크 점수·채택/제외 사유·최종 완료/오류를 남긴다. 질문 본문·자유 형식 판단·키는 기록하지 않으며 질의는 지문으로 구분한다.

```powershell
docker logs --since 30m molelaw-app-local-backend-1 2>&1 | Select-String '유형=후속'
```

최초 요약은 유형=최초로, 한 실행은 복사한 traceId로 필터링한다. 내부 상태는 진단용으로 유지하지만 최종 사용자 답변에는 자연어로 전달한다. 검색을 끝내지 못한 경우나 판례를 찾았지만 본문 예산에 걸린 경우를 전체 판례의 부재로 표현하지 않는다.
